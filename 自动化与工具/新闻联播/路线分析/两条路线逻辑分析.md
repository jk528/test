# 新闻联播日报生成 — 两条路线逻辑分析

> **创建时间**：2026-10-19
> **分析目的**：梳理"机制的AI"与"极致的本地化脚本"两条技术路线的核心逻辑、优劣与适用场景

---

## 一、背景

当前新闻联播日报生成系统已有混合方案（脚本抓取 1-5 部分 + AI 精读六要素 + 脚本渲染 6-7 部分）。
现需将两条技术路线拆开分析，明确各自的完整逻辑链路、能力边界与取舍依据。

---

## 二、路线 A：机制的 AI

### 2.1 核心理念

**让 AI 理解新闻内容，由 AI 完成分类、提炼、填充与质检。**

AI 不是辅助工具，而是生成流程的**主引擎**。脚本只负责把原始数据搬到 AI 面前，剩下的交给 AI 判断。

### 2.2 逻辑链路

```
央视网/齐鲁网 → [脚本] 原始数据采集 → [AI] 逐条精读理解
  → [AI] 分类修正（假期文旅→社会文化、经济调研→经济要闻）
  → [AI] 六要素提炼（地点/人物/事件/原因/方式）
  → [AI] 快讯合集拆分与子条目展开
  → [AI] 第七部分人物/机构/事件归类
  → [AI] 质检自检（"—"占比、分类合理性、编号连续性）
  → [脚本] 渲染最终 Markdown
```

### 2.3 关键环节

| 环节 | 做什么 | 为什么需要 AI |
|------|--------|--------------|
| 内容理解 | 逐条阅读 title + summary + full_text | 正则无法"理解"新闻在讲什么 |
| 六要素提炼 | 从正文提取地点、人物职务姓名、事件、原因、方式 | 需要语义理解，非模式匹配 |
| 分类修正 | 纠正脚本的常见分类错误 | 分类标准是语义的，不是关键字的 |
| 合集拆分 | 判断快讯子条目属于国内还是国际 | 需要判断内容归属 |
| 人物/机构归类 | 第七部分把人物和机构分开，用全称 | 需要实体识别 + 知识匹配 |
| 质量自检 | 判断"—"是否合理、分类是否准确 | 规则质检查不出语义错误 |

### 2.4 优势

1. **理解能力强**：能处理正则无法覆盖的新新闻类型、新表达方式
2. **分类准确**：语义分类远优于关键字匹配，尤其对边界模糊的新闻
3. **六要素质量高**：从"模式匹配填占位符"升级为"阅读理解后提炼"
4. **自适应**：央视网页面结构变化时，AI 能容错理解，不依赖固定 CSS 选择器
5. **可扩展**：加新分析维度只需改 prompt，不需要写新正则

### 2.5 劣势

1. **成本**：每条日报消耗 AI API 积分（约 10-20 条新闻 × 每条精读）
2. **延迟**：AI 调用串行精读，全流程约 2-5 分钟（脚本方案 <30 秒）
3. **不确定性**：AI 输出质量有波动，需要质检兜底
4. **依赖外部**：断网或 API 不可用时完全停摆
5. **隐私**：新闻正文需发送到外部 API

### 2.6 适用场景

- 对六要素质量要求高（人物/事件/原因需要语义提炼）
- 新闻类型多样、边界模糊、正则难以穷举
- 有稳定的 AI API 积分来源
- 可接受分钟级延迟

## 三、路线 B：极致的本地化脚本

### 3.1 核心理念

**用正则、规则、映射表把一切可穷举的模式写死，零 AI 依赖，纯本地运行。**

不调用任何 AI API，所有分类、提炼、填充全部由 Python 脚本 + 正则 + 预定义规则表完成。

### 3.2 逻辑链路

```
央视网/齐鲁网 → [脚本] 原始数据采集
  → [正则] 标题分类（关键字→类别映射表）
  → [正则] 六要素模式匹配
    ├─ 地点：提取"在XX" / "XX市" / 国名正则
    ├─ 人物：提取"职务+姓名"正则（不脱敏）
    ├─ 事件：取标题核心短语（去前缀/去修饰）
    ├─ 原因：匹配"为了""旨在""由于"后接短语
    └─ 方式：匹配"通过""采用""印发"后接短语
  → [规则表] 快讯合集拆分（is_dir 标记 + 子条目展开）
  → [映射表] 第七部分人物/机构全称映射（70+ 预定义）
  → [正则] 占位符检测（26 种数据占位正则）
  → [脚本] 质检（结构/表头/链接/"—"占比）
  → [脚本] 渲染最终 Markdown
```

### 3.3 关键规则资产

| 资产 | 内容 | 维护方式 |
|------|------|---------|
| 分类关键字表 | 标题关键字 → 类别映射（如"习近平"→头条要闻、"经济"→经济要闻） | 手动维护，遇新词追加 |
| 人物全称映射 | 70+ 机构全称（如"国务院安委会办公室"） | 手动维护 |
| 职务+姓名正则 | `(?P<title>厅长\|部长\|主任...)(?P<name>[\u4e00-\u9fa5]{2,4})` | 正则，误召率较高 |
| 地点正则 | 国名/省名/市名 + "在XX"句式 | 正则 + 地名表 |
| 因果句式正则 | "为了/旨在/由于/因为" + 后接短语 | 正则，覆盖率有限 |
| 数据占位符正则 | 26 种数值模式（百分比/金额/数量等） | 正则 |
| CNTV 接口兜底 | 返回 <5 条时回退央视网日页 | 脚本逻辑 |

### 3.4 优势

1. **零成本**：不消耗任何 AI 积分，纯本地运行
2. **极速**：全流程 15-30 秒
3. **确定性**：同样输入永远产出同样输出，无波动
4. **零依赖**：断网到外部 API 不影响（只需能访问央视网/齐鲁网）
5. **可无人值守**：定时任务稳定运行，不需要人盯着
6. **可审计**：每一步逻辑都是显式规则，出问题能定位到具体正则

### 3.5 劣势

1. **理解能力为零**：遇到没见过的新闻类型/表达方式，分类和六要素会填错或填"—"
2. **维护负担**：新词汇、新人物、新机构需要手动追加映射表
3. **六要素质量低**：正则提取的人物/原因/方式经常不准，"—"占比高
4. **分类易错**：关键字匹配无法处理边界模糊的新闻（如"假期文旅"被分到"社会文化"还是"经济"）
5. **泛化差**：央视网页面结构大改时，正则全部失效，需要人工修
6. **第七部分粗糙**：人物/机构归类靠映射表，没映射到的就漏掉

### 3.6 适用场景

- 每日无人值守定时生成，要求稳定可预测
- 无 AI API 积分或积分不稳定
- 对六要素质量要求不高，能接受"—"占位
- 需要秒级出报告
- 归档批量重建（rebuild_archives.py 跑历史数据）

## 四、两条路线对比

### 4.1 核心差异

| 维度 | 路线 A：机制的 AI | 路线 B：极致本地化脚本 |
|------|-------------------|----------------------|
| 生成引擎 | AI 语义理解 | 正则 + 规则表 |
| 六要素质量 | 高（语义提炼） | 低（模式匹配，"—"多） |
| 分类准确性 | 高（语义判断） | 中（关键字匹配，有误分类） |
| 速度 | 2-5 分钟 | 15-30 秒 |
| 成本 | 每次消耗 AI 积分 | 零 |
| 确定性 | 有波动 | 完全确定 |
| 外部依赖 | 央视网 + 齐鲁网 + AI API | 央视网 + 齐鲁网 |
| 维护方式 | 改 prompt | 改正则 + 追加映射表 |
| 泛化能力 | 强（新表达方式自动处理） | 弱（没见过就填不对） |
| 无人值守 | 可（但 API 不稳定时失败） | 可（最稳定） |

### 4.2 质量边界

| 质量项 | 路线 A | 路线 B |
|--------|--------|--------|
| 六要素"—"占比 | <10%（AI 依据正文实质提炼） | 30-50%（正则覆盖不到的填"—"） |
| 分类错误率 | <5%（语义分类） | 15-25%（关键字误匹配） |
| 第七部分人物遗漏 | <5%（AI 实体识别） | 20-30%（映射表外的漏掉） |
| 快讯子条目拆分 | AI 判断国内/国际 | 正则 `_looks_international` |
| 新类型新闻适应 | 自动适应 | 需手动追加规则 |

### 4.3 当前系统的混合策略

现有"最终版"实际是两条路线的**折中**：

```
脚本采集 1-5 部分（路线 B 的采集层）
  + AI 精读六要素（路线 A 的理解层）
  + 脚本渲染 6-7 部分（路线 B 的渲染层）
  + 脚本质检（路线 B 的质检层）
```

- **oneshot 模式**：纯路线 B（正则一键生成，零 AI）
- **ai_api 模式**：混合（脚本采集 + AI 填六要素 + 脚本渲染）
- **staged 模式**：分阶段，中间产物可调试

## 五、路线选择建议

### 5.1 选路线 A（机制的 AI）如果

- 六要素质量是核心交付要求
- 有稳定积分来源
- 可接受分钟级延迟
- 新闻类型多样且变化快

### 5.2 选路线 B（极致本地化脚本）如果

- 首要目标是稳定无人值守
- 积分有限或不可靠
- 需要秒级出报告
- 可接受六要素质量降级
- 需要批量重建历史归档

### 5.3 选混合（当前策略）如果

- 日常用 oneshot 保证产出（路线 B 兜底）
- 关键日期用 ai_api 提升质量（路线 A 增强）
- 定时任务跑 oneshot，人工触发跑 ai_api

---

## 六、演进方向

| 方向 | 路线 A 演进 | 路线 B 演进 |
|------|------------|------------|
| 提速 | 批量 API 调用 / 并发精读 | 已到极限（受网络 I/O 约束） |
| 提质 | 更好的 prompt + few-shot 示例 | 扩充映射表 + 更细粒度正则 |
| 降本 | 精简 prompt / 只对低置信条目调 AI | 本身为零成本 |
| 健壮 | 脚本兜底（AI 失败时降级 oneshot） | CNTV 接口漂移兜底已有 |
| 终极形态 | AI 全流程 + 脚本只管 IO | 规则表自学习（从 AI 产出反哺规则） |

**最可能的终态**：路线 B 做日常兜底（保证每天都有报告），路线 A 做关键日期增强（重要新闻深度提炼），两条路线共享同一套渲染和质检管线。

---

## 七、总结

| | 路线 A | 路线 B |
|---|--------|--------|
| 一句话 | **AI 理解内容，语义驱动生成** | **正则穷举模式，规则驱动生成** |
| 核心矛盾 | 质量高但成本高、不确定 | 稳定快但质量低、维护累 |
| 最佳角色 | 质量增强层 | 稳定兜底层 |
| 共享基座 | 同一套数据采集 + 渲染 + 质检管线 | 同一套数据采集 + 渲染 + 质检管线 |

两条路线不是互斥的，而是**同一系统的两个置信档位**：路线 B 保证下限（每天都有报告），路线 A 拉高上限（关键日期深度提炼）。当前最终版的 oneshot/ai_api 双模式已经实现了这一分层。
