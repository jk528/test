# 天翼云盘登录态保活与维护

> 整理日期：2026-10-29　|　回答问题：**「天翼云盘如何延长登录时间？」**
> 结论先行：**保活无效（有实测证据）——会话由服务端吊销而非滑动过期；现行逻辑为「自动提取兜底 + 精准识别吊销 + 指引手动重登」；根治方案是关闭设备锁后启用密码自动重登（待决策）。**

## 一、会话机制：为什么「保活」这个思路不成立

`COOKIE_LOGIN_USER` 不是自包含的长期凭证（对比百度 BDUSS 实测 399 天有效），而是**服务端会话凭证**：

- 会话生命周期由服务端统一管理，**不是滑动过期**。滑动过期 = 每次使用自动刷新有效期，那样保活才有意义；天翼不是——用不用、用多勤，到点或触发策略照样吊销
- **实测证据**：签到脚本每天 10:35 都在用该会话调 `userSign.action`（等价于每日保活），10-25 会话正常，10-26 仍被服务端吊销——**活跃使用不能阻止吊销**
- 吊销后的特征：`HTTP 400 {"errorCode":"InvalidSessionKey","errorMsg":"cookieUserSession is null or invalid"}`，且**连 `getUserInfo.do` 等只读接口也一并 400**（整个会话作废，非单接口问题）

## 二、失效时间线（2026-10-29 本次实测）

| 时间 | 现象 |
|---|---|
| 10-25 06:42 | 平台接入：夸克浏览器登录 cloud.189.cn，脚本提取 `COOKIE_LOGIN_USER` + `JSESSIONID` 回写配置 |
| 10-25 09:56 | 签到正常（isSign=true，累计 +65M）——会话健康 |
| 10-26 10:47 | 签到返回 400 InvalidSessionKey；脚本自动从浏览器重提取 → **仍是同一死会话**（值未变），重试仍 400 |
| 10-26 ~ 10-29 | 连续失败，等待浏览器重新登录 |

两点关键观察：

1. **会话寿命不固定**（本实例约 1 天）。吊销触发源在服务端，推测为异端登录挤掉网页会话（手机 App / PC 客户端登录同账号）、账号安全策略强制下线等，无法从脚本侧预判或规避
2. **浏览器里「看起来已登录」≠ 会话有效**：COOKIE_LOGIN_USER 仍躺在浏览器 Cookie 库里（提取、解密全正常），但服务端已注销对应会话——所以「失效自动重新提取」救不了这种失效，**必须走一次完整登录流程签发新会话**

## 三、现行处理逻辑（tianyi_checkin.js，2026-10-29 版）

```
config 有 Cookie？
  ├─ 无 → 从夸克浏览器提取（VSS+DPAPI+AES-GCM 链路）→ 回写 → 签到
  └─ 有 → 直接签到
           ├─ 成功 → 结束（今日已签 / 签到成功 +xxM）
           ├─ 网络异常 → 报错退出
           └─ 会话失效 → 自动从夸克浏览器重提取 → 回写 → 重试一次
                         ├─ 成功 → 已恢复（普通 Cookie 失效场景，全自动）
                         └─ 仍失效且响应含 InvalidSessionKey
                              → 判定「服务端吊销会话」（与普通失效区分）
                              → 输出指引：夸克浏览器重登 cloud.189.cn
                              → 退出码 1（如实上报，不误报）
```

**判定要点**：响应体命中 `InvalidSessionKey` / `cookieUserSession` 关键字即标记 `sessionInvalid`，报错文案区分两种失效：

| 失效类型 | 识别特征 | 报错指引 |
|---|---|---|
| 服务端吊销会话 | 400 + InvalidSessionKey，重提取后依旧 | 「浏览器中的登录态也已过期，请重新登录（若显示已登录，退出后重登以刷新会话）；登录后无需改配置，下次自动提取恢复」 |
| 普通 Cookie 失效 | 提取不到 / 解密失败 / 浏览器未登录 | 「请用夸克浏览器登录 cloud.189.cn 网页版后重试」 |

**用户侧操作只有一步**：夸克浏览器打开 cloud.189.cn 重新登录。若页面显示「已登录」，需先退出再登录——否则签发不出新会话（这正是 10-26 起自动恢复失灵的原因）。之后零改动，次日 10:35 计划任务自动提取新 Cookie 恢复。

## 四、为什么不做「定时保活脚本」

| 论点 | 依据 |
|---|---|
| 会话非滑动过期，调用不续命 | 每日签到的活跃使用未能阻止 10-26 吊销（日志实锤） |
| 吊销触发源在服务端 | 异端登录 / 安全策略，本机无法预判和规避 |
| 额外保活请求徒增风险 | 高频访问用户信息类接口有触发风控的嫌疑，且收益为零 |

结论：**不做保活脚本，是经过实测验证的正确决策，不是没做。**

## 五、根治路线（可选，待决策）

保活既然无效，「延长登录时间」的唯一真正答案是让脚本**具备自动重新登录能力**：

| 方案 | 做法 | 效果 | 代价 |
|---|---|---|---|
| A. 关设备锁 + 密码自动重登 | 天翼云盘 App → 设置 → 账号与安全 → **关闭设备锁**；脚本在「重提取仍失效」时走 RSA 加密账号密码登录（`loginSubmit.do`，`dynamicCheck=false`）拿全新会话 | **全自动，永不再手动登录** | 账号安全性略降（新设备登录不再短信二次校验） |
| B. 维持现状 | 失效后手动在夸克浏览器重登一次 | 不定期人工介入（频率 ≈ 会话寿命，不固定） | 无 |

密码链路技术可行性已验证（上游青龙脚本 agluo/ql-script-hub 的 `ty_netdisk_checkin.py` 2026 年仍在用同链路）；当前唯一障碍是设备锁（`loginSubmit.do` 返回 `result=-133` 二次设备校验），**设备锁只能由用户在 App 里手动关闭，脚本侧无法绕过、也不应绕过**。

若选方案 A：关闭设备锁后补两处即可——`tianyi_config.json` 增加可选 `username` / `password` 字段；`tianyi_checkin.js` 在吊销分支前插入「密码重登 → 回写新 Cookie → 重试」兜底（未配置密码时行为与现状完全一致）。

## 六、巡检关注点

- 失效不可避免，关注点是**别静默失效**：日志中天翼 `[FAIL]` **连续 ≥ 2 天**即需人工重登（单日失败大概率是普通 Cookie 失效，已自动恢复）
- 服务器重启后（夸克浏览器进程彻底退出）：COOKIE_LOGIN_USER 属会话 Cookie 会丢失，需确认 cloud.189.cn 仍登录
- 改密码 / 动账号安全设置（开/关设备锁、二次验证）：会话立即作废，属预期行为
