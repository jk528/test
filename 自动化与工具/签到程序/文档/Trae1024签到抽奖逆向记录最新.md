## 四、接口清单

网关：`https://api.trae.cn`（与签到同网关、同鉴权）

| 用途 | 方法+路径 | 请求体 |
|------|-----------|--------|
| 活动/抽奖状态 | POST `/trae/api/v2/ug/activity/info` | `{"version_code":"<appVersion>","req_source":1}` |
| 执行抽奖 | POST `/trae/api/v2/ug/activity/action` | `{"activity_id":"checkin_1024","req_source":1}` |

> **req_source 勘误（2026-10-20 实测修正）**：必须为 **1** 而非 2。`req_source=2` 时 `activity/info` 只返回 6 个活动且**不含 checkin_1024**（与客户端 CommercialActivityService 活动集不一致）；`=1` 时返回 8 个活动，含 checkin_1024，与客户端完全一致。已抽后 `activity/info` 不再返回该活动（服务端隐藏），次日 00:00 重置后重新出现。
>
> **action 响应结构**：成功时**无 `code`/`data` 包装**，`work_extra` 直接在顶层：`{"work_extra":{"granted":true,"prize_type":2,"prize_text":"AI Build 专属抵扣券","coupon_face_amount_fen":1000,...}}`。失败时才有 `code` 字段（9090/9102/1002/4001）。

**鉴权头**（与 `checkin_credits` 完全一致）：

```text
Authorization: Cloud-IDE-JWT <token>
x-device-id: <纯数字 device_id>   # local_env.json 的 device_id
x-device-type: Windows
x-os-version: <os.release()>
x-app-version: <客户端版本，如 1.107.1>
```

> 关键：无需额外字段；`req_source=1`（见上方勘误）。已抽后 `activity/info` 不再返回该活动（服务端隐藏），次日 00:00 重置后重新出现。

## 五、响应判定逻辑（从主进程 J1 / RGe / PGe / Que 还原）

### 5.1 业务错误码（J1）

| code | 含义 |
|------|------|
| 9090 | 活动不可用（含"今日已抽"/活动未开始或已结束） |
| 9102 | 未签到 |
| 1002 | 鉴权失败 |
| 4001 | 参数错误 |

### 5.2 状态解析（RGe，从 activity/info）

- 列表内无 `checkin_1024` 或 `Enabled!==true` → `unavailable`
- `work_extra.granted===true` → `draw.kind:"granted"`（今日已抽，带 prize）
- `granted===false` 且 `eligible`/`grantable` 为布尔 → `draw.kind:"not_drawn"`（**可抽**）

### 5.3 抽奖结果解析（PGe + Que）

- `data.work_extra.granted===true` → 抽奖成功
  - `prize_type=1` → 积分（`general_credits`）
  - `prize_type=2` → 抵扣券（`coupon_face_amount_fen`，单位：分）
  - `prize_type=3` → 幸运奖
- 否则未成功（今日已抽/未签到/活动结束等）

### 5.4 抽奖执行前置条件（controller run()）

```
checkin==="signed"（当天已签到）
state.kind==="ready"
state.eligible===true
state.grantable===true
state.draw.kind==="not_drawn"（当天未抽）
```

任一不满足 → `blocked`，不发奖。**这就是"当天第二次抽奖"被拦截的机制。**
