## 二、重大功能演进叙事

### 2.1 阅读器内核：为什么是 Monaco，以及"给 VS Code 的编辑器打补丁"的生存史

**为什么做它**：项目定位是"本地 TXT 小说阅读器"，但小说动辄数百万字、需要精确的行/列定位（书签、笔记、划线都要锚定到行列）、需要只读与编辑双模式。富文本 div 方案做不了大文件和高亮性能，而 Monaco（VS Code 内核）天然具备：百万行级性能、行列模型、装饰器（decorations）体系、stickyScroll、Diff 编辑器（智能排版预览直接复用）、查找栏。README 明确写"框架 Electron_+Vue_+Monaco"。内容上色的灵感也直接来源于 VS Code 插件 vscode-txt-syntax——**作者本来就是从"VS Code 里看小说"这个体验出发造的轮子**。

**初版怎么做**：1.0 即采用 Monaco；2.0 做 Monaco 中文化；2.2 编辑模式加小地图（显示大号章节名，便于长文定位）。

**遇到的问题（_fix 痕迹与已知问题清单）**：

1. **中文换行不准**——README："阅读器默认使用一套比较简单的换行算法，效率高，但不够准确，会出现该换行却没有换行的情况。**这个问题连 VSCode 都没能完美解决**。"于是提供「高级换行策略」，但"性能较差……会出现明显卡顿"，且"会有很大的内存开销，且这个占用难以被释放，见 [microsoft/monaco-editor#5311]"（README 直接挂出上游 issue 链接，作为已知无法解决的问题）。
2. **大文件优化反噬**——2.6 修复列表："**禁用 Monaco 的大文件优化，避免大文件无法自动换行和显示粘性标题**"。Monaco 自身的大文件优化路径（禁用某些特性换取性能）与阅读器的软换行+粘性标题需求冲突，只能整体关掉。
3. **中文符号撑破行宽**——3.7 修复 #65："中文换行优化补上 `♡` `※` `☆` 等网文常用符号，避免右侧溢出"。
4. **内嵌字体选区错位**——3.7 修复 #22："内嵌京華老宋体纯英文行选区错位问题（**关闭 Monaco 等宽渲染优化**）"。又一个"关掉 Monaco 内置优化"的案例。
5. **圆角选区抠图露底**——3.8："阅读器多行选区列重叠处不再露出实心底色块（**关掉 Monaco 圆角选区抠图**），避免盖住背景图"。Monaco 默认在多行选区重叠的内角铺 `.cslr` 再用编辑器底色抠图；阅读器底色透明以透出背景图，一抠就露馅。
6. **粘性标题与背景图互相伤害**——3.8.11："修复背景图功能带来的堆叠粘性章节标题问题"；更早 3.8 直接"粘性章节标题去掉阴影，避免切开背景图"。
7. **找书窗口二次打开粘性标题失效**——docs 记载 DocumentSymbolProvider 须随实例重新注册（卸载时 dispose），否则第二次打开失效。

**如何解决——核心思路是"补丁层"**：

- 3.4 是里程碑（release 原文标注"重要体验优化版本，建议更新"）：「**启用中文换行优化**（默认开启）：给 Monaco 打补丁，在简单换行策略下将中文标点按全角估算、用汉字校准全角字宽，减轻行尾缺字与溢出；不作用于高级换行策略」。
- 「**段间距**（0～100，默认 0）：给 Monaco 打补丁，每个物理行结束后增加常数像素空隙；同一物理行因软换行产生的多行之间不加距（区别于行间距 lineHeight，**额外状态 O(1)**）」（#53）。docs 补充实现：经 **Vite transform 改写 Monaco LinesLayout**——行偏移/视口累加/ViewZone 绝对 top 全部计入段间距；"若只改行高未改 whitespace 偏移，md 插图会叠在上方正文上"。
- 章节识别接入 Monaco：`stickyScroll` + 自写 `DocumentSymbolProvider`（chapterStickyScroll.ts）实现粘性章节标题。
- 翻页防遮挡（3.7，#80）："空格/PageUp/PageDown 翻页时相邻两页重叠一条完整行，避免被粘性章节标题盖住"——向下用落点预测条高（`predictStickyChapterScrollHeight`），向上用 `getTargetAtClientPoint` 取粘性条下方第一条完整行。

**现状**：Monaco 补丁体系成为项目的护城河之一（中文换行、段间距、左右边距、粘性标题、阅读尺锚点、点击模式翻页全部构建其上）；唯一明确无解的是高级换行策略的内存问题（上游 #5311），README 以 WARNING 形式告知用户并建议默认不开。

### 2.2 内容上色与高亮：从"灵感来源"到产品灵魂

**为什么做它**：README 第一句卖点："一款**会给内容上色的本地 TXT 小说阅读器**，带给你不一样的阅读体验！"；功能表里"个性内容上色"加粗："使用一套自定义的高亮规则对内容进行着色，带来独特的阅读体验！"灵感来源标注为 VS Code 插件 vscode-txt-syntax——把代码语法高亮的视觉体验移植到网文（引号内对话、括注、数字、字母各自着色，长篇阅读时对话与叙述一眼可分）。

**演进路径**：

- 1.1：自定义阅读区配色 + 自定义高亮词与高亮配色；引号/括号支持跨行匹配开关；字母高亮匹配带声调字符（à、é）。
- 2.8（#19）：配色选项支持**开关**——"比如阅读英文书籍时，可暂时关掉「字母」上色"。这是用户反馈驱动的典型细节。
- 3.5：引号内文字支持全角双引号 ＂（U+FF02）。
- 3.5（#56）：高亮词**AI 检索**——"支持 AI 检索语义（如人名/地名），批量添加高亮词"；单项多词（"一个高亮词项可以包含 东邪/西毒/南帝/北丐/中神通，展示为 东邪 (+4)"）；拖动合并/拆分/移动/排序的完整手势系统。
- 3.8：上色范围大扩容——圈号/括注/数点/罗马数字（①❶⑴㈠⒈Ⅰ）按数字上色、上下标/分数（¹²³ ₁₂₃ ½¼¾）按数字上色、括号补 ‹›〈〉«»﹝﹞〔〕［］、网文常用符号（几何/花色/星月/勾叉/音符/箭头/单位货币百分与比较运算）。
- 3.8：**配色方案**成型（#19）——内置 8 套（默认/素纸/羊皮纸/护眼/毛绒地毯/墨竹/雪梅/星空）+ 阅读区**背景图**（混合模式/不透明度/平铺/对齐，随 WebDAV 同步）+ 拾色器增强（HSL/滴管全屏取色）。

**带来的新问题**：背景图与透明底色引发连锁修复——粘性标题阴影切开背景图（去阴影）、Monaco 圆角选区抠图露底（关圆角）、背景图路径问题（3.8.1 修复）、堆叠粘性章节标题（3.8.11 修复）。**一次视觉特性引入，两周内产生了 4 个后续 fix**，是"新功能带来新问题"的典型样本。

**沉淀**：内容上色 + 高亮词 + 配色方案 + 背景图构成"阅读体验层"，与 Monaco 补丁层（排版）分离，各自可独立演进。

### 2.3 大文件流式读取：v2.1 的加载管线重构

**为什么做它**：网文单文件 10MB+、数百万字很常见。初版（1.x）的加载流程是"流式读取 → 边读边统计字数/匹配章节"，大文件打开慢、且每次改格式化选项（压缩空行/行首缩进/章节规则）都要**重新加载文件**。

**v2.1 怎么改**（CHANGELOG 原文）：

> 流式加载 → 文本格式化 → 章节生成逻辑重构：
> - 加载期间不统计字数、不匹配章节，在加载完成后再统一处理，逻辑更简单清晰
> - 「压缩空行」「行首缩进」、章节匹配规则变更等，**不再重新加载文件，直接基于内存中的物理文本进行操作**，对大文件的体验有明显优化

**配套细节**（后续版本与 docs）：
- 2.2：只读↔编辑以"第二行视觉行为锚点"恢复视口，减轻排版差异跳动；编辑模式自动刷新章节，但"出于性能考虑，内容大于 30 万行时，会禁用自动刷新"。
- docs 记载当前架构：物理文本（physical lines）常驻内存，展示层（display lines）做替换/转换/缩进的映射（`ebookDisplayLineToPhysical`）；装饰仅注册视口 ±约 80 行；脚注极多时侧车批量处理。
- 2.6 的"禁用 Monaco 大文件优化"（见 2.1）实际是为流式管线让路——Monaco 自己的优化路径与自管管线冲突。

**沉淀**：这套"物理行常驻 + 展示层映射 + 装饰视口化"的管线，后来直接支撑了 .md 内链/插图（2.5）、找书阅读器复用（3.0）、阅读尺锚点（3.8）。

### 2.4 电子书格式支持：两次推翻的转换方案

**初版（v1.2，2026-04-13）**：支持 epub/mobi/azw3/fb2/fbz/pdf/chm，"打开时会**转换为 .txt** 进行加载"。此时用 `<<A>>`/`<<ID>>`/`<<IMG>>` 等自造特殊标记表示链接/图片。

**第一次推翻（v2.5，2026-06-12）**——CHANGELOG 原文：

> 打开其他电子书格式不再转换为 .txt，而是转换为 **Markdown（.md）**
> - 电子书目录会映射为相应层级的 ATX `#` 标题
> - 内链/注脚：支持鼠标移上显示内容、跳转与回跳
> - 外链：点击打开系统默认浏览器
> - 以前转换的带有 `<<A>>`/`<<ID>>`/`<<IMG>>` 等特殊标记的 `.txt` 文件会被当成普通的纯文本文件，**请重新转换**

动机线索：自造标记是私有格式，既不能展示图片（小说插图），又与生态割裂；换成标准 Markdown 后标题层级（章节列表缩进）、图片、链接全部自然表达，还顺带获得了 v2.2 的 ".md 直接打开"能力。

**第二次推翻（v3.3，2026-08-02）**：

> 电子书转 Markdown：图片/链接目标路径中的 `(` `)` `\` 等按 CommonMark 转义写出；**解析侧走 marked、不再做非标准兜底（旧 md 需重新转换）**

从手写正则解析 Markdown 迁移到 marked 的 `Lexer.lexInline`——docs 明确记载"扫描基于 marked Lexer.lexInline（与 AI 助手 Markdown 规则一致），**替代手写正则**"。这是典型的"自造轮子 → 标准库"回归。

**转换管线的深度演化**（docs/基础功能.md）：
- **CHM**：作者"基于 libmspack（GNU GPL）**移植了一套 JavaScript 实现**"——为一个格式移植了整个 C 库（chmArchive + lzxDecode）。
- **MOBI/AZW3**：先 `tryConvertZipAsEpub`（部分 AZW3 实为 ePub 封装），否则走 foliate-js 的 MOBI 引擎；目录缺失时从 NCX 重建。
- **PDF 三连修（v3.7）**：①中文 PDF 改用随包 pdfjs-dist CMap/wasm（"不会因 CSP 拦截 jsDelivr 卡在转换中"）；②插图按 XObject 抽取（JPEG 原样、JPX/JBIG2 走 wasm；同一对象只解码一次，**不再逐页 getOperatorList**——"那会把整页文字路径搬到主线程，比 Foliate 的 page.render 慢很多"）；③Indexed 调色板正确展开（含 4bit 打包索引，"不再把索引字节当成 RGB 解成黑条/下半截全黑"）。
- **目录注入**：从各格式嵌入目录（EPUB nav/NCX、MOBI toc、PDF getOutline）写 ATX 标题 + `<span id>` 锚点；标题匹配经历"包含匹配 → 仅精确匹配"的收紧（docs："**已移除**「包含」匹配与按标点拆段的子串匹配，避免目录为『卷一 周纪一』、正文为两行『卷一』+『周纪一』时误将『卷一』升为 # 卷一"）。
- **缓存与和解**：严格缓存（路径+mtime 一致才复用）+ 多候选路径和解查找（输出目录变更后旧文件仍在原记录路径）。
- **行内字形图（v3.8.10-11）**："段落里的行内图片（如字形图）不再拆成独占行插图，阅读器按字号显示在句中"。

**沉淀**：统一 .md 中间格式 + 严格缓存 + "需重新转换"的坦诚提示，构成所有格式的公共底座；新增格式只需实现 parse*.ts 一个解析器。

### 2.6 语音朗读：从三引擎到七引擎，与 Edge TTS 的 WordBoundary 攻坚

**为什么做它**：网文场景的刚需（通勤/做家务时"听书"），且网文对话密度高，天然适合多角色演绎。

**引擎扩张时间线**：
- 2.0：Edge TTS、系统语音（Web Speech API）、阿里云通义（DashScope/Qwen3-TTS）三引擎首发。
- 2.7：MiniMax；**多音色**（旁白/对白分轨、对白引号样式多选）；**AI 识别说话人**（识别性别用男声/女声，角色卡专属音色）。
- 2.8：**小米 MiMo**（"支持音色定制（VoiceDesign）和音色克隆（VoiceClone），目前限免，可以薅一波"——作者原话，薅羊毛式接入云端 TTS）；情绪标注开关（"如果感觉情绪听感不自然，可关闭"）。
- 3.2（#36）：Windows 讲述人自然语音（PowerShell System.Speech 调 SAPI5，配合 NaturalVoiceSAPIAdapter）；docs 记载动机：系统语音枚举"Windows 上多为 OneCore，**看不到** SAPI5/NaturalVoiceSAPIAdapter 自然语音"——为用上 Windows 本地高质量音色专门写了 winSapiProvider。
- 3.7（#67）：火山引擎豆包语音合成大模型 2.0（内置官方 2.0 主表 293 + 多语种表 151 共 444 音色；方言标签；角色卡专属音色可指定语种/方言）。

**遇到的问题与解决**：

1. **AI 识别说话人准确率**——3.2 修复 #39："AI 识别说话人时会带上少量上下文，能一定程度上增加一些准确性"。docs 记载最终方案：按行识别，输入为当前行原文+角色表姓名/别名+**邻近参考行**（"向两侧穿过纯对白行至首个非纯对白行后再多收一行……单向最多约 15 非空行；不做全书向量检索"），结果缓存键含上下文。
2. **情绪听感不自然**——2.8 加开关；3.7 文档化各引擎情绪映射差异：通义 instruct/MiMo 走自然语言语气描述；火山 2.0 改对话式指令写入 additions.context_texts（"官方仅此字段；不写 req_params 顶层，也不用 1.0 多情感音色的 audio_params.emotion"）；MiniMax 固定 9 枚举标签"无法映射则不传"。
3. **试听音频不停止**——2.8 修复："切换到其他设置页或关闭设置面板，现在会停止试听音频"。
4. **快捷键全禁**——2.8 修复："之前会禁用所有快捷键，现在只禁用阅读器滚动/跳转相关的快捷键"。
5. **MiMo 网关选择**——3.2 修复 #41："小米 MiMo 按 API 密钥前缀自动选择网关（sk- 走按量付费，tp- 走 Token Plan 中国集群）"。
6. **朗读过滤与自动暂停**——3.7（#71）："按规则把括号、加粗等匹配段替换为空格后再合成（正则可跨行）；可按章节数或时长自动暂停"。细节：过滤的是 TTS 文本但"AI 说话人识别仍用原文"；自动暂停按"累计实际出声时间（暂停不计）"。

**Edge TTS 标点停顿攻坚（v3.8.9–3.8.11，PR #90）——最精彩的一段工程叙事**：

背景：用户希望朗读在标点处有自然停顿。标准做法是 SSML `<break>`，但——docs 原文：

> Edge 的 readaloud 端点**不支持** SSML `<break>`（带上后服务端直接断连、无音频返回），改走元数据方案：

解决方案（三层设计，docs/语音朗读.md 完整记载）：

1. **定位**：主进程收集 `audio.metadata` 中的 **WordBoundary** 事件，`@shared/voiceReadPunctuationPauses` 按词序把全角标点段映射为音频内待替换区间 `[fromMs, toMs]`（"标点前语音结束 → 标点后语音开始，含标点词自身音频"）；词与标点粘在同一 WordBoundary 时按文本比例插值；段尾标点从末词末尾延伸到音频总长；连续标点合并为一段（句末优先）；`。」`等右引号并入同段；**ASCII 标点不参与，避免数字 12.5、URL、英文缩写误伤**。
2. **传输**：区间随 mp3 一并返回，经 IPC/合成缓存原样携带；"**区间只依赖音频内容，与停顿时长解耦**，调整滑块不失效已缓存的音频"。
3. **播放**：`decodeAudioData` 后把区间整体**替换为干净静音**（"边缘 2ms 淡入淡出；重叠/相邻区间合并，取最宽区间+最长停顿"）；时长随语速同比缩放（"2x 时停顿减半"）。

CHANGELOG 补充的产品细节：句中停顿（，；：、0～600ms）与句末停顿（。！？… 0～1200ms）两个滑块，0 为默认行为；"仅 Edge TTS 引擎显示与生效（**其他引擎的音频流没有词级时间戳**）"。

git log 显示该功能开发节奏：09-07 "Edge TTS 朗读标点停顿（句末/句中时长可调，基于 WordBoundary 插静音）" → 09-08 "Edge TTS 朗读时支持按标点插入停顿 #90" 合入。

**现状**：7 引擎（edge/system/winSapi/dashscope/minimax/mimo/volcengine）+ 统一 Provider registry（synthesize/listVoices/healthCheck）+ 12 套朗读方案 + 密钥分槽入保险库，成为桌面端开源项目里覆盖最全的 TTS 矩阵之一。

### 2.7 AI 阅读助手 / RAG / 本地向量库

**为什么做它**：README 用一段通俗解释回答了"为什么需要向量模型"：

> 对话模型擅长「思考」和「说」，却不擅长「找」，我们也不可能每提一个问题都把整本小说的内容一起发给 AI 服务器，成本太高。（比如你问 xxx在第几章出场？……）而向量模型就是来做这个事情的……这个过程是在本地执行的，不需要消耗 Token。

**演进路径**：

- 2.4：思维导图（markmap，导出 SVG）、词云图（d3-cloud，导出 PNG）；角色卡文生图云端接口。
- 2.5：**AI 智能排版**——"清理 HTML 残留/修正硬换行/修正标点/统一对话符号/修正乱码/还原 \* 屏蔽/移除盗版水印/移除广告引流/压缩空行/行首缩进"九项，Monaco Diff 预览逐一确认。3.3 修复 #44："明确禁止结构助词「的/地/得」的语法互替，减轻 Diff 噪声"（docs 补充：写回前还会 `revertDeDiDeParticleSubstitutions` 硬性还原）。
- 2.6：附加系统提示词（"分析敏感题材小说时，可一定程度上减少拒答"——很现实的需求）；工具调用轮数；角色卡别名（"检索时会自动检索角色别名"）。
- 3.0 修复 #21：向量模型设为内置但未下载时关不掉 AI 助手——暴露了"内置模型需先下载"的状态机漏洞。
- 3.5 修复 #57：思维导图"现在只渲染一次"。

**ragContext 的策略演进（2.2）**——CHANGELOG 原文：

> AI 阅读助手 ragContext：优先从阅读器取章节原文而不是通过向量索引拼接 chunk；≤1 万字返回完整正文；超过 1 万字时按每 1 万字一段压缩为约 1 万字全章提要；压缩过程中显示分段进度；**向量索引仍用于语义检索**

**技术栈沉淀**（docs/AI功能.md）：
- 本地向量库：**better-sqlite3 + sqlite-vec**，向量/会话/消息同库（vector.sqlite），词云分词缓存独立（segment.sqlite）。

### 2.8 书源找书：用 TypeScript 复刻 Legado 的 Java 规则引擎

**为什么做它**：3.0 的版本定位（README 标题即"彩读｜ColorTxt 3.0 **书源 × AI+**"）。Legado（阅读）是安卓开源阅读器的事实标准，其书源生态（数万社区书源 JSON）是一笔现成财富；桌面端长期没有兼容方案。作者选择**不造新格式，直接兼容 Legado 书源**。

**初版声明（v3.0 CHANGELOG 原文，坦诚到罕见）**：

> `阅读` 书源用到了一些 `Java` 接口，彩读移植了一套 `JavaScript` 实现，**做不到 100% 复刻**……大概率有错漏，**只能通过迭代不断纠错兼容，目前算是测试版**，如发现问题，请提交 issue
>
> 「彩读」**不提供、不内置、不分发任何书源**，鼓励大家通过正规渠道支持作者与正版

**工程规模**（docs/书源找书.md，719+ 行开发文档）：
- 主进程 `bookSource/engine/` 完整复刻 AnalyzeRule/AnalyzeUrl/AnalyzeByJSoup/AnalyzeByJSonPath/AnalyzeByRegex 五大解析器 + jsExtensions（java.* 全套 API 桩）。
- **JS 引擎差异是最大障碍**：Legado 用 Rhino（同步、JVM），彩读用 Node AsyncFunction。文档记录了大量 V8/Rhino 兼容修补：`ensureLegadoScriptReturn` 给末尾表达式补 return（"对齐 Rhino completion"）、`arr.forEach(async…)` 改写为串行（"对齐 Rhino 同步阻塞"）、`function f(key){ let key = … }` 形参与 let 同名（Rhino 允许、V8 SyntaxError，预处理改名）、Mozilla `let (x = expr) body` 表达式改写、`\\ ({n,m}` 正则字面量修复（"部分正文剥标签规则在 Rhino 可跑"）、零宽字符剥离（"否则 source.getSource​() 在 V8 抛 missing ) after argument list"）。
- **Java 桩**：`JavaImporter` + DES（DESKeySpec/SecretKeyFactory/Cipher.ENCRYPT_MODE + android.util.Base64，"部分书源 encryptByDES"）、AES（"部分 API 书源 AES 正文"）、`java.util.Base64` 与 android 桩并存、Jsoup.connect(url).get() 异步化、洛雅橙分叉桩（readBookConfig，"官方 Legado 无；仅满足 typeof 存在性检测"）。
- **HTML 解析器差异**：Jsoup vs Cheerio 的行为对齐——`Element.select` 含根节点自身匹配、`[attr~=val]` 语义是"包含"（改写为 `*=`）、无引号属性值自动加引号、孤立 `<tr>/<td>` 须包 `<table>`（"否则搜索 td.N@text 会全空"）、`JSON.stringify(Element)` 对齐 Rhino 输出 outerHtml、结构破损页面先经 cheerio/parse5 纠错再给 xmldom（否则 XPath 静默取空）。
- **超时双轨**：同步 CPU 超时 30s（vm timeout 防死循环卡主进程）+ 异步墙钟 180s（"覆盖 bookList 内几十次串行 java.ajax 补拉详情的场景"）；"Legado/Rhino 无整段 JS 超时，只有单请求超时（我们单请求 20s）"。
- **网络层**：普通请求走 Chromium `session.fetch`（**浏览器 TLS 指纹**，对抗 Cloudflare 类检测）；仅显式 webView:true 才开隐藏窗；Cookie 以 eTLD+1 归档（"登录常在 accounts.example.com 写 Domain=.example.com 会话 Cookie、业务请求在 www.example.com，按主机名归档会取不到登录态"）；`ses.fetch` 须 `credentials:'omit'`（"实测 Electron 35 分区 Cookie 会整体替换显式 Cookie 头，游客 Cookie 会把登录请求降级成游客"）。
- 3.3 修复书源导入："之前 Node/undici 的 TLS 会被部分站点（或前面的 Tengine）重置"——正是改用 session.fetch 的动机。

**后续迭代**：3.1/3.3/3.5 连续三个版本出现"完善书源解析逻辑"；3.8（#84）书源校验可指定并发数（默认 4，范围 1–32）——校验大量书源时的实际需求。

**沉淀**：这是项目里最大的单一子系统（独立找书窗口：书架/找书/发现 + WebDAV 同步书架/书源 + 章节缓存/离线缓存 + 封面代理与 HEIC 转码）。README 链接显示项目曾被"科技爱好者周刊"（ruanyf/weekly issue #10004）和 LINUX DO 收录——3.0 的书源能力是出圈主因。

### 2.9 摸鱼模式：一个功能的 bug 修复马拉松

**为什么做它**：v3.8（#50）。README 一贯的幽默笔法："打开一个无边框、无任务栏、透明背景、始终置顶的阅读窗口，**不知道有什么用**"（与更早的"摸鱼快捷键 Ctrl+` 快速隐藏阅读器，不知道有什么用"一脉相承）。

**初版（v3.8.0，2026-09-02）**：无边框透明置顶窗口；全局快捷键 Ctrl+↑/↓ 翻页、Ctrl+←/→ 切章；Ctrl+滚轮改字号、Shift+滚轮改字体不透明度、Alt+滚轮改背景不透明度；右键菜单开关定时滚动/独立设置窗/退出。

**随后 11 天的修复连环（3.8.1–3.8.11）**——这是全项目最密集的一次功能救火：

| 版本 | 日期 | 修复 |
| --- | --- | --- |
| 3.8.5 | 09-04 | 摸鱼模式支持定时滚动 |
| 3.8.9 | 09-08 | 「摸鱼模式」优化：进入时半透明绿色左右点按提示层（「上一页」/「下一页」）；**Windows 下可缩到单行高度（系统最小窗高用 `setShape` 绕过）**；出右键菜单时点窗口只收菜单不翻页 |
| 3.8.10 | 09-08 | **#91：点任务栏时，系统会强行把任务栏抬到前面，导致摸鱼窗口被压到下面**，"现在会在指针进入任务栏区域时立刻重申置顶，并周期兜底以覆盖关窗等层级重排" |
| 3.8.11 | 09-09 | **#89：摸鱼窗口拖动移动时钉死逻辑宽高，避免在某些情况下窗体被越拖越大**；#89 极简/全屏浮动侧栏里分类管理打不开 |

技术点拆解：
- **系统最小窗高限制**：Windows 规定窗口最小高度，单行摸鱼窗低于该值做不到——用 Electron `setShape`（窗口形状裁剪）绕过，逻辑高度保持、视觉高度裁掉。
- **任务栏 Z 序大战**（#91）：Windows 点击任务栏时系统会强制抬升任务栏层级，把 alwaysOnTop 的摸鱼窗压下去。解法是"指针进入任务栏区域时立刻重申置顶，并**周期兜底**以覆盖关窗等层级重排"——事件驱动 + 定时兜底双保险。
- **拖动窗口越拖越大**（#89）：无边框透明窗的自绘拖动逻辑在高 DPI/缩放场景下把物理像素与逻辑像素混算，每拖一次涨一点。解法是"钉死逻辑宽高"。
- **右键菜单与翻页冲突**：出右键菜单时点窗口本意是收菜单，却被当成翻页点击——事件语义分流。

**现状**：摸鱼模式成为 3.8.x 的主战场，也从侧面暴露了"无边框透明置顶窗"在三大平台上的系统级坑位清单。

### 2.10 书包打包（.ctz/.ctzx）与 WebDAV 同步

**为什么做它**：跨设备/分享需求。阅读进度、书签、高亮词、笔记、角色卡、立绘散落在 userData 各处，用户无法整体迁移。

**v3.2 方案**：
- 书包 = `txt/md/插图目录 + 书签/高亮词/笔记/角色卡 + 阅读进度` 的压缩包；扩展名 **.ctz**（普通 zip）/ **.ctzx**（加密包，**AES-256-GCM + PBKDF2**，即 CTZE 整包加密）。
- 安装时注册 .ctz/.ctzx 的打开方式（可双击打开）；".txt/.md 仅加入「打开方式」，**不抢系统默认**"——作者对系统文件关联的克制态度。
- 打开/导入均支持，按文件名匹配当前打开/最近打开/文件列表做更新或解压到「书包解压目录」；「书包默认密码」设置项。
- **WebDAV 同步**（#5）：主窗配置/书包 + 找书窗书架/书源/设置三线同步；冲突策略"**一律覆盖（不比较时间）**"+ 增量（书包按内容 hash/mtime、背景图按文件名+大小、书源合并不删本地多出的源）。

**沉淀**：书包目录结构（characters/portraits、content/、bookmarks.json 等）成为事实上的"彩读存档格式"；3.8 的配色导出（"含自定义背景图时也会一起打包，方便分享"）复用了同一思路。

### 2.11 界面形态演进：全屏 → 极简 → 阅读尺 → 摸鱼（注意力经济四部曲）

- **全屏阅读**（1.x 早期）："禅模式，沉浸式阅读体验，阅读区域宽度可自由调整"；1.4 平滑滚动开关（"关闭后……以减缓长时间阅读的视觉疲劳"）。
- **极简视图**（3.8，#58）：顶栏/侧栏/底栏默认隐藏，阅读区撑满窗口，鼠标移到窗口边缘唤起面板，F10。与全屏差异：不进系统全屏、不套百分比居中留白。
- **阅读尺**（3.8，#83）：**明确面向 ADHD 人群**——"适合注意力不容易集中的人（ADHD），聚焦阅读行，淡化其他行"；可调聚焦行数、非聚焦行不透明度；开启后翻页变为"按聚焦行数移动阅读尺"、跳转"将阅读尺移到视口中间"。
- **摸鱼模式**（3.8，#50）：见 2.9。
- **番茄时钟**（3.1）："保护眼睛，健康阅读，从你我做起！"；阅读倒计时结束"整个界面会呈现毛玻璃效果"；每 4 轮进入长休息。
- **点击模式**（3.7，#4）：正文不可选，左键下一屏、右键上一屏，按住可拖动——为触屏/翻页器式阅读设计。

**背后的一套统一交互模型**（docs/基础功能.md 详细记载）：边缘感应唤起、mouseleave 收起、蒙版弹层互斥、Esc 按层关闭（输入框失焦 → 蒙版弹层 → 弹出菜单 → 查找栏 → 浮动面板 → 退出全屏，全屏需连按两次 Esc）、IME 候选框防误收（"输入法候选框出现在指针下方不收起面板"）。3.8 的修复列表里有 10+ 条极简/全屏交互修补，全部源于这套模型在真实使用中的边角暴露。

### v3.4（Monaco 补丁里程碑，2026-08-05）

> **重要体验优化版本，建议更新**
> - 「**启用中文换行优化**」（默认开启）：给 Monaco 打补丁，在**简单换行策略**下将中文标点按全角估算、用汉字校准全角字宽，减轻行尾缺字与溢出；不作用于**高级换行策略**
