### 1.2 加密方案对照

| 维度 | TraeWork | Trae CN | TeleAgent | WorkBuddy | Qoder |
|------|----------|---------|-----------|-----------|-------|
| token 格式 | Base64 加密 | 同 TraeWork | Base64 → v10 OSCrypt | **明文 JSON** | v10 OSCrypt（auth.v1.dat） |
| 加密算法 | AES-128-CBC | 同 TraeWork | AES-256-GCM | 无 | AES-256-GCM |
| 密钥派生 | SHA-512 + XOR 内置常量 | 同 TraeWork | DPAPI（Windows 用户级） | 无 | DPAPI（Windows 用户级） |
| 解密难度 | 中 | 中 | 中 | **零** | 中 |
| 解密依赖 | 纯 JS | 纯 JS | DPAPI + Node crypto | 无 | DPAPI + Node crypto |
| token 自刷新 | 否 | 否 | 否 | 否 | **是**（脚本临期自动刷新并写回） |
| token 有效期 | 跟随客户端 | 跟随客户端 | 跟随客户端 | 跟随客户端 | token 30 天 / refreshToken 1 年 |

### 1.3 API 对照

| 维度 | TraeWork | Trae CN | TeleAgent | WorkBuddy | Qoder |
|------|----------|---------|-----------|-----------|-------|
| API 网关 | api.trae.cn | api.trae.cn | agent.teleai.com.cn | copilot.tencent.com | openapi.qoder.com.cn |
| 签到方法 | POST | POST | GET | POST | **先 GET 列表再 POST claim** |
| 鉴权头 | Cloud-IDE-JWT | 同 TraeWork | X-Token | Bearer JWT | Bearer + 9 个 Cosy-* |
| 风控参数 | req_source=2 + 数字设备ID | 同 TraeWork | 无签名 | Turing Token（可选） | **设备指纹桥接程序实时生成** |
| 客户端依赖 | 不需要 | 不需要 | 不需要 | 不需要 | 不需要（但需已登录过一次 + runtime-info.exe 存在） |

### 1.4 TraeWork 与 Trae CN 的特殊关系

两者是**独立产品**（不同安装目录、不同数据目录），但签到 API **完全共用**：
- 同一域名 `api.trae.cn`、同一接口路径、同一加密方案
- 唯一区别：数据目录（`TRAE SOLO CN` vs `Trae CN`）

### 1.5 Qoder 的三点独特性

1. **活动制而非固定签到接口**：campaignId 每天变化（campaignKey 形如 `act-20260920-044`），必须先 GET `/sash/api/v1/me/campaigns` 查列表，再 POST `/sash/api/v1/me/campaigns/<campaignId>/claim` 领取
2. **风控头依赖客户端自带的 native 桥接程序**：`resources\umid\runtime-info.exe` 每次签到时 spawn 生成 machineToken/Code/Type（与账号绑定），不是可静态伪造的 HTTP 头
3. **时区敏感**：每日 10:00（UTC+8）刷新活动，任务时间设计必须围绕这个点

## 二、各平台逆向要点

### 2.1 TraeWork（TRAE SOLO CN）

**数据目录**：`%APPDATA%\TRAE SOLO CN\`

**token 存储**：
- 文件：`User\globalStorage\storage.json`
- 键名：`iCubeAuthInfo://icube.cloudide`
- 格式：Base64 加密字符串

**解密链路**：
```
Base64 解码 → 提取 key(32字节) → SHA-512(key) → XOR(ure,dre)
→ 拼接 [SHA-512(key) + XOR] → SHA-512 → 取前16字节=AES密钥, 16-32=IV
→ AES-128-CBC 解密 → 去掉前64字节 → 明文 JSON {token, userRegion}
```

**接口**：
- POST `https://api.trae.cn/trae/api/v2/ug/checkin_credits/status` body=`{"req_source":2}`
- POST `https://api.trae.cn/trae/api/v2/ug/checkin_credits/claim` body=`{"req_source":2}`

**鉴权头**：`Authorization: Cloud-IDE-JWT <token>` + `x-device-id` + `x-device-type` + `x-os-version` + `x-app-version`

**风控踩坑**：
- `req_source` 必须为 2（桌面端标识），缺失报 code 9004
- `x-device-id` 必须为纯数字格式（如 `1963102595468793`），用 UUID 格式报 code 9074

> 详细文档：`TraeWork积分API直连-逆向研究全记录.md`

### 2.2 Trae CN

**数据目录**：`%APPDATA%\Trae CN\`

**与 TraeWork 的差异**：仅数据目录不同，其余完全一致。解密代码直接复用 TraeWork 的 `decryptTrae()` 函数。

**额外踩坑**：

- 需要多域名测试才能发现正确域名

### 2.3 TeleAgent

**数据目录**：`%USERPROFILE%\.local\share\TeleAgent\`

**token 存储**：
- 文件：`users\<uid>\app-auth\token.json` → `encryptedToken`（Base64）
- 主密钥：`Local State` → `os_crypt.encrypted_key`（DPAPI 加密）
- 设备 ID：`app-auth\device-meta.json` → `deviceId`

**解密链路**：
```
1. Local State → os_crypt.encrypted_key → Base64 解码 → 去掉 "DPAPI" 前缀
2. DPAPI Unprotect (CurrentUser) → 32 字节 AES 主密钥
3. encryptedToken → Base64 解码 → "v10" + nonce(12) + ciphertext + tag(16)
4. AES-256-GCM 解密 → JWT token (439字符)
```

**接口**：
- GET `https://agent.teleai.com.cn/superCowork/sapi/user/portal/companyStore/v2/checkDayTask`
- GET `https://agent.teleai.com.cn/superCowork/sapi/user/portal/companyStore/checkTask?type=daily_login`
- GET `https://agent.teleai.com.cn/superCowork/sapi/user/portal/companyStore/userCenter`

**鉴权头**：`X-Token` + `X-Timestamp` + `X-Nonce` + `X-SuperAgent-Device-Id` + `X-OS-Type`

**关键发现**：无请求签名，头齐全即过。

> 详细文档：`TeleAgent积分API直连-逆向研究全记录.md`

### 2.4 WorkBuddy（CodeBuddy）

**数据目录**：
- 主数据：`%USERPROFILE%\.workbuddy\`
- **auth 文件不在 `.workbuddy` 下**，在 `%LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\`

**token 存储**：
- 文件：`workbuddy-desktop.info`
- 格式：**明文 JSON**（无需解密）
- 字段：`auth.accessToken`（JWT）、`account.uid`、`auth.domain`

**发现 token 的曲折过程**：
```
.restore() → getAuthSavePath() → sharedDataPath → basePath → EXTENSION_DATA_DIR_NAME
→ "CodeBuddyExtension" → %LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\
```

**接口**：
- POST `https://copilot.tencent.com/billing/meter/checkin-activity-status` body=`{}`
- POST `https://copilot.tencent.com/billing/meter/daily-checkin` body=`{}`

**鉴权头**：`Authorization: Bearer <token>` + `X-User-Id`

**风控发现**：Turing Token（腾讯防刷）是可选增强，`postCheckin` 代码逻辑为"无头也照发"，实测确认 200 通过。

> 详细文档：`WorkBuddy积分API直连-逆向研究全记录.md`

### 2.5 Qoder（Qoder CN）★ 2026-09-20 新增

**数据目录**：`%APPDATA%\com.qodercn.app.stable\`（国际版 `com.qoder.app.stable` 兜底）

**token 存储**：
- 文件：`auth.v1.dat`（v10 加密，含 token/refreshToken/user）
- 主密钥：`Local State` → `os_crypt.encrypted_key`（DPAPI，与 TeleAgent 完全同体系）
- 机器 ID：`auth.machine-id`（明文 UUID）

**解密链路**（同 TeleAgent）：
```
1. Local State → os_crypt.encrypted_key → DPAPI → 32 字节 AES 主密钥
2. auth.v1.dat → "v10" + nonce(12) + ciphertext + tag(16)
3. AES-256-GCM 解密 → JSON {token(dt-…), refreshToken(drt-…), expiresAt, user}
```

**接口**（网关 `https://openapi.qoder.com.cn`）：
- GET `/sash/api/v1/me/campaigns` — 查活动（响应含 campaigns[].claimStatus/benefit/campaignId）
- POST `/sash/api/v1/me/campaigns/<campaignId>/claim` — 领取（**路径在活动页 CDN JS 里逆向得到**，asar 内无此接口）
- POST `/api/v1/deviceToken/refresh` — token 刷新（body `{"refresh_token":…}`，响应 token 字段名是 `device_token`|`token`）

**鉴权头**（9 个）：
```
Authorization: Bearer dt-…
Cosy-ClientType: 10        Cosy-Version: 0.3.4
Cosy-MachineOS: x86_64_windows    Cosy-MachineHostname: <主机名>
Cosy-MachineId: <auth.machine-id>
Cosy-MachineToken / Cosy-MachineCode / Cosy-MachineType  ← runtime-info.exe 实时生成
User-Agent: Qoder
```

**风控机制**：
- `resources\umid\runtime-info.exe <env> --account-stdin`，stdin 传 `{"account": userId}`，stdout 首行 JSON 出 machineToken/Type/Code
- 国内版 env=0，国际版 env=3；风控身份按账号绑定，服务端校验
- 活动页虽加载阿里云风控 JS（sufei_data/AWSC），但桌面端领取走同源 XHR + 上述头注入，无需破解页面风控

**活动规则**（实测）：每日 10:00（UTC+8）生成当天新活动（startAt 即当天 10:00），actionType=CLAIM_BENEFIT，claimStatus=CLAIMABLE 时可领，领取后 100 Credits 30 天有效，当天不领作废。

**签到判定逻辑**（脚本核心）：
- 有 CLAIMABLE 的 CLAIM_BENEFIT 活动 → 领取 → 复查
- 全 CLAIMED 且存在今日活动（startAt ≥ 今天10:00 UTC+8）→ 「今日已签到」
- 全是昨日活动 → 「活动未刷新，跳过」（凌晨统一签到走此分支）

> 详细文档：`Qoder积分API直连-逆向研究全记录.md`

## 五、跨项目踩坑总集

### 5.1 通用坑（多项目重复遇到）

| # | 问题 | 涉及项目 | 解决 |
|---|------|---------|------|
| 1 | rg 搜索 asar 报 "binary file matches" | TeleAgent / WorkBuddy / Qoder | 加 `-a` 强制文本模式，或自写 asar 解析器 |
| 2 | 搜 `points/checkin` 上万条命中 | TeleAgent / WorkBuddy | 搜 UI 独有中文字符串当锚点 |
| 3 | PS 5.1 `ConvertFrom-Json` 解析大 JSON 失败 | TeleAgent / Qoder | 用 Node 解析 |
| 4 | asar 被进程占用无法 `File.Open` | WorkBuddy | 用 Node `fs.openSync('r')` 或 rg |
| 5 | PS 修改 JS 文件后 Node 报语法错误 | TeleAgent | PS 5 的 `Set-Content` 默认 ANSI，用 Write 工具 |
| 6 | 日志中文乱码 | 全部 | `Get-Content -Encoding UTF8` 读取 |
| 7 | 定时任务注册成功但不执行 | 全部 | `Test-Path "C:\Windows\System32\Tasks\任务名"` 验证落盘 |
| 8 | cmd 批处理中文注释在 GBK 代码页下变乱码命令 | Qoder（新踩） | **cmd 文件一律英文注释**（四平台 cmd 未踩是因为本来就英文） |
| 9 | 从自动化会话 `Start-ScheduledTask` 触发，进程被会话回收 ^C 杀掉（0xC000013A） | Qoder（Git 同步任务也曾偶发） | 定时自然触发不受影响；验证用一次性触发器或前台直跑 |
| 10 | Node 24 Windows 下 `process.exit()` 偶发 uv 断言噪音 | Qoder（新踩） | 改用 `process.exitCode` 自然退出 |

### 5.2 各平台特有坑

| 平台 | 坑 | 解决 |
|------|---|------|
| TraeWork | `req_source` 缺失报 9004 | 请求体固定 `{"req_source": 2}` |
| TraeWork | 设备 ID 用 UUID 报 9074 | 用 `local_env.json` 里的纯数字 `device_id` |
| TraeWork | 解密后 JSON 前 64 字节是垃圾 | `dec.slice(64)` 去掉（rh=64） |
| Trae CN | `product.json` 配的 `api.trae.com.cn` 返回 404 | 实际域名是 `api.trae.cn`（与 TraeWork 一致） |
| TeleAgent | DPAPI 直接解 token 失败 | token 是 OSCrypt v10 格式，先解主密钥再 AES-GCM |
| TeleAgent | 密文头 `76 31 30` 不认识 | = ASCII "v10"，Chromium OSCrypt 版本前缀 |
| TeleAgent | asar JSON 起始偏移与网传不符 | hexdump 前 64 字节确认：JSON 从偏移 16 开始 |
| WorkBuddy | auth 文件不在 `.workbuddy` 下 | 逆向 `getAuthSavePath` 链路找到 `CodeBuddyExtension` |
| WorkBuddy | `EXTENSION_DATA_DIR_NAME` 不是 "WorkBuddy" | 底层是 CodeBuddy 体系，值为 "CodeBuddyExtension" |
| **Qoder** | asar 头不是标准 8 字节格式（jsonLen 在 @12、JSON 在 @16、数据区 = 8+@4） | hexdump 实测定制解析器；TeleAgent 用的偏移 16 逻辑在此同样成立但长度字段位置不同 |
| **Qoder** | asar 里搜不到领取接口 | 领取逻辑在活动 Web 页（g.alicdn.com CDN JS）；顺日志里 campaignUrl 下载页面 JS 才找到 claim 路径 |
| **Qoder** | `/turns/claim` 是远程任务认领（290+ 处），不是积分领取 | 认准 `/me/campaigns/<id>/claim` + POST |
| **Qoder** | `credits-summary`/`seat-activity` 是账户指标，不是签到状态 | 签到状态以 campaigns 的 claimStatus 为准 |
| **Qoder** | 刷新接口响应 token 字段名不叫 token | 取 `device_token`\|`token` 多字段兜底 |

## 六、统一脚本架构（checkin_all.js + qoder_checkin.js）

签到体系由两个独立入口组成：统一签到（4 平台）+ Qoder 专项任务，各平台独立执行，互不阻塞。

```
run_checkin_all.cmd → checkin_all.js（每天 01:00±30min）
    │
    ├── 1. TraeWork 签到（内联）
    │   ├── 读取 %APPDATA%\TRAE SOLO CN\...\storage.json
    │   ├── AES-128-CBC 解密 token
    │   ├── POST status → POST claim → 刷新积分
    │   └── 随机延迟 30~300 秒
    │
    ├── 2. TraeCN 签到（内联，复用解密函数）
    │   └── 同上（数据目录不同）
    │
    ├── 3. TeleAgent 签到（内联）
    │   ├── DPAPI 解主密钥 → AES-256-GCM 解 token
    │   ├── GET status → GET claim → GET userCenter
    │   └── 随机延迟 30~300 秒
    │
    └── 4. WorkBuddy 签到（内联）

        ├── POST status → POST claim → 复查
        └── 随机延迟 30~300 秒
```

设计要点：
- **职责单一**：统一签到管 4 平台；Qoder 活动 10:00 刷新、凌晨领不到，由独立任务专责（2026-09-21 调整：移除了凌晨必然空跑的探测分支，消除冗余）
- **模块化**：Qoder 逻辑独立成 `qoder_checkin.js`（模块化导出 + `require.main` 守卫），需要时可被其他脚本引用，当前由独立任务唯一使用
- **随机延迟**：每个平台签到前等待 30~300 秒 + 触发器 PT30M，两层打乱固定模式
- **独立执行**：单平台失败不影响其他平台
- **统一日志**：带时间戳的中文输出，退出码 0=全部成功、1=至少一个失败；日志统一 UTF-8（cmd 入口加 `chcp 65001`）

## 七、逆向方法论总结

### 通用七步流程

```
界面字符串/客户端日志 → 代码定位（asar 或明文） → API 路径 → 鉴权头 → token 来源 → 解密链路 → 验证接口
```

> Qoder 的经验补充：**客户端日志有时比代码更快**（main.log 直接给出接口、请求头、响应结构）；**接口不在客户端包里时，去看它的 Web 页面 JS**（活动页 CDN bundle）。

### 判断加密类型

| 密文特征 | 加密类型 | 解密方法 | 案例 |
|---------|---------|---------|------|
| 文件是明文 JSON | 无加密 | 直接 `JSON.parse` | WorkBuddy |
| Base64 开头 `v10` | Chromium OSCrypt | DPAPI 解主密钥 → AES-256-GCM | TeleAgent、Qoder |
| Base64 + 内置常量表 | 自研混淆 | 逆向解密函数 | TraeWork、TraeCN |

### 判断签到形态

| 形态 | 特征 | 应对 |
|------|------|------|
| 固定接口型 | status + claim 两个固定路径 | 直接调用（Trae 系/TeleAgent/WorkBuddy） |
| **活动制** | 先查列表拿动态 ID 再领取 | GET campaigns → 匹配 claimStatus → POST claim（Qoder） |
| 时间窗限制 | 活动按天刷新且刷新点非 0 点 | 任务时间设在刷新点之后（Qoder 10:00 → 10:30） |
