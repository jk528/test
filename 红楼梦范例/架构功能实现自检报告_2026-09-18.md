### 1.1 双坐标系统一性

| 坐标系 | 用途 | 转换规则 | 状态 |
|--------|------|----------|------|
| 0 基物理行 | 业务层（章节、书签、情感、实体） | 行号 +1 → Monaco 1 基 | ✅ 统一 |
| Monaco 1 基行列 | 渲染层（decoration、滚动、定位） | 行号 -1 → 业务 0 基 | ✅ 统一 |
| 视觉行（软换行） | 阅读尺聚焦带 | `getTopForPosition` + 二分查找 | ✅ 独立封装 |

**结论**：物理行作为唯一锚点贯穿全链路，视觉行计算完全封装在 `visualRowStart/stepVisualLine/collectFocusBand` 内部，不泄漏到业务层。架构清晰。

### 1.2 装饰渲染分层

```
renderDecorations()
├─ decoColl (行内装饰，视口化)
│  ├─ 章节标题（小体量，全量）
│  ├─ 书签（小体量，全量）
│  ├─ 情感行底色 + 字级高亮（大体量，视口化）
│  ├─ 人物高亮 inline（大体量，视口化）
│  ├─ 阅读尺聚焦带（小体量，全量但视觉行级）
│  ├─ 查找匹配 inline（大体量，视口化）
│  └─ 段间距 + 行首缩进（大体量，视口化）
└─ overviewColl (右侧概览栏，全量)
   ├─ 人物高亮 overviewRuler（全量）
   └─ 查找匹配 overviewRuler（全量）
```

**结论**：双集合分离清晰，行内装饰追求性能（视口化），概览栏追求完整性（全量）。P0-1 修复后不再冲突。

### 1.3 分层架构

```
App.vue (状态管理 + 侧边栏 + 控制栏)
  ↓ props / emit
Reader.vue (渲染层 + 交互层)
  ↓ 调用
lib/monaco.ts (主题 + 初始化)
lib/chapters.ts (解析 + 二分查找)
lib/annotations.ts (书签)
lib/sidecar.ts (RAG 数据类型)
  ↓ IPC
sidecar/*.py (后端：存储 + 检索 + 分析)
```

**结论**：单向数据流，Vue 单向 props 向下，emit 向上。Monaco 实例封装在 Reader 内部，外部通过 `defineExpose` 的方法操作。符合组件化原则。

### 2.2 P0-1：overviewRuler 被视口化 ⚠️ → ✅ 已修复

**问题**：OPT-1 视口化渲染把人物高亮和查找结果的 `overviewRuler` 也做了视口过滤，导致右侧概览栏只显示视口内的标记，滚动时标记会"消失又出现"。

**根因**：装饰集合单一时，inline 和 overviewRuler 共享同一视口过滤逻辑。

**修复**：拆分为 `decoColl`（行内，视口化）+ `overviewColl`（概览栏，全量）两个独立集合。
- 人物高亮：inline 视口化 + overviewRuler 全量
- 查找匹配：inline 视口化 + overviewRuler 全量

**验证**：TypeScript 类型检查通过。

### 2.3 P0-2：StickyScroll Provider 全局注册 ⚠️ → ✅ 已优化

**问题**：`registerDocumentSymbolProvider('plaintext', ...)` 是全局注册，若 Reader 多次销毁重建或章节变化时重复注册，会导致 provider 叠加。

**根因**：Monaco 的 `registerDocumentSymbolProvider` 按 language id 全局注册，不区分编辑器实例。

**修复**：
- 注册前先 `stickyProviderDisposable?.dispose()` 销毁旧 provider
- `onBeforeUnmount` 中确保销毁
- 章节变化 watcher 中先销毁再注册
- 章节变化后通过 `updateOptions({ stickyScroll: { enabled: false } })` → rAF → `enabled: true` 强制 Monaco 重新计算粘性条

**局限**：若存在多个 Reader 实例仍会冲突（当前单 reader 架构无影响）。

### 2.4 P1：查找跳转匹配项短暂不显示 ⚠️ → ✅ 已完善修复

**问题**：跳转到视口外的查找匹配项时，平滑滚动过程中匹配项的行内高亮短暂消失，直到滚动到位才重新出现。

**根因**：
1. 旧修复仅在 `revealMatch` 中临时扩展视口到目标行 ± 20 行
2. 但 `onDidScrollChange` 事件会在平滑滚动中持续触发，每次都把视口重置为 `可见范围 ± 80 行`
3. 目标行远离当前视口时，滚动中途视口不包含目标行，匹配项装饰被过滤掉

**修复**：引入 `forcedVpLine` 机制
- 跳转时设置 `forcedVpLine = targetLine`，强制视口包含目标行
- 滚动事件中：若 `forcedVpLine` 存在，视口范围扩展为 `max(可见范围, 目标行 ± 80)`
- 当目标行进入可见范围后，自动清除 `forcedVpLine`，恢复正常视口管理
- `revealMatch` 和 `revealLine` 均使用此机制

**效果**：平滑滚动全程，目标匹配项的行内高亮始终可见。

### 3.2 性能优化：行数组缓存

**问题**：`renderDecorations` 中段间距 + 行首缩进逻辑每次都执行 `props.text.split("\n")`，对于《红楼梦》约 7000 行文本，每次滚动触发的 renderDecorations 都要做一次完整字符串切割。

**优化**：
- 引入 `cachedLines` 和 `cachedTextKey` 缓存
- 缓存 key = `长度 + 前20字符 + 后20字符`，高效检测文本变化
- `props.text` 变化时（watch）主动失效缓存
- 首次访问时惰性计算，后续命中缓存

**收益**：滚动时 `renderDecorations` 调用从 O(n) 字符串切割降为 O(1) 缓存命中（段间距部分仍需遍历视口范围的行，但避免了全量 split）。

### 3.3 边界情况检查

| 边界场景 | 处理方式 | 状态 |
|----------|----------|------|
| 空文本 / 0 行 | `splitPhysicalLines` 返回 `[""]`，chapters 为空数组 | ✅ 安全 |
| 单行超长文本（软换行 N 行） | 阅读尺按视觉行移动，二分查找视觉行边界 | ✅ 正确 |
| 查找 0 结果 | `findMatches` 为空，`renderDecorations` 跳过查找块 | ✅ 安全 |
| 查找结果在首行/末行 | `revealLineNearTop` 受 `scrollBeyondLastLine` 限制 | ✅ 合理 |
| 章节列表为空 | StickyScroll provider 返回空数组，不显示粘性条 | ✅ 安全 |
| 书签在空行 | glyph margin 仍可点击，行底色作用于空行 | ✅ 正常 |
| 情感数据为空章 | `props.emotions` 为空，`showEmotions` 开关不生效 | ✅ 安全 |
| 阅读尺在文档首/末行 | `stepVisualLine` 越界时返回原位置，不崩溃 | ✅ 安全 |
| 视口范围 [0, Infinity] 初始态 | 首次滚动前全量渲染，rAF 后收窄到真实视口 | ⚠️ 初始帧全量渲染 |

### 3.4 剩余低优先级注意事项

1. **初始帧全量渲染**：`onMounted` → `renderDecorations()` 时视口为 `[0, Infinity]`，所有装饰全量渲染。双 rAF 后才收窄到真实视口。对于超长篇小说（10万+行 + 海量实体）可能导致首帧卡顿。当前《红楼梦》规模下可接受。

2. **StickyScroll 全局注册**：`registerDocumentSymbolProvider` 是 plaintext 全局的，多 Reader 实例会冲突。当前单 reader 架构无影响。若未来需支持多标签页，建议改用自定义 language id 或 per-model 方案。

3. **`chapterLinesSet` 每次重建**：`renderDecorations` 中段间距部分每次都 `new Set(props.chapters.map(...))`。章节数量少时（红楼梦 120 章）开销可忽略。
