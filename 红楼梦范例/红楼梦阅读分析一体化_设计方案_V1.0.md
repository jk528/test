## 0. 摘要：三个结论

**结论一：能并入的比想象的多 —— ColorTxt 前 4 类功能（阅读、标注、格式、检索）几乎是本方案的空白区，可以整块拿来。**

现有 V2.0 是一台**批处理分析机**：输入 120 个章节文件，输出报告、索引、图表。它没有"给人读"的那一层 —— 没有阅读器、没有目录跳转、没有书签高亮、没有边读边问。ColorTxt 恰好补齐这一层，且它的实现方式（Monaco + 物理行坐标系 + 着色规则）与本项目的分析产物**天然可对齐**。

**结论二：析域（V2.0 的 M1–M8）整体保留，但两处架构要改 —— 通信与存储。**

- **通信**：V2.0 用 FastAPI + localhost 端口。桌面应用不该开端口（防火墙弹窗、端口冲突、CORS、暴露面）。改为 **stdio JSON-RPC 的 Python sidecar**（ColorTxt 的 IPC 思路，主体不变）。
- **存储**：V2.0 以文件（`分析结果/*.md` + `*.json`）为唯一存储。交互式产品需要**单文件 SQLite**（书籍 + 标注 + 分析结果 + 向量索引），**同时保留 MD/JSON 导出** —— 报告仍是文件，只是从"主存"降为"导出格式"。这条既不丢现有资产，又让"边读边析"成为可能。

**结论三：架构判优 —— 析域抄 V2.0，读域抄 ColorTxt，但桌面壳要反着选。**

| 维度 | 谁更好 | 采谁 |
|---|---|---|
| 阅读体验（渲染、上色、标注、阅读辅助） | **ColorTxt** | 采 ColorTxt |
| 领域分析深度（分词、双引擎情感、事件/人物、质量门禁） | **V2.0** | 采 V2.0 |
| 功能广度与成熟度（词典、翻译、TTS、书源） | **ColorTxt** | 按需并入 |
| 数据分层（SQLite + JSON + localStorage） | **ColorTxt** | 采 ColorTxt（+ MD 导出） |
| 进程通信（IPC vs localhost HTTP） | **ColorTxt** | 采 ColorTxt |
| **桌面壳** | **两者取舍不同，本项目选 Tauri** | 见 §5.1 |
| 打包体积 | **V2.0**（Tauri 路线，55 MB vs 137 MB） | 采 V2.0 |

**一句话总账**：**读域抄 ColorTxt，析域留 V2.0，壳用 Tauri，两者用「统一锚点模型」缝合。**

## 一、ColorTxt 功能架构剖析

### 1.1 产品定位与六类功能

ColorTxt（彩读 3.0）是一款**本地 TXT/电子书阅读器**，核心差异点是**给内容上色**：用一套可自定义的高亮规则对文本着色，把"读小说"变成"看语法高亮"。它同时是 Electron 桌面应用，支持 macOS / Windows / Linux。

功能可分为六类：

| 类别 | 功能 |
|---|---|
| **① 阅读内核** | 本地 txt/md 阅读、epub/mobi/pdf/fb2/chm 转换后加载、自动编码识别（UTF-8/ANSI，jschardet + iconv-lite）、自动章节识别（内置规则 + 自定义 `#` ATX 匹配）、黏性章节标题、阅读进度恢复、最近打开 |
| **② 视觉与阅读辅助** | **个性内容上色**（自定义高亮规则）、自定义高亮词、多套配色方案、全屏禅模式、极简视图、**阅读尺**（ADHD 聚焦行）、摸鱼模式、番茄钟、主题（明/暗）、字体与排版（字距/行距/段距/边距）、定时滚动 |
| **③ 标注与编辑** | 书签（带备注）、**划线标注 + 笔记**、编辑模式、全局文本替换、简繁互转 + 字母/数字全半角、空行压缩、行首缩进 |
| **④ 检索与工具** | 侧栏全文搜索、Monaco 查找栏、**词典**（Wiktionary/Wikipedia 在线 + StarDict/MDict/DICT/Slob/BGL 本地词库）、**翻译**、**多角色语音朗读**（Edge TTS + AI 说话人识别）、多窗口 |
| **⑤ AI 增强** | **AI 阅读助手**（剧情分析、章节规则生成、思维导图、词云）、**角色卡生成**（AI 检索 + 文生图立绘）、**AI 智能排版**（硬换行/标点修正）、**RAG 全文检索** |
| **⑥ 生态与同步** | 书源找书（Legado 引擎）、**彩读书包**（`.ctz` / `.ctzx` 加密封包）、WebDAV 跨设备同步 |

### 1.2 进程与目录架构

**技术栈**：Electron + Vue 3 + TypeScript；构建 `electron-vite`，打包 `electron-builder`（dmg / nsis / portable / AppImage），CI 用 GitHub Actions 三端并行。

**四段式进程划分**（这是它最值得学的地方）：

| 进程 | 职责 | 关键约束 |
|---|---|---|
| `src/main/` | 窗口、协议、IPC 业务（`ipcHandlers.ts`）、编码探测、全局快捷键、自动更新；子域 `ai/`（RAG/文生图/语音说话人识别）、`voiceRead/`（TTS Provider 注册）、`dictionary/` | **所有重活与原生模块在这里**（OpenCC、SQLite、模型推理） |
| `src/preload/` | 仅 `index.ts`，通过 `contextBridge` 暴露 `window.colorTxt` | 受控 API 面，渲染进程拿不到 Node |
| `src/renderer/` | Vue 应用、Monaco 阅读器、侧栏、AI 面板 | 纯 Web，无 Node |
| `src/shared/` | 跨进程共享类型、IPC 载荷、默认配置（`@shared/...`） | 单一事实源 |

**渲染进程内部按功能域深拆**（这是它可维护的根因）：

```
renderer/src/
├── composables/    数十个细粒度组合式钩子（书签/搜索/标注/持久化/语音/AI桥接）——业务逻辑核心
├── constants/      UI 存储 key、配色/调色板、高亮色、分类、语音设置
├── monaco/         Monaco 深度扩展：黏性章节条、CJK 换行、行距、插图 ViewZone、自定义高亮 Monarch 规则
├── reader/         阅读显示管线：物理行↔展示行映射、章节索引/树、视口锚点、标注装饰、阅读尺算法
├── markdown/       章节检测、内链剥离、图片扫描、代码块上下文防护
├── ebook/          电子书 → Markdown（EPUB/MOBI/PDF/FB2/CHM 解析 + 目录注入）
├── ai/ aiAssistant/ aiSmartFormat/   向量索引构建、助手消息分段、排版差异预览
├── services/       对话框队列、Toast、文件列表合并、物理行流、快捷键注册表、文本转换编排
├── stores/         cacheStore(localStorage) / fileMetaStore(单文件meta) / recentHistoryStore(MRU)
└── utils/          颜色换算、路径解析、拖放、WebDAV 同步、AI 切块
```

> **状态管理刻意不用 Pinia/Vuex** —— 全部靠 Vue Composition API 的 `composables/` 拆解串联。对单窗口状态密集的编辑器类应用，这个选择降低了抽象层级。**本方案沿用**。

### 1.3 阅读管线：物理行 / 展示行双坐标系

这是 ColorTxt **最关键的架构决策**，也是它能同时做"上色 + 标注 + 编辑 + 定位"的原因。

```
流式读盘 useTxtStreamPipeline
   └─ 只追加【物理行】physicalLineContents（磁盘原文，不加工）
        │
        ├─ 只读：formatPhysicalLinesForReader → 生成【展示行】+ 双向映射表
        │         displayLineToPhysicalLine / chapterTitleDisplayLineByPhysical
        │         再依次套用：
        │           ① applyReplaceRulesToDisplayText（替换规则，分"正文作用域/标题作用域"）
        │           ② applyTextDisplayConverts（简繁转换 / 全半角）
        │           ③ setFullText 写入 Monaco
        │
        └─ 编辑：直接展示 physicalReaderPath 磁盘全文，Monaco 行 ≡ 物理行（1:1）
```

**两个坐标系各管一摊**：

| 坐标系 | 用途 | 谁挂在这上面 |
|---|---|---|
| **物理行** physical | 磁盘真实位置、编辑、持久化 | **书签、高亮、笔记、阅读进度、分析锚点** |
| **展示行** display | 屏幕显示、着色、搜索命中 | 高亮渲染、查找结果 |

**一切持久化数据锚定在物理行** —— 这样"显示层做多少次替换/转换"都不会让标注错位。搜索时：只读态在 `getDisplayLineContent` 匹配，编辑态在 `getPhysicalLineContent` 匹配，再用 `physicalSearchRangeToDisplayColumns` 把列号映射回展示列。

**本项目的分析产物（逐章、逐段、逐句）可以无痛挂到同一坐标系上** —— 这是两套架构能缝合的技术前提（见 §3.2）。

**章节识别**：
- `.md`：只认 ATX 标题（`#`…`######`，行首最多 3 空白），**跳过代码块内的 `#`**，扫描基于物理行；
- `.txt`：从展示正文按内置/自定义正则匹配；
- 电子书：把各格式目录注入为 `# 标题` + `<span id="toc_N"></span>`，保证侧栏章节与源书一致。
- 章节树由 `markdownChapter.ts` 构建；黏性标题条由 `chapterStickyScroll.ts` 的 `DocumentSymbolProvider` 提供多级大纲。

**着色**：Monaco 的 Monarch 语法规则被改造成"高亮规则引擎"（内容上色灵感来自 VS Code 插件 `vscode-txt-syntax`）—— 即把 Monaco 当**可编程着色画布**，而不是代码编辑器。

### 1.4 AI 子系统：对话 / RAG / 技能 / 角色卡

**（1）对话**
- 独立方案制 `chatProfiles`（最多 12 套），每套含完整 `AIChatEndpoint`（baseUrl、系统提示词、Token 单价）；
- 密钥加密存 `ai.chatProfileKeys`（`profileId → apiKey`），落盘 `config.json` **不含明文**；
- 渲染层发起 → 主进程代理（IPC）→ OpenAI 兼容 `POST {baseUrl}/chat/completions` → 流式增量与工具事件经 `ai/chat/agentChat.ts` 回推 `window.colorTxt.ai.onAgentEvent`；
- 支持深度思考（按 `baseUrl` 注入厂商思考参数，`reasoning_delta` 写入 `payload.reasoning`）；
- Token 统计双阶段：`token_usage_estimate`（预估）→ `token_usage_final`（实际）。

**（2）RAG 全文检索**（这是"分析"能力的关键基建）

| 环节 | 实现 |
|---|---|
| 分块 | 建索引时**按章节分块**（切块大小与 `ragTopK` 可配） |
| 嵌入 | 内置本地模型（`@huggingface/transformers` Worker 线程，`BGE Small ZH v1.5` ~47 MB / 512 维，或 `Multilingual E5 Small` ~118 MB / 384 维）**或**远程 API（OpenAI 兼容 `POST /embeddings`，`remoteEmbedBatchSize` 控批） |
| 索引 | 经 preload → 主进程写入 `vector.sqlite`（`better-sqlite3` + **`sqlite-vec`** 扩展） |
| 检索 | `ragSearch` 跨章向量搜索；整章原文用 `ragContext`：优先向阅读器索要切片（源 `reader`），拿不到则用分块拼接兜底（源 `vector`） |
| 长文档 | 原文字数 > 1 万，按每 1 万一段调模型压缩合并 |

> 它给出的 RAG 理由说得很清楚：对话模型擅长"想"和"说"、不擅长"找"；不可能每问一句就把整本书发给服务端。**先本地建索引，再把命中的几个片段交给 AI** —— 检索在本地执行、不耗 Token。

**（3）技能与 Agent**
- 内置技能元数据 `@shared/aiSkills`，用户可覆盖（`aiSkillOverrides` / `aiCustomSkills`）；
- Agent 工具与主进程 `ai/chat/agentTools.ts` 对齐，单次提问的工具往返受 `chat.maxToolRounds` 限制；
- 具体工具：**思维导图**（`aiMindmapTool.ts` → markmap 渲染）、**词云**（`tools/wordcloudTool.ts` + `@node-rs/jieba` 分词 → d3-cloud 渲染，分词缓存 `segment.sqlite`）。

**（4）角色卡 + 文生图**
- 侧栏"角色"→ `CharacterEditDrawer` → 生成弹窗填画风/形象/负面词；
- 对话模型先把画风+形象整理成 prompt（自然语言族或 SD tag 族）；
- 经 IPC `ai:txt2img` → 主进程按 backend 分发（A1111 `/sdapi/v1/*`、ComfyUI `/prompt`、OpenAI Images、通义万相、MiniMax 等）；
- 立绘落 `characterPortraitCacheDir`，角色卡展示支持 3D 倾斜与闪卡纹理。

### 1.5 数据层：SQLite + JSON + localStorage 三层

| 层 | 载体 | 存什么 |
|---|---|---|
| **关系/向量层** | `vector.sqlite`（better-sqlite3 + sqlite-vec） | 向量索引 + 按书（内容哈希）隔离的多会话消息 |
| **单书元数据** | `colorTxt.file.meta`（JSON） | 书签 `FileBookmarkItem`、阅读进度、高亮、笔记、角色卡、电子书转换元数据（`convertedMdPath` / `sourceMtimeMsAtConvert`） |
| **应用配置** | `config.json`（**不含明文密钥**）+ `userData/ai/secrets.v1.json`（加密密钥库，串行队列 + 原子落盘） | 模型方案、端点、密钥 |
| **UI 状态** | `localStorage`（`colorTxt.ui.settings` 等） | 侧栏宽度、字体字号、行距字距、配色、阅读尺参数、定时滚动等 |

**彩读书包 `.ctz` / `.ctzx`**（zip / 加密 zip）的内部结构 —— 这是一个很好的"可移植数据单元"设计：

```
{文件名}.ctz|ctzx/
├── content/{文件名}.txt|md          # 正文
├── content/{文件名}.Images/         # md 插图
├── bookmarks.json                    # 书签
├── highlights.json                   # 高亮
├── notes.json                        # 笔记
├── characters/manifest.json          # 角色卡（kind: "characterRoster"）
├── characters/portraits/*.png        # 角色立绘
└── manifest.json                     # { kind:"readerBook", schemaVersion:1,
                                      #   contentFileName, sourceEbookFileName?,
                                      #   imagesDirName?, viewportTopPhysicalLine? }
```

### 1.6 值得抄的 8 个设计

1. **物理行 / 展示行双坐标系** —— 所有持久化锚定物理行，显示层随便加工都不错位。**本方案的核心依赖。**
2. **Monaco 当可编程着色画布** —— 不重写渲染器，直接用工业级编辑器内核拿"高亮/装饰/黏性标题/多光标查找"。
3. **主/预载/渲染 + shared 四段式**，`contextBridge` 收口 API 面 —— 安全边界清晰。
4. **composables 取代状态库** —— 单窗口重状态应用，少一层抽象。
5. **`shared/` 单一事实源** —— 类型、IPC 载荷、默认配置三端共用，杜绝"三份定义漂移"。
6. **RAG 建索引 = 按章分块 + 本地嵌入 + sqlite-vec** —— 成本可控、隐私友好，正是本项目要做"全书问答"的地基。
7. **书包 `.ctz` 作为可移植数据单元** —— 把"正文 + 标注 + 角色卡 + 进度"打成一包，天然适合"分析结果随书走"。
8. **打包期裁剪**：`scripts/prune-pack-deps.mjs` 在打包前裁 `node_modules`（真源映射、非目标平台原生包、Web WASM 推理）—— 与本项目第九章"jieba 瘦身"是同一套思路。

### 2.3 有冲突、必须合并的（4 项）

**① 章节切分：确定性切分 vs 运行时识别 → 合并为「双模式章节服务」**

- V2.0 的 M1 是**批处理**：一次性把 `红楼梦.txt` 切成 120 个文件，命名 `章号_字数_章名.txt`，段落以全角空格开头 —— 这是 120 章历史产物的**口径基础**，动不得。
- ColorTxt 是**运行时**：打开任意文件即时识别章节，支持用户自定义正则。

**合并方案**：一套「章节规则引擎」，两个出口 ——
- `materialize()`：批处理切分（供分析管线用，输出格式不变，保住历史口径）；
- `outline()`：运行时识别（供阅读器用，返回章节树 + 锚点）。

两者共用同一份规则表（`chapterRules.json`：ATX 标题 + 自定义正则 + 红楼特有规则如「第X回」），保证"读到的章节"与"切出的章节"永远一致。**这是个必须解决的问题** —— 否则会出现"阅读器显示 120 回、分析报告编号 119"这类错位。

**② 人物挖掘：ALIAS 归并 vs 角色卡 → 角色卡是 UI，ALIAS 是内核**

- V2.0 的 M6 核心是**别名归并**（`gen_index.py` 的 `ALIAS` 40+ 条）—— 解决"宝玉 / 宝二爷 / 怡红公子 / 神瑛侍者"是同一个人的问题。这是全项目最难、最不可替代的资产。
- ColorTxt 的角色卡是**展示与生成**：AI 检索角色信息 → 生成摘要 → 文生图立绘。

**合并方案**：`角色 = ALIAS 内核 + 角色卡 UI`。
- 数据：`entity`（主名 + 别名列表 + 首次出场章节 + 出场次数）来自 M6；
- 展示：角色卡组件呈现，可选 AI 生成摘要与立绘；
- **阅读器联动**：正文中所有人名（含别名）按 entity 着色/下划线，点开即角色卡 —— 这是"析"回灌"读"的直接体现。

**③ 全局索引：结构化索引 vs 向量索引 → 双层检索（结构化 + 语义）**

- V2.0 的 M7 产出**结构化全局索引**：归档索引表、人物出场档案、逐章累计统计、伏笔线索追踪、七类情绪汇总、情感基调演变、全局统计摘要。答案"精确、可溯源"。
- ColorTxt 的 RAG 是**语义检索**：按章分块 → 向量 → topK。答案"召回广、能容错"。

**合并方案**：**混合检索（Hybrid Retrieval）** —— 这是本方案对"分析"能力最大的增强：

```
用户提问
  ├─ 结构化通路：查 SQLite 索引表（人物→出场章、事件→章节、情绪→趋势）
  │     → 命中即得到【确定性答案 + 精确出处】
  └─ 语义通路：sqlite-vec 向量召回 topK 片段
        → 得到【相关原文片段】
  ↓ 合并去重、按锚点排序
  ↓ 交给 LLM 作答，答案每一句都附 (章, 物理行) 锚点
```

**结构化通路保证"准"，语义通路保证"全"**，且结构化那一半已经在 V2.0 里做完了，等于白得。

**④ 可视化：后端出图 vs 前端出图 → 全部改前端渲染**

- V2.0 的 M8 曾计划 Python `wordcloud`（numpy + pillow + wordcloud，装后约 70 MB）。
- ColorTxt 是纯前端出图：词云用 `d3-cloud` + `@node-rs/jieba` 分词（缓存 `segment.sqlite`），思维导图用 markmap。

**合并方案**：统一走**前端渲染**（ECharts / d3-cloud / markmap / 关系图用 ECharts graph 或 Cytoscape）。
- 直接消灭第九章"杠杆①"要省的那 70 MB；
- 而且**交互性更好**：前端图上可以直接点击 → 跳转到正文锚点，这是后端出静态图做不到的。

### 2.4 架构判优：4 个具体分歧

**分歧 1：桌面壳 —— Electron（ColorTxt）vs Tauri（V2.0）？**
→ 见 §5.1 单独决断。**结论：本项目选 Tauri。**

**分歧 2：进程通信 —— IPC vs localhost HTTP？**
- ColorTxt：`contextBridge` + IPC，**不开端口**。
- V2.0：FastAPI 起在 localhost，前端 HTTP 调用。

**判定：采 ColorTxt 的思路，但通信体改为 stdio JSON-RPC。** 理由：
1. 桌面单机应用不需要 HTTP 服务 —— 开端口带来防火墙弹窗、端口冲突、CORS 配置、以及"本机其他进程可访问"的暴露面；
2. 但 V2.0 的 Python 引擎必须保留，所以不能纯 IPC（IPC 是 Electron/Node 的能力）。**用 stdio 管道做 JSON-RPC**：壳启动 Python 子进程，通过标准输入输出收发结构化消息 —— 既有 IPC 的安全与零配置，又能复用 Python 引擎；
3. 顺带解决"分析任务进度推送"：sidecar 主动往 stdout 写进度事件，前端订阅（等价于 ColorTxt 的 `onAgentEvent`）。

**分歧 3：状态管理 —— composables vs 状态库？**
- ColorTxt 刻意不用 Pinia/Vuex，全 `composables/`。
- **判定：采 ColorTxt。** 单窗口、状态围绕"当前书 + 当前章节"高度内聚，加一层 store 只增加间接性。但**跨章节共享的分析结果**（实体表、事件表）应放在一个明确的 `analysisStore` 类（单一实例、显式 API），避免散落在几十个 composable 里。

**分歧 4：数据存储 —— 文件为唯一 vs SQLite 为骨？**
- V2.0：`分析结果/*.md` + `*.json` 是唯一存储，报告即数据。
- ColorTxt：SQLite 存可查询/可检索的东西，JSON 存单书元数据，localStorage 存 UI 状态。

**判定：采 ColorTxt 的分层，但把"MD/JSON 导出"升级为不可省的契约。** 理由：现有 120 章报告、全局索引是**已有资产**，且"报告即可读文件"对本项目有独立价值（可直接进 Git、可被人读）。所以：
- **主存**：SQLite（可查询、可检索、可事务）；
- **导出**：MD/JSON（保持现有格式与命名不变，一键导出）；
- **不丢资产**：现有 `分析结果/` 目录可以直接 import 进 SQLite（一次性迁移脚本）。

### 2.5 判断为「不并入」的（3 项）

**① 书源找书（Legado 引擎）—— 不并入。**
红楼梦是一部固定文本，本项目是"阅读+分析一本书"的工作台，不是"找书"的阅读器。它的价值在于"多源搜索 + 下载"，与本项目"深度分析一本"的定位正交。若将来要泛化到"任意中文小说"，可作为 P3 独立模块补充。

**② 摸鱼模式 / 番茄钟 —— 不并入。**
属于通用阅读器的注意力管理功能，与研究型工作台的目标用户不匹配。（阅读尺（ADHD 聚焦）则保留 —— 长文本精读确有用。）

**③ 多窗口 —— 不并入（P3 再议）。**
本项目是"单书深读"场景，多窗口带来的状态同步复杂度（`isMinimalistView` 就是按窗口写入、不跨窗口同步的例子）不值得。

### 3.1 分层：读域 / 析域 / 通域

└───────────────────────────┬─────────────────────────────────────┘
                            │  统一锚点模型（chapter, physical_line_range）
┌───────────────────────────┴─────────────────────────────────────┐

│  R4 阅读辅助与转换（尺/禅/简繁/替换）   │  A4 人物挖掘与角色卡（ALIAS）    │
│                                     │  A5 LLM 深度分析与技能/Agent     │
└─────────────────────────────────────┴───────────────────────────────┘
                            │

**壳与运行时**：Tauri 2（Rust，薄壳）+ Vue 3 + TS（前端）+ Python sidecar（全部重活）。

### 3.2 核心创新：统一锚点模型

**这是整个融合方案的技术支点。**

ColorTxt 证明了"把持久化数据锚定在物理行"是可行的；本项目需要把**分析产物也锚定到同一个坐标系**，于是两类数据可以互相引用。

```python
# 统一锚点（所有阅读产物与分析产物共用）
Anchor = {
  "bookId":         "hongloumeng",       # 书籍标识（内容哈希）
  "chapterIndex":   27,                  # 0-based 章序
  "lineStart":      142,                 # 物理行起（闭）
  "lineEnd":        147,                 # 物理行止（闭）
  "charStart":      12,                  # 可选：行内字符偏移
  "charEnd":        48,
}
```

在此基础上，**所有对象共享一种"可寻址性"**：

| 对象 | 来源 | 锚点粒度 |
|---|---|---|
| 书签 bookmark | 读域 R3 | 单物理行 |
| 高亮 highlight | 读域 R3 | 行 + 字符区间 |
| 笔记 note | 读域 R3 | 行 + 字符区间 |
| 情感段 emotionSegment | 析域 A2 | 段（若干物理行） |
| 事件 event | 析域 A3 | 段 / 跨章区间 |
| 人物提及 entityMention | 析域 A4 | 行 + 字符区间 |
| 伏笔线索 foreshadow | 析域 A4/X1 | 跨章（起锚点 + 收锚点） |
| 知识块 chunk（RAG） | 通域 X1 | 章（分块边界） |

**带来的直接能力**：
- 从分析报告里点"此处"，**直接跳到阅读器对应物理行并高亮**；
- 从阅读器选中一段，**直接查到它属于哪个事件、哪个人物、什么情感**；
- 一切"卷/回/章/行"的引用都是**可点击的锚点**，而不是文本描述。

### 3.3 双管线如何交汇

```
                      ┌────────────────────────────────┐
   打开书籍 ─────────▶ │ R1 章节识别（outline 模式）      │
                      └───────────────┬────────────────┘
                                      │ 章节树 + 物理行锚点
              ┌───────────────────────┴───────────────────────┐
              ▼                                               ▼
    ┌──────────────────┐                          ┌──────────────────────┐
    │ 读管线（即时）      │                          │ 析管线（可后台/批量）   │
    │ R2 渲染上色        │                          │ R1 materialize 切分   │
    │ R3 标注            │                          │ A1 分词 → A2 情感      │
    │ R4 辅助            │  ◀── 同一锚点坐标系 ──▶   │ A3 事件 → A4 人物      │
    └────────┬─────────┘                          │ A5 LLM 深度分析        │
             │                                     └──────────┬───────────┘
             │  ① 分析产物按锚点回灌（着色/下划线/事件标记/伏笔标记）  │
             │  ② 阅读行为按锚点回灌（选中→问 AI；改动→增量重析）     │
             └────────────────────┬───────────────────────────┘
                                  ▼
                    ┌──────────────────────────────┐
                    │ X1 混合检索（结构化 + 向量）    │
                    │ X2 呈现与导出（含 MD/JSON）     │
                    │ X3 存储（SQLite 为骨）          │
                    └──────────────────────────────┘
```

**两条关键回流**：
1. **析 → 读**：分析结果按锚点画回正文（§4）；
2. **读 → 析**：用户在阅读中的行为（选中提问、手动标注、修订文本）可以触发**增量重析** —— 只重算受影响的章节，而不是全量重跑。这需要析管线支持**按章粒度的增量执行**（V2.0 的 M4 已有"断点续跑"，扩成"章节级失效重算"即可）。

### 3.4 进程与通信：Tauri + Python sidecar + stdio JSON-RPC

```
┌──────────────── Tauri（Rust 主进程） ────────────────┐
│  窗口/菜单/全局快捷键/文件对话框/原生能力              │
│  Sidecar 管理器：拉起、健康检查、重启、优雅退出         │
└──────┬───────────────────────────────┬──────────────┘
       │ Tauri IPC（invoke/emit）        │ stdio（JSON-RPC 2.0，逐行）
       ▼                               ▼
┌──────────────────────┐      ┌──────────────────────────────┐
│ 前端：Vue 3 + TS      │      │ Python sidecar（全部重活）      │
│ · Monaco 阅读器        │      │ · jieba 分词 / 词频            │
│ · 标注 / 章节树 / 搜索  │      │ · 双引擎情感分析                │
│ · ECharts/d3/markmap  │      │ · LLM 调度 + 提示词模板         │
│ · AI 助手面板          │      │ · 事件/人物/索引               │
│ · 设置/主题            │      │ · sqlite-vec 向量检索 + 嵌入    │
└──────────────────────┘      │ · MD/JSON 导出                 │
                              └──────────────┬───────────────┘
                                             ▼
                                  book.sqlite（唯一数据文件）
```

**协议设计要点**：
- **逐行 JSON（NDJSON）**：每行一个完整 JSON-RPC 消息，天然分帧，不必处理粘包；
- **双向**：前端 → sidecar 是 `request`（有 `id`，等 `result`）；sidecar → 前端是 `notification`（无 `id`，推进度/日志/流式 token）；
- **流式**：LLM 输出的 token 增量、分析任务进度（`{chapter, done, total}`）都走 notification；
- **取消**：`cancel(requestId)` —— 长任务（如全书情感分析）必须可中断；
- **零配置**：不开端口、不写临时文件、不需要 CORS；
- **单实例**：sidecar 进程由壳托管，应用退出时先发 `shutdown` 再 `kill`（学 ColorTxt 的 sidecar 生命周期清理）。

### 3.5 融合后的 10 个模块

| 模块 | 名称 | 来源 | 职责 |
|---|---|---|---|
| **R1** | 章节识别与切分 | M1 + ColorTxt | `outline()` 运行时识别 + `materialize()` 批处理切分，共用规则表 |

## 四、分析结果如何「回灌」阅读（4 个杀手场景）

这一节是"阅读+分析"区别于"阅读器"和"分析器"的地方。

**场景 1：情感着色（Emotion Coloring）**

A2 输出的段落级情感（好/乐/哀/怒/惧/恶/惊 + 极性强度）直接映射为正文背景色：
- 七类情绪 → 七套低饱和度底色（可调透明度），叠加在段落上；
- 阅读时一眼看出"这一段是悲是喜"，配合时间轴滑块可看**全书情绪地形图**；
- 情绪曲线与正文**双向联动**：点曲线上的峰值 → 跳到对应回目。

> 这是 ColorTxt"内容上色"与 V2.0"情感分析"的正面相乘 —— 它有上色引擎但没情感数据，我们有情感数据但没上色载体。

**场景 2：人物高亮与角色卡（Entity Highlight）**

A4 的 entity 表（含别名）驱动正文着色：
- 主要人物各有专属色，**别名一并着色**（"宝玉/宝二爷/怡红公子"同色，鼠标悬停显示规范名）—— 这直接解决了"读的时候认不出别名"的问题；
- 点击人名 → 弹出角色卡（出场章列表 + 出场曲线 + 关系邻接 + 可选 AI 摘要/立绘）；
- 角色卡里点任意出场章 → 跳转正文锚点。

**场景 3：事件与伏笔的就地标记（In-place Annotation）**

- A3 的事件按锚点落在段落上，在编辑器**左侧装订线（glyph margin）**标级别色块，悬停显示事件摘要与 5W1H；
- A4/X1 的伏笔线索是"跨章锚点对"：在草蛇灰线处标「○ 起」，在应验处标「● 收」，可一键在两点间跳转；
- 全书事件时间线（X2）点击任意事件 → 正文定位。**"读到第 27 回，前面的伏笔自动亮起"** —— 这是纸质书给不了的体验。

**场景 4：选区即分析（Select-to-Analyze）**

- 在正文选中一段 → 浮动工具条（学 ColorTxt 的 `ReaderSelectionToolbar`）出现四个动作：
  - **问 AI**（带上选中文本作 blockquote，走 X1 混合检索 + A5）；
  - **看分析**（该段所属的事件 / 人物 / 情感，来自本地索引，**离线即时**）；
  - **查词典**（古白话名物词，`dictionary/`）；
  - **加笔记**（写入 R3）。
- 反向：在 AI 助手回答中，每个引用片段都是锚点链接，点击定位原文。

## 五、技术选型决断

### 5.1 桌面壳：Tauri vs Electron（关键决断）

这是两份方案**唯一正面冲突**的选型，必须给理由。

| 维度 | Electron（ColorTxt 的选择） | Tauri 2（V2.0 的选择） | 本项目权重 |
|---|---|---|---|
| 安装包体积 | 约 137 MB（内置 Chromium） | 约 55 MB | **高**（第九章专门论证过） |
| 冷启动 | 较慢 | 快（系统 WebView2） | 中 |
| 原生生态 | **Node 生态零成本**：better-sqlite3、sqlite-vec、`@node-rs/jieba`、transformers.js、onnxruntime-node、OpenCC | 需 Rust crate（rusqlite、sqlite-vec-rs、jieba-rs、opencc-rs）或落到 Python sidecar | **中** |
| 与本项目引擎的契合 | 需同时维护 **Node + Python** 两套运行时 | **只有一套重型运行时（Python）** | **高** |
| 目标机依赖 | 无（自带 Chromium） | 需 WebView2（Win10/11 基本自带，可 `downloadBootstrapper` 按需下载） | 低 |
| 成熟先例 | ColorTxt 已跑通全功能 | 本项目尚无 | 中 |
| 内存占用 | 较高 | 较低 | 低 |

**决断：本项目选 Tauri 2 + Python sidecar。**

理由链：
1. **本项目的"重活"已经在 Python 里且已被验证**（jieba + 双引擎情感 + 120 章历史产物口径锁定）。这是**不能换**的资产。
2. 若选 Electron，Node 侧能做原生库，但**分析引擎仍在 Python** → 必然被拖成"Node + Python 双运行时"，体积走 137 MB 路线，且要维护两套依赖树。
3. 若选 Tauri，只需一套重型运行时（Python），壳极薄，体积守住 55 MB 级，与第九章路线一致。
4. Electron 的优势（Node 原生库零成本）在本项目里被 Python 覆盖：`sqlite-vec` 有 Python 绑定、嵌入可用 `onnxruntime`/`fastembed`、简繁转换 Python 侧有 OpenCC、jieba 本就是 Python 的。

**例外与退路（诚实说明）**：若 RAG/嵌入/原生集成在 Tauri 侧被证明成本过高、工期不可接受，则**降级为 Electron** —— 届时最省事的路径是**直接 fork ColorTxt**，把 Python 分析引擎当 CLI 子进程调用。代价：体积 +80 MB、双运行时。**这是一个合理的"快速可用"路线，但不是最优架构。**

**切换成本评估**：读域（R1–R4）与通域（X1–X3）的**前端代码 100% 可迁移**（都是 Web 技术）；差异集中在壳层（约 1–2 周）与原生模块落点。所以先按 Tauri 做、必要时退 Electron，是可承受的。

### 5.2 阅读器内核：Monaco vs 自研虚拟列表

| 方案 | 优 | 劣 |
|---|---|---|
| **Monaco（ColorTxt 的选择）** | 开箱即得：行级装饰（标注）、glyph margin（事件标记）、黏性滚动（章节条）、多光标、查找栏、ViewZone（插图）、CJK 换行可改；着色 = Monarch 规则引擎 | 体积大（gzip 约 5 MB）；"编辑器"心智负担；超长文本需调优 |
| 自研虚拟列表 | 体积小、完全可控 | 装饰系统、查找、选择、折叠、标记全都要自己写 —— **这是几周 vs 几天的差距** |

**决断：采 Monaco。** 红楼梦全书仅 2.45 MB / 120 章，远未触及 Monaco 的性能上限；而它一次性提供了本方案需要的**全部文本装饰能力**（高亮、glyph、ViewZone、黏性标题）。自研的唯一收益是体积，但前端资源本就只有约 3 MB 预算，Monaco 的 5 MB gzip 可接受（且可经打包期裁剪语言服务，只留纯文本模式）。

### 5.3 AI / RAG 的落点

| 能力 | 落点 | 说明 |
|---|---|---|
| LLM 对话 / 深度分析 | **Python sidecar** | 复用 V2.0 的 M4（模板化提示词、质量门禁、断点续跑）+ ColorTxt 的技能/Agent 工具机制 |
| 嵌入（向量化） | **Python sidecar** | `onnxruntime` / `fastembed`；模型 BGE-small-zh-v1.5（实测 90.4 MB / 512 维，HF 缓存磁盘占用约 181.6 MiB），首次使用时下载 |
| 向量索引 | **Python sidecar + sqlite-vec** | 与主库同文件或独立 `vector.sqlite`；按章分块 |
| 技能 / Agent 工具 | **Python sidecar** | 工具注册表 + 单次提问的工具往返上限（学 `chat.maxToolRounds`） |
| 文生图（角色立绘） | **Python sidecar** | 可选 P2；A1111 / ComfyUI / OpenAI 兼容后端 |
| 密钥保管 | **壳层保险库** | 独立加密文件（学 `secrets.v1.json`：串行队列 + 原子落盘），主配置**不存明文** |

**混合检索的落地**（§2.3-③）：
```
question
 ├─ 结构化：SQLite 索引表查询（人物→出场 / 事件→章节 / 情绪→趋势）
 └─ 语义：sqlite-vec topK（按章分块向量）
 → 合并去重、按锚点排序 → 组装上下文（含锚点标注）→ LLM 作答
 → 答案内每个引用渲染为可点击锚点
```

### 5.4 存储：SQLite 为骨，MD/JSON 为面

| 层 | 载体 | 内容 |
|---|---|---|
| 主存 | `book.sqlite` | books / chapters / annotations / entities / events / emotions / foreshadows / chunks(VSS) |
| 向量 | 同库 VSS 表（sqlite-vec） | 分块向量 + 元数据 |
| 配置 | `config.json`（无明文密钥）+ `secrets.vault`（加密） | 模型方案、端点 |
| UI 状态 | `localStorage` | 侧栏、字体、主题、阅读尺参数 |
| **导出** | **`分析结果/*.md` + `*.json`（格式与命名不变）** | 报告、全局索引、结构化提取 |
| 可移植单元 | `{书名}.hlm.zip`（借 `.ctz` 思路） | 正文 + 标注 + 分析与角色卡 + 进度 |

**关键约束：导出格式必须与现有 120 章产物同名同构**，这样新旧产物可以混放、可被现有脚本（`gen_index.py`、`extract_v34_v2.py`）继续消费 —— 迁移期间两套并存，不打断现有工作流。

## 六、数据模型

```sql
-- 书籍与章节
CREATE TABLE books (
  book_id      TEXT PRIMARY KEY,        -- 内容哈希
  title        TEXT, source_path TEXT,
  total_chars  INTEGER, created_at INTEGER
);
CREATE TABLE chapters (
  book_id TEXT, idx INTEGER,            -- 0-based
  title TEXT, start_line INTEGER, end_line INTEGER,
  PRIMARY KEY (book_id, idx)
);

-- 读域：标注（锚定物理行）
CREATE TABLE annotations (
  id INTEGER PRIMARY KEY, book_id TEXT,
  kind TEXT,                            -- bookmark | highlight | note
  chapter_idx INTEGER,
  line_start INTEGER, line_end INTEGER,
  char_start INTEGER, char_end INTEGER, -- 可空（整行）
  text TEXT, note TEXT, color TEXT,
  created_at INTEGER
);

-- 析域：情感段（驱动着色）
CREATE TABLE emotions (
  book_id TEXT, chapter_idx INTEGER,
  line_start INTEGER, line_end INTEGER,
  dutir_top TEXT,                       -- 好/乐/哀/怒/惧/恶/惊
  polarity REAL, intensity REAL,
  weights_json TEXT                     -- 七类分量
);

-- 析域：事件
CREATE TABLE events (
  id INTEGER PRIMARY KEY, book_id TEXT,
  level TEXT,                           -- 主线 | 支线 | 细节
  chapter_idx INTEGER, line_start INTEGER, line_end INTEGER,
  summary TEXT, w5h1_json TEXT, participants_json TEXT
);

-- 析域：实体（ALIAS 归并内核）
CREATE TABLE entities (
  id INTEGER PRIMARY KEY, book_id TEXT,
  canonical TEXT,                       -- 规范名
  aliases_json TEXT,                    -- 别名数组
  first_chapter INTEGER, appear_count INTEGER,
  profile_md TEXT, portrait_path TEXT   -- 角色卡内容（可选）
);
CREATE TABLE entity_mentions (
  entity_id INTEGER, book_id TEXT,
  chapter_idx INTEGER, line_start INTEGER,
  char_start INTEGER, char_end INTEGER, surface TEXT  -- 原文写法
);

-- 析域：伏笔（跨章锚点对）
CREATE TABLE foreshadows (
  id INTEGER PRIMARY KEY, book_id TEXT,
  setup_chapter INTEGER, setup_line INTEGER,
  payoff_chapter INTEGER, payoff_line INTEGER,
  note TEXT, status TEXT                -- open | closed
);

-- 通域：RAG 分块 + 向量
CREATE TABLE chunks (
  id INTEGER PRIMARY KEY, book_id TEXT,
  chapter_idx INTEGER, line_start INTEGER, line_end INTEGER,
  text TEXT
);
CREATE VIRTUAL TABLE chunk_vec USING vec0(
  chunk_id INTEGER PRIMARY KEY, embedding FLOAT[512]
);
```

**一致性规则**：
- 一切"位置"都是 `(chapter_idx, line_start/end)`，与读域完全同构；
- `chapters` 是唯一的行号权威 —— 任何文本替换/转换**不得改变物理行号**（这正是 ColorTxt 双坐标系的作用）；
- 增量重析的失效键 = `(book_id, chapter_idx)`。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **壳选型反复**（Tauri ↔ Electron） | 工期翻倍 | M1 完成前**冻结选型**；前端代码保持 100% 可迁移，壳层隔离在 `shell/` 目录 |
| **双坐标系被破坏**（替换/转换改了物理行） | 所有标注与分析锚点错位 | 硬规则：**加工只作用于展示层**；物理行由 `chapters` 表唯一权威；写单元测试断言"替换后物理行号不变" |
| **锚点粒度不一致**（句子 / 段 / 章） | 跨模块无法对齐 | 锚点统一为"物理行区间"，最细到行内字符偏移；句子级分析结果向上归并到行 |
| **嵌入模型体积与下载** | 破坏"开箱即用" | 模型**不进安装包**，首次使用 RAG 时按需下载（学 ColorTxt），并给出"不用 RAG 也能全功能离线分析"的降级路径 |
| **SQLite 与现有 MD 产物双写不一致** | 报告与库数据打架 | MD/JSON **只作为导出**（单向：库 → 文件）；迁移期用一次性 import 脚本反向灌入 |
| **Tauri 侧原生集成成本超预期** | 阻塞 M3/M5 | 预留 Electron 退路（§5.1）；把 RAG/嵌入放在 Python，避免绑定壳的原生能力 |
| **Monaco 体积与"编辑器感"** | 包体偏大 / 心智负担 | 打包期裁剪语言服务（只留纯文本）；UI 上隐藏编辑态入口，默认只读 |
| **分析口径被无意改动** | 120 章历史产物失去可比性 | 沿用既有约定：词库扩展只做并集、情感引擎不替换、报告命名与结构不变 |
