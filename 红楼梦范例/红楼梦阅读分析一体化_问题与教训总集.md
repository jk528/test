## 一、M0 环境搭建：工具链 10 个坑

环境阶段的问题集中在 Windows 上「自动化安装多语言工具链」这一场景。10 个坑逐一记录：

| # | 问题 | 根因 | 处理方式 |
|---|------|------|---------|
| 1 | PowerShell 5.1 中文乱码、脚本语法错误 | 含中文的 `.ps1` 以 UTF-8 无 BOM 保存，PS5.1 按 GBK 解码 | 脚本统一存 UTF-8 带 BOM（或注释只用英文） |
| 2 | `winget` 误报 Python 已安装 | 注册表残留幽灵 ARP 记录，指向已删除的目录 | `winget install --id Python.Python.3.12 --force` 强制实装 |
| 3 | Rustup 安装报作用域不匹配 | winget 1.4 对 `Rustlang.Rustup` 加 `--scope user` 不被接受 | 去掉 `--scope`，rustup 本就默认用户级 |
| 4 | `winget --info` 版本低于预期 | 包元数据与 CLI 版本不同步，部分新参数不支持 | 不依赖新参数，传了也不报错但要留意 |
| 5 | Node MSI、MSVC 安装弹 UAC | 机器级安装必须授权 | 脚本说明需用户手动点「是」 |
| 6 | `Set-ExecutionPolicy` 报 Security error | 执行策略受限 | 用 `-ExecutionPolicy Bypass` 调用脚本 |
| 7 | `cargo --version` 报工具链不适用 / Missing manifest | 工具链半成品（有 cargo.pdb 无 cargo.exe），`rustup component add` 误报 up to date | 整体卸载后 `rustup toolchain install ... --force` 重装 |
| 8 | `python -m venv` 的 ensurepip 失败 | 本机 Python 的 ensurepip 引导不可用，venv 无 pip | 先 `--without-pip` 建 venv，再 `get-pip.py` 引导 |
| 9 | `setup.exe modify` 报 Option 'wait' is unknown | VS Installer 4.5.35 不支持 `--wait` | 去掉 `--wait`，用 `--quiet --norestart --nocache`（命令本身会阻塞） |
| 10 | 云盘同步目录锁文件、毁数据库 | 工程位于华为云盘同步目录，客户端扫描加锁、多机互相覆盖 | 一切本机环境与运行时数据移出同步目录 |

其中三个坑值得展开。

### 坑 1-7：Rust 工具链「半成品」重装

**现象**：`rustup show` 正常，但 `cargo --version` 报 `the 'cargo.exe' binary ... is not applicable to the toolchain`，工具链 `bin\` 里只有 cargo.pdb 没有 cargo.exe，呈 rustc 1.95.0 半成品状态。普通 `rustup component add cargo` 无效，误报 up to date。

**处理**：整体卸载后强制重装才拿到完整的 rustc/cargo 1.98.1（6 个组件齐全）。

**教训**：工具链半成品状态不能用「增量修复」，必须整体卸载重装。复装后立即做端到端冒烟验证（在 `%TEMP%` 建 `cargo new` 项目并 `cargo run` 输出 Hello world），用「真实编译通过」作为环境就绪的证据，而不是只看 `--version`。

### 坑 1-10：云盘同步目录是环境与数据的「隐形杀手」

**现象**：编辑源码时反复出现 `EBUSY: resource busy or locked`（云盘客户端正在扫描/上传该文件）；运行时数据（SQLite + 模型）放在目录内会被多机覆盖、被客户端加锁、白占同步流量。

**处理**：把所有「本机环境与本机运行时数据」放同步目录外：venv → `%USERPROFILE%\.venvs\honglou`，主库与模型 → `%USERPROFILE%\.honglou`。同步目录内只放「清单/锁文件 + 源码 + 数据资产」，环境各机重建。

**教训**：判断「什么该同步」的标准很简单：**含本机绝对路径的、带二进制伴随文件的、能重新生成的，都不要同步**。这一原则在 M3 阶段（主库 + 181.6 MiB 模型误放工程目录）又踩了一次，见第三、七节。

### 坑 1-8：venv 没有 pip 的引导链

**现象**：`python -m venv` 报 ensurepip 返回非零，生成的 venv 里没有 pip。

**处理**：`python -m venv --without-pip` 建壳 → `Invoke-WebRequest` 拉 get-pip.py → 用 venv 的 python 执行。

**教训**：Windows 上「Python 自带 ensurepip」并非总可靠，get-pip.py 是兜底方案。venv 刻意放在同步目录外（`pyvenv.cfg` 硬编码绝对路径、含二进制，不能跨机同步），依赖清单以 `requirements.txt` 随目录走，每台机器各自重建。

## 二、M1 前端骨架：构建与渲染坑

### 坑 2-1：Vite 8（rolldown）对 monaco worker 裸包解析失败

**现象**：`?worker` 导入裸包路径时构建失败。

**根因**：Vite 8 改用 rolldown 内核，对 monaco worker 的裸包 `?worker` 解析不兼容。

**处理**：降到稳定的 **Vite 6 + rollup**（`@vitejs/plugin-vue@5`、`typescript@5.6`、`vue-tsc@2`）。

**教训**：追新工具链版本前先验证生态兼容性。monaco 这类重度依赖 worker 机制的库，对打包器内核升级非常敏感。

### 坑 2-2：monaco-editor 0.56 的 exports 映射变化

**现象**：裸包深路径 `monaco-editor/esm/vs/editor/...` 无法解析。

**根因**：monaco 0.56 的 `exports` 把 `./*` 映射到 `./esm/vs/*.js`，深路径不能再带 `esm/vs` 前缀。

**处理**：裸包深路径写 `monaco-editor/editor/editor.worker.js`；worker 经 `src/workers/editor.worker.ts` 相对路径 `?worker` 打包；`esbuild` 加入 `pnpm.onlyBuiltDependencies` 白名单。

**教训**：版本升级时，深路径导入格式与构建白名单是隐藏破坏点，升级后必须重跑构建 + 冒烟。

### 坑 2-3：wordWrap 截断 Bug（超长段落只显示前 20 字）

**现象**：一个物理行 = 一整段 300+ 字时，只显示前 20-25 字，右侧文字不可见且不换行；窗口拉宽后仍截断。

**根因**：`Reader.vue` 的 `reader-container` 在 flex 布局 `onMounted` 时宽度未就绪，Monaco 按错误宽度换行。

**处理**（`Reader.vue`）：
1. `wrappingStrategy: "advanced"`（先进换行算法）
2. `editor.layout()` 双保险：`requestAnimationFrame` + `setTimeout(500ms)` 强制重布局
3. 补 `window.addEventListener("resize", fixLayout)` 防 WebView2 下 ResizeObserver 漏触发
4. `onBeforeUnmount` 清理监听器与定时器

**教训**：WebView2 / flex 布局下 Monaco 的初始化时序问题，要用「延迟强制重布局 + 事件兜底」双保险，且必须清理副作用。

## 三、M3 数据与检索：8 项缺陷修复

M3 是「数据层落地」阶段，暴露了 8 个真实缺陷，全部按「先在真实库/真实协议上复现，再改代码」的原则修复。这 8 项是本文档最重要的部分，它们揭示了「SQLite + 向量库 + sidecar 通信」三类基础设施的常见暗坑。

### 缺陷 3-1（P0）：同一本书被重复入库，检索自我重复

**现象**：提问「贾宝玉梦游太虚幻境」，召回 6 条里前 3 条是同一段原文的三个副本，LLM 上下文被严重稀释。实测 `books` 3 条 / `chapters` 360 条（应 120）/ `chunks` 684 条（应 228），库膨胀到 6.32 MB。

**根因**：`book_id_of(source_path, text)` 把源路径掺进了哈希。同一本书被不同路径读到（`C:\…`、`\\?\C:\…`（Rust canonicalize 产物）、另一份拷贝）即生成不同 book_id。

**处理**：`book_id_of(text)` 改为纯内容哈希（先换行归一化，CRLF/LF 视为同书）。修复后 book_id 稳定，检索 6/6 满额去重。

**教训**：**书 = 内容，不是位置**。任何「内容身份」类 key 都不能掺路径、时间戳等位置性信息，且必须做换行归一化（`红楼梦.txt` 实测是 CRLF，3366 处）。

### 缺陷 3-2（P0）：向量表孤儿行累积，召回数随重建递减

**现象**：首次建索引后检索正常，但每次重建都会掉召回。

**根因**：`add_chunks()` 只 `DELETE FROM chunks`，不清 `chunk_vec`。`chunks` 是 AUTOINCREMENT，重插后拿到全新 id，旧向量行不会消失，变成指向已删除分块的孤儿。KNN 照常命中孤儿，随后的 `JOIN chunks` 再丢弃它们。实测 `chunk_vec` 1140 行 / `chunks` 684 行 → 孤儿 456 行。

**处理**：① `add_chunks` 插入前先 `_purge_vectors_of(book_id)`；② 新增 `purge_orphan_vectors()` 与 `maintenance` 方法清理历史遗留；③ `store_embeddings` 的 `INSERT OR REPLACE` 改裸 `INSERT`（vec0 虚拟表不支持 OR REPLACE（实测报 UNIQUE constraint failed），旧写法靠 id 永不复用才没炸，是个哑弹。

**教训**：**AUTOINCREMENT 主键 + 独立向量表 = 天然的孤儿制造机**。任何「重建索引」路径必须同步清向量表；虚拟表语法与普通表不同，改 SQL 前先查该引擎的约束。

### 缺陷 3-3（P0）：索引每次打开书都重建

**现象**：每次开书白跑 228 次嵌入（一次全量建索引 108.2s，其中模型下载 67s）。

**根因**：`App.vue` 的 `loadBook` 无条件调 `buildIndex`，不判断库里是否已有。

**处理**：① `books` 表加 `index_sig` 列（存「内容 + `RAG_CHUNK_LINES` + 章节结构」签名）+ 老库 `ALTER TABLE` 迁移；② 新增 `index_status` 方法；③ `build_index` 加幂等判断与 `force` 参数；④ 前端先问状态再决定是否重建。

**验证**：二次调用 `skipped=True`，耗时 108.2s → 0.03s。

**教训**：**昂贵的重活（嵌入、LLM 调用）必须幂等 + 有签名判据**，前端永远「先问再算」。

### 缺陷 3-4（P1）：`print` 污染 NDJSON stdout（哑弹）

**现象**：一旦 sqlite-vec 加载失败，Rust 侧 `serde_json::from_str` 解析失败，整个 sidecar 通信崩掉，表现为「打开书就报错」难以定位。

**根因**：`_try_load_vec` 的降级日志走 `print(...)`，而 stdout 是 NDJSON 协议通道，混入一行纯文本就破坏了响应流。

**处理**：改 `file=sys.stderr`；用「伪造 sqlite-vec 使 load 抛异常」实测：降级日志正确出现在 stderr，stdout 仍为纯 NDJSON。

**教训**：**在 stdout 跑协议的进程里，任何 `print` 都是定时炸弹**。本项目把「stdout 纯净性」写进了 e2e 回归测试（断言 stdout 无非 JSON 行）。

### 缺陷 3-5（P1）：情感分析结果不持久化

**现象**：重启后字级高亮丢失，段落底色能回放但字级词位置没有。

**根因**：分析结果只存在前端内存，没有落库。

**处理**：新增 `storage.upsert_emotions()` + sidecar `upsert_emotions` 方法，按行增量写、幂等；`emotions` 表加 `spans_json` 列存字级情感词位置。

**教训**：**不能用整章替换**：前端是视口驱动分批算的，整章替换会让后到的批次冲掉先前批次。增量幂等是「分批产生结果」场景的正确落库方式。

### 缺陷 3-6（P1）：书签未迁到 SQLite

**现象**：书签只存 localStorage，跨设备/跨会话丢失。

**处理**：前端 `loadBook` 后拉 `listAnnotations(book_id,'bookmark')`；库为空时把 localStorage 存量一次性迁移上去；切书签/删书签双写（localStorage 作离线兜底与首屏即时显示）。

**教训**：迁移类功能要「权威源 + 兜底源」双轨，先迁移存量再切换权威。

### 缺陷 3-7（P1）：运行时数据落在云盘同步目录内

**现象**：`app/.data/` 同时放 SQLite 主库与嵌入模型缓存，位于同步目录内：云盘加锁导致 EBUSY、多机互相覆盖导致库损坏、上百 MB 白占流量。

**处理**：新增 `config.DATA_DIR`，默认 `%USERPROFILE%\.honglou`（与 venv 同一原则），可用 `HONGLOU_DATA_DIR` 覆盖；把 `app/.data`（281.56 MB）整体迁出并删除同步目录内的旧副本。

**教训**：M0 的坑 1-10 在 M3 换了一种形式复现：**运行时数据与源码目录分离这一原则要写进配置层，而不是靠自觉**。

### 缺陷 3-8（P2）：401 直接抛原始 SDK 报文

**现象**：界面显示一长串英文 JSON，用户看不出该改哪里。

**处理**：`llm.py` 新增 `_explain()`，按 401/403/404/429/超时/连接失败分类给出中文可操作提示（含当前 model 与 key 前后缀）。

**教训**：**外部服务错误要翻译成「用户能行动」的语言**，而不是把 SDK 原始报文直接上抛。

## 四、M3 依赖与模型：下载与 API 坑

### 坑 4-1：HuggingFace 直连超时

**现象**：fastembed 默认从 huggingface.co 下载模型，国内超时（WinError 10060）。

**处理**：设 `HF_ENDPOINT=https://hf-mirror.com`。

### 坑 4-2：hf-xet CAS 401

**现象**：镜像站不支持 xet CAS 协议，下载报 401。

**处理**：设 `HF_HUB_DISABLE_XET=1` 禁用 xet，走普通 HTTP。

### 坑 4-3：sqlite-vec 的 KNN 语法约束

**现象**：用 `ORDER BY ... LIMIT ?` 查询 vec0 虚拟表报 `A LIMIT or 'k = ?' constraint is required`。

**处理**：KNN 查询必须写 `v.k = ?`。

### 坑 4-4：`upsert_annotation` 未 commit

**现象**：插入/更新后跨进程会话读不到。

**根因**：写库后未 `commit()`。

**处理**：补 commit；并把「标注 CRUD 跨会话可见」写进 e2e 断言。

### 坑 4-5：Embedder 方法名错误

**现象**：`retrieval.py` 的 `embed()` 误调 `self.ready()`（不存在）。

**处理**：改为 `self._get_model()`。

### 坑 4-6：pip 官方源极慢

**现象**：numpy 12.6 MB 从 pypi.org 下载 6 分钟未完成。

**处理**：切清华镜像 `--index-url https://pypi.tuna.tsinghua.edu.cn/simple`，90 秒全装完。

### 坑 4-7：火山方舟 API Key 401（唯一未解项）

**现象**：用户提供的 key 被方舟返回 `The API key doesn't exist`。

**性质**：外部凭据问题，非代码缺陷。已把 401 报文翻译成可操作提示（见缺陷 3-8），等用户提供有效 Key 或换 DeepSeek 等。

### 坑 4-8：BGE 模型实际体积与文档不符

**现象**：文档写 47 MB，实测 90.4 MB；且 HF 缓存在 Windows 不建符号链接，blobs 与 snapshots 各存一份 → 磁盘占用约 181.6 MiB。

**处理**：以实测为准更新文档；后续清理时把 181.6 MiB 僵尸缓存与活动缓存做 MD5 逐字节比对后才删。

**教训**：**「装后实际占用」永远以实测为准**，模型体积、磁盘占用这类数字必须重测，不能沿用旧文档。

## 五、M4 全景分析：报告回灌坑

M4 把既有 120 章 V3.4 报告回灌进 SQLite。这一阶段的核心问题是「把 LLM 生成的 Markdown 报告转成结构化数据」时的口径问题。

### 坑 5-1：别名重复计数

**现象**：`基础/红楼梦人物名.txt` 把「宝玉 / 黛玉 / 凤姐」等别名同时列为独立条目，不回并会出现「贾宝玉 4072 + 宝玉 3966」两条实体。

**处理**：`build_alias_map()` 把种子别名折回本名；`_usable_name()` 过滤 >6 字与非中文垃圾名。归并后 389 人，Top1 贾宝玉 4072（别名 宝玉/宝二爷/怡红公子/绛洞花王）。

**教训**：人物名表把「本名 + 别名」并列存放，统计时必须先做别名归并。

### 坑 5-2：报告段落号 ≠ 物理行号

**现象**：报告里的「第 N 段」与物理行号并非同一套编号（第 1 回报告最大段 37 vs 物理行 67），直接换算必错。

**处理**：三级降级锚定，并如实记录精度：`quote`（事件摘要引文在原文精确匹配，320 条 / 14.3%）→ `cooccur`（多实体共现位置定锚，1525 条 / 68.2%）→ `para`（段落级估算兜底，390 条 / 17.4%）；并加**单调不回退**修正（同章事件锚点必须非递减、且落在该章行区间内）。界面上每条事件带「精确 / 近似 / 粗定位」徽标。

**教训**：**跨系统的编号不能想当然等价**。定位精度不足时，诚实地标注精度等级比假装精确更有价值。

### 坑 5-3：tone 字段 56 种写法

**现象**：报告 tone 字段有 56 种原始写法。

**处理**：`normalize_tone()` 归一为 正面 / 负面 / 中性 / 其他 四类。

### 坑 5-4：占位卡片盖住正文（GUI 点验发现）

**现象**：关掉 AI 面板后，欢迎卡片压在正文上。

**根因**：`App.vue` 里 `<div v-else class="placeholder">` 紧跟 `AiPanel` 的 `v-if`，所以 `v-else` 绑的是「AI 面板未开」而不是「未加载书」。

**处理**：改成 `v-if="!rawText"`，仅在未开书时显示。

**教训**：**`v-if` / `v-else` 必须紧邻且语义对应**，中间隔了别的条件组件就会错绑。这类布局缺陷只有真实窗口交互才能暴露，纯构建通过不了。

### 坑 5-5：PanoramaPanel.vue 死代码

**现象**：TS6133（rangeTo / foreshadowList / rangeFrom 未使用）。

**处理**：删除未接线的筛选，`vue-tsc --noEmit` 转 0 错。

## 六、M4.5 全书预处理：幂等与测试隔离坑

M4.5 把情感分析前置到开书时（全书 3366 段 + 120 章一次性入库，阅读时直接吃库）。这个阶段的两个坑都关于「幂等判据」和「测试隔离」，是数据工程的典型暗礁。

### 坑 6-1：章级有记录 ≠ 段落已备，被清空的章永远补不回

**现象**：幂等判据只看章级表（`chapter_emotions` 有行就判定已备），实测第 1 章丢 67 段却不重算。

**根因**：「章级有记录」和「段落已备」是两回事：段落被清空但章级行还在，判据误判为已备。

**处理**：新增 `emotion_lines_by_chapter()` 返回 `{chapter_idx: 段落行数}`，`prepared = {ci for ci,n in ... if n>0}`，todo 里排除已备章。

**教训**：**幂等判据必须校验「真正需要的最小完整度」**，不是「上层聚合表有没有行」。判据太粗 = 数据坏了也不重算。

### 坑 6-2：e2e 测试污染真实数据

**现象**：回归测试把预处理灌入的第 1 章 67 行删了（3366→3299）。

**根因**：测试的往返断言用 `chapter_idx=0` + `save_chapter_emotions(rows=[])` 清场，恰好命中真实 book_id 的数据。

**处理**：测试改用独立测试书 `TID = bid + "-e2e-tmp"`，与真实 book_id 隔离；M4.5 节先跑一次全书 `prepare_book` 补缺，再断言。

**教训**：**回归测试禁止对真实数据做「清场」型断言**。测试数据必须与生产数据用 id 隔离，这是数据工程的底线。

## 七、工具链与工程纪律：贯穿全程的坑

这一节不是功能缺陷，而是「开发过程本身」暴露的坑。它们对后续每一轮都适用。

### 7-1：编辑工具静默失败（最贵的教训）

**现象**：Edit 工具多次报「Successfully edited」，实测没落盘：2026-09-17 一批 4 次编辑 3 次没写入；含全角括号（`（）`）的匹配串静默失败率极高。

**处理**：默认做法升级为「批量改中文文档走 Python 脚本」：`str.replace(old,new,1)` + `assert old in s` + 回读 count 断言。只改一两行且锚点纯 ASCII 时才用编辑工具。

**教训**：**工具的成功回执不等于写入成功，编辑后必须回读验盘**。锚点只用纯 ASCII 片段，避开全角标点；大区块整段替换；编辑后重算围栏配对与 TOC 锚点。

### 7-2：Bash / PowerShell 工具不可靠

**现象**：Bash 工具不稳定（`ls`/`head`/管道常失败）；PowerShell 的 `Add-Type` / `New-Object -ComObject` 被安全策略拦截；PowerShell 工具不回显 stdout；`*>` 重定向默认 UTF-16。

**处理**：跑脚本用绝对路径托管 Python；目录枚举用 PowerShell；校验输出一律「写文件 + Read 工具读」；PowerShell 重定向文件读取前先解码。

### 7-3：pnpm.ps1 截断 stderr

**现象**：PowerShell 把原生 stderr 当 `NativeCommandError` 截断日志，前端构建失败信息丢失。

**处理**：前端校验改用 Python `subprocess` 直接驱动 `node node_modules/vue-tsc/bin/vue-tsc.js --noEmit` 与 `node node_modules/vite/bin/vite.js build`。

### 7-4：GUI 自动化的进程生命周期

**现象**：`pnpm tauri dev` 在工具调用内 20s 出窗口，调用一返回进程即被杀；后台任务也会被后续调用打断。

**处理**：把「起栈 → 交互 → 退栈」全部放在同一次调用内（`app/tools/gui_once.py` 即此模式）；起栈首选已编译的 `target/debug/app.exe` + 自起 vite dev server。

### 7-5：窗口被全屏窗口盖住，点击打偏

**现象**：屏幕上多个近乎全屏的浏览器窗口，点击会打到别的窗口。

**处理**：`SetWindowPos(TOPMOST→NOTOPMOST)` + `AttachThreadInput` + `SetForegroundWindow`，断言 `GetForegroundWindow()==hwnd`；落点用 `WindowFromPoint` + `GetAncestor(GA_ROOT)` 复核。

### 7-6：截图与坐标换算

**现象**：普通截图对被遮挡的 WebView2 无效。

**处理**：`PrintWindow(hwnd, hdc, 2)`（对 WebView2 有效、被遮挡也能取到窗口内容）；空白再回退 BitBlt / 屏幕抓取。坐标换算：`SetProcessDpiAwareness(2)` → `scale = GetDpiForWindow/96`（本机 2.25）→ `ClientToScreen(0,0)` 为原点 → `phys = origin + css*scale`。滚轮正值向上，向下要传 `-120`。

### 7-7：`vite build` 被 node 批量删除保护拦截

**现象**：`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":107,"threshold":50,...}`。vite 清空 `dist/assets`（107 文件）触发阈值，构建失败。

**处理**：先把 `app/dist` 送回收站再构建（该保护是 Node 侧 shim，Python 的删除不受影响）。

### 7-8：删除文件的安全规程

**现象**：`SHFileOperationW` 返回码不可靠（本次返回 2 视为失败但实际成功）；`pFrom` 直接赋 `create_unicode_buffer` 会 TypeError。

**处理**：一律送回收站（`FO_DELETE=3` + `FOF_ALLOWUNDO`），`pFrom` 直接赋 `path + "\0"` 字符串（双 NUL）；**返回码不可信，必须 `os.path.exists` 逐项复核**；删重复文件前先 MD5 校验两份一致。

### 7-9：空目录 ≠ 垃圾

**现象**：把 `分析结果/CSV导出/` 当空目录删了。

**根因**：该目录是 `章节分析归档规范.md` 明确指定的 CSV 导出路径（目录树、输出目标、导出路径共 3 处），属结构性占位目录。

**处理**：`os.makedirs` 复原。

**教训**：**删目录前先 grep 规范文档**，不能只按「空 = 垃圾」判定。规范承诺的输出位置必须保留。

### 7-10：文档多处引用同一事实

**现象**：同一数字（如 `.temp` 体积）出现在 3 处，单点锚点替换会 `count=2` 断言失败。

**处理**：补丁脚本要有「多出现替换（replace_all）」通道；另一处 N12 行先按 N9 锚点插入会落错位，需再补一步移到 N11 之后维持编号顺序。

### 7-11：文档与磁盘必须同口径

**现象**：多次出现「把字节数当词条数」（「91 万」实为 910,438 字节，真值 17,817 词群 / 107,934 词条）；删冗余后文档体积数字失准。

**处理**：凡写数量一律以文件系统实测为准，改完回扫全工程同步，并做算术自洽（资产表各行合计 ≈ 声明总数）。

## 八、打包与体积：M5 的前车之鉴

M5（打得包）尚未开始，但打包阶段的坑已在体积测算阶段提前暴露，提前记录以免再踩。

### 实测体积数据（非估算）

| 项 | 实测 |
|---|---|
| 工程本体（源资产） | 24.58 MB（必须随包的仅 1.3 MB） |
| jieba 安装后 | 40.97 MB（精简后可压到约 20 MB） |
| Python 运行时 | 48.34 MB（裁剪后约 20 MB） |
| B 版全功能（Tauri） | 安装后 132 MB / 安装包约 55 MB |
| Electron 版（对比） | 安装后 326 MB / 安装包约 137 MB |

### 省体积的三个杠杆（按收益排序）

1. 用 ECharts 的 wordcloud 扩展替代 Python `wordcloud` → 省约 70 MB（去掉 numpy + pillow）
2. 精简 jieba（删 lac_small、idf.txt、__pycache__）→ 省约 21 MB
3. 壳用 Tauri 而非 Electron → 省约 194 MB（前提：目标机有 WebView2）

### 打包关键决策（已成约束）

- **onedir 而非 onefile**：onefile 每次启动都要解压几十 MB，首启明显卡顿。
- **不启用 UPX**：拖慢启动且易被杀软误报。
- **Tauri `externalBin` 命名坑**：配置里写不带后缀的名字，实际文件必须带目标三元组后缀 `-x86_64-pc-windows-msvc.exe`，否则构建直接报错。
- **WebView2 用 `downloadBootstrapper`**：切勿用 `embedBootstrapper` / `offlineInstaller`，否则安装包被塞进 100+ MB 运行时。
- **前端 `base: './'`**：WebView2 以 file:// 载入时资源路径必须相对。
- **jieba 瘦身不可逆的代价**：删 `analyse/` 后不得再调 `extract_tags` / `textrank`。

## 九、教训总结：从具体问题到通用原则

把前面所有坑抽象成几条可迁移的原则。这些原则不针对本项目，适用于任何「本地桌面应用 + 数据管道 + 自动化开发」工程。

### 原则 1：内容身份与位置身份分离

`book_id` 掺路径导致一书店多条记录；运行时数据放同步目录导致 EBUSY 与互相覆盖。共同教训：**凡是「识别一个东西」的 key，只能由内容本身决定；凡是「运行时的东西」，都要与源码/同步目录隔离**。判断标准：含本机绝对路径的、带二进制伴随文件的、能重新生成的，都不该进同步目录。

### 原则 2：昂贵的重活必须幂等 + 有可验证的判据

索引重建（108s）、全书预处理（13.6s）、情感落库，所有重活都经历过「重复执行或漏执行」的问题。共同解法：加签名/幂等判据 + 前端「先问再算」。而幂等判据必须校验「真正需要的最小完整度」（段落行数 > 0），不是「上层聚合表有没有行」（M4.5-1）。

### 原则 3：通信协议通道必须纯净，且用测试守住

stdout 是 NDJSON 协议通道，任何 `print` 都是定时炸弹。这类问题肉眼很难发现，必须把「通道纯净性」写成自动回归断言。同理，KNN 的 `v.k = ?`、vec0 不支持 `INSERT OR REPLACE`：**数据库方言约束要靠测试兜底，不能靠记忆**。

### 原则 4：跨系统的编号与口径永远不能想当然

报告段落号 ≠ 物理行号；tone 有 56 种写法；`v-if`/`v-else` 错绑；`JSON 里数字的进制/单位`。凡是「两套系统对接」处，要么做归一（tone → 4 类）、要么做降级（三级锚点）并诚实标注精度。**不假装精确**，比「看起来精确」更能赢得信任。

### 原则 5：回归测试必须隔离真实数据

e2e 测试污染真实数据（M4.5-2）：测试数据必须用独立 id（`bid + "-e2e-tmp"`），禁止对真实 book_id 做「清场」型断言。这条应上升为数据工程的底线规则。

### 原则 6：开发工具本身也要怀疑

编辑工具报 success 却没落盘（4 次 3 次失效）、PowerShell 不回显 stdout、pnpm.ps1 截断 stderr、Bash 管道失败、`vite build` 被删除保护拦截。共同教训：**工具的成功回执、工具的输出通道，都要以「实际落盘/实际输出」为准来校验**。批量改中文文档走脚本 + 断言 + 回读，是这个项目最省心的编辑姿势。

### 原则 7：数字只信实测，口径随变随改

模型体积 47 → 90.4 MB、磁盘占用 181.6 MiB、jieba 40.97 MB、词条 91 万 → 17,817 词群。所有「装后占用」「资产规模」类数字都必须重测。文档改完要回扫全工程同步（同一数字多处出现时用 replace_all），并做算术自洽。

### 原则 8：外部依赖的错误要翻译成人话

LLM 401 不能抛原始 SDK 报文；镜像源超时要有切换方案（hf-mirror / 清华 pip）。外部服务故障要按状态码分类给「用户能行动」的提示，并把「外部凭据缺失」与「代码缺陷」明确区分（本项目的 401 是唯一非代码问题，靠 Key 就能解决）。
