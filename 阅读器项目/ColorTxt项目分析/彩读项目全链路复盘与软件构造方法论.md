# 彩读（ColorTxt）项目全链路复盘与软件构造方法论

> 复盘对象：ColorTxt（彩读）开源阅读器的功能架构、test1.xlsm（VBA 版小说分析工具）、以及 Excel/VSTO/Python/Electron 四条实现路径的评估结论。本文把"要做什么、选哪条路、怎么做、踩了什么坑、怎么填坑"串成一条可复用的软件构造链路。

---

## 一、项目定位与目标

彩读的原始诉求是一句话：做一款"会给小说内容上色"的本地 TXT 阅读器。这句话里藏着两个容易忽略的关键约束。

其一，"上色"不是装饰，而是核心卖点——它要求对任意文本做字符级高亮，且高亮词由用户自定义。这决定了整个项目的技术地基必须是"带语法高亮能力的编辑器内核"，而不是普通的文本框。

其二，"本地阅读器"意味着数据留在用户机器上、离线可用、能读大文件，这又把编码识别、大文件内存、格式转换、跨设备同步等问题全部牵扯了进来。

围绕这两个约束，需求被逐步扩展成一个约 16 项核心功能的清单，可以归入五个能力域。

| 能力域 | 功能 | 说明 |
|--------|------|------|
| 文件管理 | TXT/MD 阅读、目录递归、电子书转换、书包导入导出、WebDAV 同步 | 解决"能读什么、怎么带进应用" |
| 阅读核心 | 内容上色、章节识别、划线笔记、书签进度、简繁/全半角互转、主题切换、查找、编辑 | 解决"读起来舒服、能定位、能标注" |
| AI 能力 | AI 对话、RAG 向量检索、角色卡、文生图、智能排版、思维导图、词云 | 解决"读懂剧情、辅助分析" |
| 语音朗读 | 6 种 TTS 引擎、多音色、AI 说话人识别 | 解决"不想看的时候能听" |
| 书源找书 | Legado 兼容引擎、搜索/发现/详情/在线阅读/整书下载 | 解决"书从哪来" |

从需求结构化角度看，这 16 项并非同一优先级。可以按"必须闭环、锦上添花、前沿探索"三层切分：

- 核心闭环：文件导入 → 编码识别 → 章节识别 → 内容上色 → 目录跳转 → 书签进度。没有这一层，产品不成立。
- 扩展能力：简繁互转、语音朗读、划线笔记、主题、电子书转换、定时滚动。它们让体验完整，但缺了不致命。
- 前沿探索：AI 对话与 RAG、文生图、角色卡、智能排版、Legado 书源找书、WebDAV 同步。这些是差异化，但开发成本最高，风险也集中于此。

这份三层切分，就是后续"路径选择"与"迭代节奏"的原材料：先验证核心闭环里最不确定的那一块，再决定要不要投入全部功能。

## 二、路径选择：四条路与一条决策主线

项目先后评估了四条实现路径，而不是一开始就锁定某一技术。这正是值得复盘的地方——选型是一个"逐条排除"的过程，排除标准不是技术潮流，而是**产品形态与技术范式是否匹配**。

### 四条候选路径

| 方案 | 技术载体 | 上色体验 | AI 能力 | 开发成本 | 适用场景 |
|------|---------|:---:|:---:|:---:|------|
| A. 纯 xlsm | VBA + Excel 单元格 | 差 | 极有限 | 低 | 文本分析、章节提取等数据处理 |
| B. VSTO + Excel | C# + 单元格 | 一般 | 部分 | 中 | 需要 Excel 数据交互 + 部分 AI |
| C. VSTO + 任务窗格 | C# + WPF/WebBrowser | 好 | 完整 | 高 | 强留在 Excel 里复刻阅读器 |
| D. 独立应用 | Electron/Vue 或 Python/PyQt | 好 | 完整 | 中高 | 目标是做真正的阅读器 |

### 决策的主线：范式冲突

排除 A、B 的真正理由不是"VBA 语法旧"，而是一条更深的问题：Excel 的单元格模型是"二维离散表格"，而连续文本阅读是"一维连续流"。两种范式在"细粒度、可滚动、高性能"的文本渲染上不可调和。

这条冲突在"内容上色"上暴露得最彻底。VBA 里给字符上色唯一的手段是 `Range.Characters(start, length).Font.Color`——每个子串一次 COM 调用，10 万字可能要数万次调用，耗时 3 到 10 分钟。这不是"优化不够"，是宿主模型从根上就不支持这件事。换到 VSTO + WPF 的 `FlowDocument` 可以改善，但仍需自己实现 tokenizer，且受制于 Excel 进程的稳定性。

于是评估进入一个被文档点破的"方案 C 悖论"：为了复刻阅读器，VSTO 方案不得不在任务窗格里嵌一个 WebBrowser，把真正的阅读逻辑全部塞进浏览器——此时 Excel 只剩一个外壳，那为什么不直接做一个独立应用？结论倒过来：**独立应用（Electron/Tauri 或 Python/PyQt）才是与产品形态同构的技术选择**，Excel 只适合做"文本分析助手"，不适合做"阅读器"。

### 两个落地方向的分工

确定"独立应用"后，项目内部其实有两个平行的落地方向：

- 参考实现：ColorTxt 本身走的是 Electron 35 + Vue 3.5 + TypeScript 5.8，Monaco Editor 作内核，这是"要什么功能、怎么架构"的标杆。
- 迁移落地方案：用户自己的 test1.xlsm（约 80 个 VBA 模块）要走"VBA → Python/PyQt6"的迁移路线，这是"旧资产如何重生"的具体执行。

两条线共享同一批需求，却在技术栈上各走各的，最终都能收敛到"独立应用 + 强编辑器内核"这一判断上。

## 三、实现方式：技术栈与关键方法

### 3.1 参考实现的技术栈

ColorTxt 的选型围绕一个原则：把最重、最专业的活交给成熟的第三方内核，自己只做业务编排。

| 层面 | 选型 | 承担的角色 |
|------|------|-----------|
| 框架 | Electron 35 + Vue 3.5 + TypeScript 5.8 | 桌面三端承载 + 组件化 UI |
| 编辑器内核 | Monaco Editor | 上色、查找、编辑、Diff 预览的统一底座 |
| 数据库 | better-sqlite3 + sqlite-vec | 结构化存储 + 向量检索 |
| AI 推理 | @huggingface/transformers | Worker 线程本地跑嵌入模型 |
| 中文处理 | @node-rs/jieba、OpenCC | 分词、简繁转换 |
| 编码检测 | jschardet + iconv-lite | 编码探测与解码 |
| 打包发布 | electron-builder + GitHub Actions | 三端并行构建 |

### 3.2 分层架构

参考实现采用 Electron 的四层划分，这一划分在 Python 方案里被等价地保留了下来——它们是同一种"关注点分离"思路的两处投影。

参考实现（Electron）：主进程（文件系统、AI 引擎、TTS、书源、自动更新）→ 预加载层（contextBridge 暴露安全 API）→ 渲染进程（Vue 组件、Monaco 阅读视图）→ 共享层（类型与 IPC 通道声明）。

Python 方案（迁移落地）：`core/`（无 GUI 依赖的业务逻辑：导入、章节、查询、分析、EPUB）→ `gui/`（窗口、视图、控件、对话框）→ `models/`（数据模型）→ `utils/`（工具）。两者的共性是把"能脱离界面独立测试的业务逻辑"与"界面层"彻底隔开。

### 3.3 四个关键方法的实现

**内容上色**——用编辑器内核的 tokenizer 机制，而非手写逐字符着色。把用户自定义高亮词注册为语言的 token 规则，Monaco 依据 token 类型套用主题颜色。Python 侧用 Qt 的 `QSyntaxHighlighter` 做同样的事：C++ 底层一次扫描即可完成全部着色，`highlightBlock` 只负责声明"哪些词配哪个格式"。这正是"性能重设计"的典型——删除慢的根因（逐个子串的 COM 调用），换成引擎底层的批量机制。

**编码识别**——三级策略：先看文件头 BOM，再用 jschardet 统计检测，最后针对中文环境用 ANSI 启发式补判断（GBK/GB2312）。Python 侧用 chardet 直接替代手写的 BOM + 启发式。大文件则用流式按块读取，避免一次性加载撑爆内存。

**RAG 向量检索**——把正文按章节分块，用本地嵌入模型（BGE Small ZH v1.5，约 47MB、512 维）在 Worker 线程生成向量，写入 sqlite-vec；提问时同样嵌入查询向量、取 TopK 相似块拼成上下文再喂给模型。全程离线，兼顾隐私与零外部成本，同时保留"远程嵌入 API"作为第二种模式。

**书源找书（Legado 引擎）**——这是复杂度最高的模块，做法不是调库，而是用 TypeScript 在主进程复刻 Legado 的完整解析链路（AnalyzeRule、AnalyzeUrl、jsExtensions、章节缓存），从而直接兼容 legado-E 的书源 JSON 生态。它的投入极大（数百 commits），但换来了对现成书源生态的零迁移成本复用。

## 四、遇到的问题与处理方式

这一节把踩过的坑按"问题 → 根因 → 处理 → 结果"整理成一张表。理解根因比记住方案更重要，因为方案会随技术栈变，根因不会。

| 问题 | 根因 | 处理方式 | 结果 |
|------|------|---------|------|
| 字符上色极慢（3-10 分钟 / 10 万字） | 每个子串一次 COM 调用，宿主模型不支持高效着色 | 换成编辑器内核的 tokenizer（Monaco / QSyntaxHighlighter） | 降到 0.5 秒内，提升百倍 |
| Excel 复刻阅读器不现实 | 单元格（二维离散）与连续文本（一维流）范式冲突 | 放弃 Excel 作宿主，改独立应用 | 上色、滚动、AI 能力全部解锁 |
| 大文件撑爆内存 | 一次性读入整个文件 | 流式按 chunk 读取 | 大文件可稳定打开 |
| 编码识别不准 | 单靠 BOM 或单靠启发式都不稳 | 三级策略：BOM → 统计检测 → 中文 ANSI 启发式 | 中英文编码识别更可靠 |
| 原生模块在 Electron 下失效 | Node ABI 与 Electron ABI 不一致 | electron-rebuild 重编译；asarUnpack 解出 .node 与词典；createRequire 加载 external 模块 | 原生模块正常运行 |
| API 密钥明文落地 | 密钥散落在配置文件与 localStorage | 独立加密保险库 secrets.v1.json，按功能分槽，串行队列 + 原子落盘 | localStorage 与配置零明文 |
| VBA 生态缺电子书解析库 | VBA 无 epub/mobi/chm 库 | 参考实现用 foliate-js/libmspack；C# 用 VersOne.Epub/PdfPig；Python 用 ebooklib + beautifulsoup4 | 各栈都有纯库替代 |
| Legado 引擎复杂度高 | 规则解析 + JS 扩展 + 缓存一整套 | 主进程 TS 复刻全链路 | 直接复用现有书源生态 |
| 安装包体积过大 | node_modules 含大量无用文件 | 打包前用脚本裁剪（去 source map、README、非目标平台原生包） | 包体显著缩小 |
| 迁移旧 VBA 成本高 | 概念、API、性能模型全变 | 先做概念映射表，再语义等价重写，不逐行翻译 | 迁移可控、可并行推进 |

从这张表能提炼出三条处理模式的共性：**慢的问题换底层机制，缺的问题找生态等价物，险的问题（密钥、隐私）走隔离与默认安全**。三类问题的解法思路不同，但都要求先定位根因再动手。

## 五、方法论：一套可复用的软件构造流程

把上面的复盘抽象成六步，构成一条"从模糊想法到可交付软件"的通用链路。它不依赖具体语言，Electron 和 PyQt 都走通了它。

### 第一步：需求结构化

把一句模糊愿望拆成"能力域 → 功能 → 输入/处理/输出"三级清单，再按"核心闭环 / 扩展 / 探索"分层排序。判断标准是：缺了它产品是否成立？成本是否集中？这一步的产出不是文档，而是**一张带优先级的可验收功能表**。

### 第二步：范式匹配选型

先回答"产品形态属于什么范式"（连续流、二维表、看板、流媒体……），再判断候选技术是否同构。用能力矩阵逐功能打分：可完整实现、可部分实现、无法实现。选型的否决项应来自范式冲突和生态缺失，而不是语法新旧或个人偏好。

### 第三步：风险前置验证

在做全量功能前，先挑出"最关键、最不确定"的那一个点做一个最小原型。本项目的这个点是字符级上色——它决定了整个技术栈的地基选型。核心风险点验证通过，才值得投入后续的 AI、TTS、书源等重头戏。

### 第四步：分层架构

把"能脱离界面独立测试的业务逻辑"与"界面层"隔开，再叠一层平台适配（文件系统、原生模块、系统快捷键）。Electron 的三进程就是这种隔离的极端形态；Python 的 `core/gui/models/utils` 是它的平实版本。好处是一致的：核心逻辑可单测、可复用、换壳成本低。

### 第五步：增量迭代

按"先核心闭环，后扩展，最后探索"的顺序推进，每一步都有量化验收标准。例如先交付"文件导入 → 章节识别 → 上色 → 目录跳转"这个最小可用的闭环，再逐块叠加字频分析、语音朗读、AI 问答。每走一步都在验证，而非最后一次性拼装。

### 第六步：迁移三原则

当从旧资产迁移到新栈时（这里是 VBA → Python），记住三件事：

- 概念映射：先建一张"旧概念 → 新概念"对照表（如 `Characters.Font.Color` → `QTextCharFormat.setForeground`），迁移前先对齐心智模型。
- 性能重设计：不是逐行翻译，而是找到旧实现慢的根因，换一套底层高效的机制。`QSyntaxHighlighter` 替代逐子串着色就是范例。
- 生态补位：旧生态缺什么库，就在新生态找等价物，而不是硬着头皮自己造。

三者合起来一句话：**迁移是对旧实现的语义等价重写，而不是语法转录。** 只做语法转录的迁移，会把旧实现的性能债原封不动地搬进新家。

## 六、决策陷阱与经验教训

三条最值得记住的判断，每条都曾在项目里真实出现过。

**"留在熟悉宿主"的路径依赖，会产生套壳悖论。** 死守 Excel 的结果是 VSTO + WebBrowser 这种"外壳 + 引擎"的畸形结构——外壳什么都没做，引擎其实已是一个独立应用。与其绕这么大一圈，不如一开始就承认"该换宿主了"。

**性能问题不要用"优化"去补，要用"换机制"去解。** 逐子串 COM 调用慢上千倍，任何 VBA 层面的微调都救不回来。先确认慢的根因是机制性的，就直接换底层机制，省下无效的优化时间。

**迁移最大的风险不是技术，是"逐行翻译"的惯性。** 守住"概念映射 + 性能重设计 + 生态补位"三原则，迁移才能带走旧资产的价值、甩掉旧资产的包袱。反之，逐行照搬只会得到一份"换了语法、原样保留的烂代码"。

---

## 七、一句话总结

彩读项目从"给小说上色"这个朴素愿望出发，在需求分层后，用"范式匹配"排除了 Excel 宿主、锁定了独立应用的方向，靠"强编辑器内核 + 成熟第三方库 + 分层架构 + 增量迭代"把 16 项功能落地，再用"换机制、找等价物、默认安全"三类手段把路上的坑逐一填平。这条"结构化需求 → 范式选型 → 风险前置 → 分层 → 增量 → 迁移三原则"的链路，就是可以从它身上直接搬走的软件构造方法论。
