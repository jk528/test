## 二、站点与订阅形式（第 1 步：摸清站点）

`https://shuyuan.yiove.com/` 是一个 **Vue SPA + Cloudflare** 的书源分享站，页面本身只是一个壳（2,090 字节 HTML），真正的数据走独立 API 域 `shuyuan-api.yiove.com`（FastAPI）。

站点提供 4 种导入链接，注意**网页域名下的链接是给 SPA 路由用的，curl 拿到的是 HTML，不能直接给 reader 当订阅用**：

| 形式 | 地址 | 实际返回 |
| --- | --- | --- |
| 合集（推荐） | `https://shuyuan.yiove.com/import/book-source-collection/<uuid>` | 200 / 2,090 字节 `text/html` → **SPA 壳，不是 JSON** |
| 单源 | `https://shuyuan.yiove.com/import/book-source/<uuid>` | 200 / 2,090 字节 `text/html` → 同样是壳 |
| 合集（API 直链） | `https://shuyuan-api.yiove.com/import/book-source-collection/<uuid>` | **200 / 1,667,636 字节 `application/json`，标准 bookSource 数组** |
| 单源（API 直链） | `https://shuyuan-api.yiove.com/import/book-source/<uuid>` | **200 / 148,685 字节 `application/json`** |

> 关键坑：网页端“导入到阅读”按钮是前端拦截后自己调 API 的，所以复制网页链接丢给 reader 会拿到 HTML 而失败。要跨机器导入，必须用 **`shuyuan-api.yiove.com`** 的 `/import/...` 直链。

本次使用的合集：`已效验书源383个`（uuid `b8fd3e19-08dd-4f05-a7b4-d6cc909de8e6`）。
其他可浏览的资源列表接口（用于挑选合集）：`https://shuyuan-api.yiove.com/shuyuan/book-sources?page=1`、`https://shuyuan-api.yiove.com/shuyuan/book-source-collections?page=1`。

**参数要求**：无导入口令、无邀请码、无需登录、无 Referer/UA 校验、无时效签名（实测 3 个月后仍为同一 UUID 可访问）。唯一要求是能访问 Cloudflare 的 IPv4/IPv6。

## 四、导入步骤（第 3 步）

reader 没有 `/reader3/importBookSource` 这个路由，等价接口是 **`POST /reader3/saveBookSources`**（body 为 bookSource 数组）。该接口**只带 `secureKey` 会报「请登录后使用」**，必须先用账号换 `accessToken`。

> 安全约定：下文用 `<secureKey>`、`<用户名>`、`<密码>` 占位，真实值见服务器 `users.json` / 部署时设定，不写入本文档。

### 4.1 导入前记录数量

```bash
# 注意 getBookSources 必须是 GET（POST 空 body 会 NullPointerException）
curl -s 'http://127.0.0.1:8080/reader3/getBookSources?accessToken=<token>' \
  | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{const j=JSON.parse(s);console.log("sources",j.data.length)})'
```

### 4.2 登录换 token

```bash
TOKEN=$(curl -s -X POST 'http://127.0.0.1:8080/reader3/login' \
  -H 'Content-Type: application/json' \
  -d '{"username":"<用户名>","password":"<密码>","isLogin":true}' \
  | node -e 'let s="";process.stdin.on("data",d=>s+=d).on("end",()=>{console.log(JSON.parse(s).data.accessToken)})')
```

### 4.3 下载书源 JSON 并导入

```bash
curl -sS --max-time 90 -o /tmp/coll-src.json \
  'https://shuyuan-api.yiove.com/import/book-source-collection/b8fd3e19-08dd-4f05-a7b4-d6cc909de8e6'

curl -sS -X POST "http://127.0.0.1:8080/reader3/saveBookSources?accessToken=$TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @/tmp/coll-src.json
# 返回示例：{"isSuccess":true,"errorMsg":"","data":"新增283条书源，更新100条书源。"}
```

### 4.4 用户书源上限（重要）

reader 有**用户级书源上限**，默认 **100**。首次导入只进了 100 条，返回「你已达到书源数上限」。处理方式（**只在容器内改数据文件，不动系统配置**）：

```bash
docker stop reader
cp /opt/reader/storage/data/users.json /opt/reader/storage/data/users.json.bak-$(date +%Y%m%d%H%M%S)
node -e 'const f="/opt/reader/storage/data/users.json";const fs=require("fs");
  const j=JSON.parse(fs.readFileSync(f,"utf8"));const u=Object.values(j).flat?j:j;
  console.log("before", JSON.stringify(u).match(/"book_source_limit":\d+/g));'
# 用编辑器把目标用户的 "book_source_limit":100 改为 500（或需要的值）
docker start reader && sleep 20 && curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
```

> 若 `users.json` 被加密/校验导致改后登录异常，可改用管理员接口 `POST /reader3/resetPassword`（需 secureKey）重置口令后继续，不必手改文件。
> 本次操作前已备份，回滚：`cp users.json.bak-<时间戳> users.json` 后重启容器。

## 六、资源占用与精简建议（第 5 步）

实测（宿主机 1.7G，容器上限 640MiB）：

```
导入前              reader  159.3 MiB
导入 383 条后        reader  189.5 MiB
全量搜索结束后       reader  355.4 MiB / 640 MiB   (峰值，JVM 未回落)
宿主机               total 1775  used 950  free 115  buff/cache 902  available 824 MB
```

- **内存**：搜索会让 JVM 堆明显上涨（+166MiB），当前 355MiB 仍有余量，但离 640MiB 上限只剩 45%，宿主机 available 已从 963MB 降到 824MB。**保持观察，不要再叠加全量扫描。**
- **耗时**：首页批次约 0.2 秒（体验无感）；全量扫描 44 秒（其中 3 次明显卡在慢源上：第 4–5 轮各约 5 秒、第 11 轮约 19 秒）。

建议（按性价比排序）：

1. **`concurrentCount` 不要盲目降低**（前端默认就是 4，24 只是测试脚本参数）。实测降低并发并不会变快，反而因为“每轮都要等最慢的源”而更慢，详见第九节。
2. **按分组精简**：`念心 || 小说` 一组就 220 条（57%），可只保留其中实测有命中的几条；`发现规则为空` 15 条、`已校验,@小说,搜索目录失效,常规模式`、`发现失效,搜索失效`、`网站失效` 这类名字已自曝失效的，直接停用。
3. **不要做“全源扫描”式验证**——44 秒 + 166MiB 内存，一次就够，重复跑既慢又容易触发对方风控。
4. 若内存逼近 500MiB：先停用 `念心 || 小说` 组，再重启容器释放堆；仍不够则把书源总量控制在 150–200 条。
5. 漫画源（`漫画 书源` 6 + `正版漫画 书源` 4）对文字阅读无贡献，可整组停用。

### 9.2 ⚠️ 关键发现：`enabled=false` 不影响搜索

实测确认：把 361 条置为 `enabled=false` 并重启容器后，`/reader3/searchBookMulti` **仍然会扫描这些源**
（`lastIndex` 依旧从 0 递增到 383 才结束；返回结果里还出现了 `中文书城（优+）`、`海词词典（优）` 等已被禁用源的名字）。

- 该版本的 `enabled` 只在 API 数据层存在，前端 bundle 里**没有「启用/停用」的 UI 文案**，搜索服务也没读这个字段。
- 因此**真正能让搜索变快的开关是 `bookSourceGroup`（分组）**，不是 `enabled`。
  实测 `bookSourceGroup="🎉 精选"` 时只扫描该组 5 条、`"正版小说 书源"` 只扫描 12 条。

所以本次的做法是双保险：

1. 361 条置 `enabled=false`（标记意图，若后续版本修复该行为则自动生效）；
2. 保留的 20 条追加 `✅精简` 分组（**原分组不覆盖，逗号追加**），搜索时在搜索框的「书源分组」里选 `✅精简` 即为 20 源极速模式。

> 默认（不选分组）仍然是全量 383 源，约 44 秒。若要让默认搜索也变快，只能**真删**（见 9.5）。

### 9.4 并发数实测（20 源、`✅精简` 分组）

| 词 | c=24 | c=8 | c=4（22 源时测得，含两个慢源） |
| --- | --- | --- | --- |
| 红楼梦 | 1.65 s / 127 条 / 11 源 | 3.68 s / 84 条 / 7 源 | 63.9 s / 109 条 / 5 源 |
| 诡秘之主 | 1.95 s / 61 条 / 8 源 | 1.86 s / 36 条 / 3 源 | 40.5 s / — |
| 斗破苍穹 | 1.65 s / 117 条 / 10 源 | 0.49 s / 22 条 / 3 源 | 11.9 s / — |

结论：**降低并发不会更快**。多源搜索按批推进，每批要等该批最慢的源，批越小轮次越多、总墙钟时间越长；同时批内并发低时部分站点会返回更少结果。
前端默认 `concurrentCount=4`，建议保持 4（稳）或调到 8–12（快），不要再回到“全量 383 源 + 任意并发”。
