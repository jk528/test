> **技术栈**：Electron 35 + Vue 3 + Monaco Editor + TypeScript
> **报告日期**：2026-10-18
> **数据来源**：彩读分析目录 20 份 MD 文件 + GitHub 仓库 + 万维读书计划

## 一、核心结论：一个人如何 5 个月造出 1.7k Star 软件

彩读作者从「在 VS Code 里看小说」的体验出发，5 个月内交付 24 个版本、跨 3 平台 5 架构的桌面应用，其成功可复制的核心公式是：

```
高质量软件 = (清晰定位 × 积木式架构) + (小步快跑 × 发布即公告) + (补丁优先 × 兼容不复制) + (全链路自动化 × 诚实风险声明)
```

这不是天才叙事，而是一套**可学习、可复刻的工程工作流**。本报告将其拆解为「从零开始的心法」「高质量工作流的技法」「GitHub 打包同步的战法」三层。

## 二、从零开始：立项前的 7 个关键决策

彩读在写第一行业务代码前，先完成了以下决策，这些决策决定了后续 5 个月能否高速迭代。

### 2.1 灵感锚定：从体验痛点到产品定位

| 步骤 | 彩读的做法 | 可学习点 |
|------|-----------|---------|
| 发现痛点 | 在 VS Code 里看小说，发现代码高亮体验可移植到网文 | 从自己真实使用场景出发，不造伪需求 |
| 找到轮子 | 发现插件 vscode-txt-syntax 的语法高亮可复用 | 先找现成方案，确认"差最后一公里"再立项 |
| 一句话定位 | "一款会给内容上色的本地 TXT 小说阅读器" | 定位要能一句话说清，且含核心差异点 |

### 2.2 技术选型：选成熟内核而非自造

| 选型 | 彩读的选择 | 选型理由 | 反例（不选的原因） |
|------|-----------|---------|-------------------|
| 桌面壳 | Electron 35 | 跨平台 + Node 生态 + Chromium 渲染 | Tauri 更轻但生态当时不够 |
| UI 框架 | Vue 3 组合式 API | 响应式、轻量、composable 易拆 | React 在桌面端无额外优势 |
| 编辑器内核 | Monaco（VS Code 内核） | 百万行级性能 + 行列模型 + 装饰器体系 | 富文本 div 做不了大文件 |
| 类型系统 | TypeScript 全栈 | 主进程/渲染/共享层统一类型 | JS 在多进程项目维护成本高 |
| 构建工具 | electron-vite | 统一三端构建 + HMR | 手配 webpack 维护成本高 |

**核心原则**：每个选型都选「最成熟 + 生态最厚」的方案，把创新留给业务层。

### 2.3 架构分层：积木式拆分

```
┌─────────────────────────────────────────────────┐
│  Main 主进程    │  Preload 预加载  │  Renderer 渲染 │
│  (系统侧能力)    │  (contextBridge) │  (Vue 组件树)   │
│  IPC/文件IO/AI  │   contextIsolation │  Monaco/Store  │
└─────────────────────────────────────────────────┘
│              Shared 共享层（类型/常量/通道）          │
```

**积木式设计要点**：
- 多窗口 = 多个独立积木块，共用 BrowserWindow 工厂，通过参数区分入口 HTML
- 每个窗口可单独创建、组合使用、互不干扰
- Preload 只做一件事：把 IPC 包装为 `window.colorTxt.*` API
- `contextIsolation: true` + `nodeIntegration: false`，无直接 Node 暴露

### 2.4 范围控制：首发只做一件事

彩读 v1.0.1（2026-04-04）的 release 正文仅一句话："支持空格键跳转到下一屏"。

| 控制维度 | 做法 | 反例 |
|----------|------|------|
| 范围 | 首发一个核心功能 | 堆砌十个半成品功能 |
| 架构 | 1.0 即采用 Monaco | 先用 div 后期再换内核 |
| 包体 | 剔除语言包 + 启用 asar | 不管体积任其膨胀 |
| 节奏 | 每版聚焦 2-4 个功能点 | 一版塞一个子系统 |

### 2.5 存储分层：四层积木

```
层级1: localStorage       → UI 偏好、会话快照、文件列表
层级2: userData JSON 文件  → 窗口位置、AI 配置、密钥保险库
层级3: SQLite (better-sqlite3) → 向量索引、AI 对话、书源数据
层级4: 模型缓存目录         → 内置嵌入模型权重
```

### 2.6 安全基线：从第一天就考虑

密钥存储三阶段演进（可学习的是"逐步收紧"的节奏）：
```
明文 config.json (≤2.2) → 系统钥匙串 (2.3) → 保险库 secrets.v1.json 分槽 (多方案后)
```
- 串行队列 + tmp→rename 原子替换
- 密钥与配置分离，config.json 不含明文 Key

### 2.7 开源协议与发布制度

| 决策 | 彩读的做法 |
|------|-----------|
| 协议 | MPL-2.0（允许商用但需公开修改文件） |
| CHANGELOG | 与 release 正文同源同步，每个版本前有 "Update CHANGELOG.md" 提交 |
| issue 回链 | release 说明逐条回链 issue 编号 |

## 三、高质量开发工作流：彩读的 10 条控制哲学

这 10 条是从彩读 5 个月迭代中提炼的可复用工作流，每条都有事实支撑。

### 3.1 发布即公告

24 个 release 全部带结构化中文说明（新功能/改进/修复），issue 编号直接回链。CHANGELOG.md 与 release 正文同源同步。

**可学习点**：把每次发布当作一次产品宣讲，而非技术流水账。

### 3.2 小步快跑

| 阶段 | 节奏 | 每版功能点 |
|------|------|-----------|
| 1.x | 每 5-11 天一版 | 2-4 个 |
| 2.x | 每 3-7 天一版 | 聚焦一个子系统 |
| 3.x 高产期 | 每 3.7 天一版 | — |

**可学习点**：小版本高频发布 > 大版本低频发布。小版本容易回滚、容易验证、容易保持心流。

### 3.3 补丁优先于替换

面对 Monaco 的中文排版短板，作者没有换内核，而是建立 **Vite transform 改写 + 运行时补丁** 的双层体系，解决了中文换行、段间距、左右边距、粘性标题等问题。上游无解问题（#5311）以 WARNING 明示，不掩盖。

**可学习点**：成熟内核的短板用补丁层解决，而非换内核。换内核的成本是补丁的 100 倍。

### 3.4 兼容而不复制

| 兼容对象 | 做法 |
|----------|------|
| Legado 书源 JSON | TypeScript 复刻规则引擎，不引入 Java/Rhino |
| CHM 格式 | 移植 libmspack 为 JavaScript 实现 |
| MOBI/EPUB | 参考 foliate-js，集成进自有管线 |

**可学习点**：不造新格式，直接兼容已有生态，但用自己的技术栈重新实现，避免依赖债。

### 3.5 安全边界逐步收紧

密钥从明文 → 钥匙串 → 保险库分槽 + 原子写 + localStorage 剥离，每一步都带旧数据自动迁移与废弃 slot 清除。

**可学习点**：安全不是一步到位的，而是随功能复杂度逐步收紧，但每步都要有迁移方案。

### 3.6 平台坑清单化

跨平台桌面应用的系统级问题全部进入版本说明与文档，不掩盖：

| 平台 | 问题 | 解决方案 |
|------|------|----------|
| macOS Intel | 交叉编译缺原生包 | 改用原生构建 |
| Linux | AppImage 缺 FUSE2 | 静态 AppImage runtime |
| Windows | NSIS 清空安装丢数据 | 改为覆盖安装 |
| Windows | 任务栏 Z 序压摸鱼窗 | 重申置顶 + 周期兜底 |

**可学习点**：平台坑是跨平台应用的必修课，清单化 + 文档化比假装不存在更专业。

### 3.7 issue 驱动的公开开发闭环

5 个月近百个 issue/PR，大量 issue 直接成为版本主线（#50 摸鱼、#58 极简、#83 阅读尺），release 说明逐条回链。

**可学习点**：把 issue 当作需求池，按需求池排期，让用户看到自己的反馈被采纳。

### 3.8 诚实的风险声明

- "做不到 100% 复刻……目前算是测试版"（v3.0 书源）
- "请自行测试"（v2.5 AI 智能排版）
- "这个问题连 VSCode 都没能完美解决"（README 高级换行策略）

**可学习点**：诚实声明局限性比假装全能更能建立信任。

### 3.9 格式策略两次收敛

电子书中间格式从私有标记收敛到标准 Markdown，Markdown 解析从手写正则收敛到 marked。**"私有方案活得越久，迁移成本越高"**——作者两次都在私有方案扩散前完成了切换。

**可学习点**：私有方案是技术债，越早切换成本越低。标准格式 > 私有格式。

### 3.10 三次"降级即升级"

| 关闭的特性 | 动机 |
|-----------|------|
| 禁用 Monaco 大文件优化 | 为软换行/粘性标题让路 |
| 关闭等宽渲染优化 | 字体保真 |
| 关闭圆角选区抠图 | 透明背景下不露馅 |

**可学习点**：关掉通用优化以服务特定场景，不是退步而是升级——关键是明确服务哪个场景。

## 四、全链路自动化体系：从开发到发布

彩读 5 个月完成 24 版本 × 5 架构的交付，背后是三层自动化。

### 4.1 项目拆积木：postinstall 补丁体系

```json
{
  "postinstall": "electron-rebuild -f -w better-sqlite3,opencc && node scripts/patch-nested-sharp-stub.mjs && node scripts/patch-monaco-hover-pointer-below.mjs && node scripts/patch-vite-plugin-monaco-rmdir.mjs && node scripts/patch-xpath-following.mjs"
}
```

每次 `npm install` 后自动执行 5 个补丁脚本，无需人工干预。每个补丁脚本遵循**幂等+安全**设计模式：

```
1. 检查目标文件是否存在 → 不存在则 warn + exit(0)
2. 检查是否已打过补丁（marker 注释）→ 已打则 exit(0)
3. 精确匹配 needle → 匹配失败则 warn"结构已变" + exit(0)
4. 字符串替换写入 → 打印成功日志
```

### 4.2 运行时积木：Vite transform 插件

4 个 Vite 插件在构建时自动改写 Monaco 源码（中文换行、段间距、pdfjs 资源）。关键设计：`optimizeDeps.exclude: ["monaco-editor"]` 确保开发模式补丁也生效。

### 4.3 CI/CD：GitHub Actions 五架构并行

```yaml
on:
  push:
    tags: ["v*"]          # 推送 v 开头的 tag 自动触发
```

| 平台 | 架构 | Runner | 产物 |
|------|------|--------|------|
| Windows | x64 | windows-2025-vs2026 | NSIS + Portable |
| macOS | arm64 | macos-latest | DMG |
| macOS | x64 | macos-15-intel（原生 Intel） | DMG |
| Linux | arm64 | ubuntu-24.04-arm | AppImage |
| Linux | x64 | ubuntu-latest | AppImage |

**发布流程（开发者视角）**：
```bash
git commit -a -m "修改了xxx"
npm version patch|minor|major    # 自动改 package.json + 打 tag
git push && git push --tags
# CI 自动完成：5 架构并行构建 → 统一发布到 GitHub Release
```

### 4.4 包体大小自动校验

CI 流水线内置包体回归检测，AppImage 超过 200MB 直接 fail，防止裁剪退化。

### 4.5 调试效率设计

| 命令 | 用途 | 效率设计 |
|------|------|----------|
| `npm run dev` | 全功能热重载 | 三端统一 HMR |
| `npm run dev:find` | 只开找书窗口 | 跳过主窗加载，直接调试目标模块 |
| `npm run typecheck` | 类型检查 | 不产出文件，只检查 |
| `npm run test` | 单元测试 | Node 原生 --test，直接跑 .ts |

## 五、GitHub 打包与同步方案

### 5.1 打包流水线全流程

```
npm run build / npm run release
    ├─ Step 1: electron-vite build       (编译三端 + worker)
    ├─ Step 2: electron-rebuild          (重编译原生 .node)
    ├─ Step 3: prune-pack-deps.mjs       (裁剪 node_modules)
    ├─ Step 4: electron-builder          (打包 NSIS/DMG/AppImage)
    └─ Step 5: --publish always          (上传 GitHub Releases)
```

### 5.2 node_modules 裁剪（体积控制核心）

| 类别 | 被裁剪的内容 | 理由 |
|------|-------------|------|
| 整包移除 | onnxruntime-web、完整 sharp | 不做图像推理 |
| 按平台移除 | 非目标平台的 sqlite-vec-*、@node-rs/jieba-* | 原生包按平台分发 |
| 按路径裁剪 | 各包的 src/、deps/、*.map、README | 非运行时文件 |

### 5.3 同步方案三线并行

| 同步线 | 内容 | 冲突策略 |
|--------|------|----------|
| 主窗配置/书包 | 阅读进度、书签、高亮词、笔记、角色卡 | 一律覆盖 + 增量 |
| 找书窗书架 | 书架数据 | 按内容 hash/mtime |
| 找书窗书源 | 书源列表 | 合并不删本地多出的源 |

### 5.4 书包打包与加密

- **.ctz**：普通 zip 压缩包
- **.ctzx**：加密包，AES-256-GCM + PBKDF2
- 安装时注册文件关联，双击即可打开
- 配色导出复用同一思路（含自定义背景图一起打包）

### 5.5 自动更新

electron-updater + GitHub Releases：
- 多架构更新文件隔离（`latest-${arch}`），避免 arm64/x64 互相覆盖
- 中文文件名规避（artifactName 用 `${name}` 而非 `${productName}`）
- macOS 未签名处理（`CSC_IDENTITY_AUTO_DISCOVERY: false`）

### 5.6 撤销发布

```bash
# 1. 网页端删除 Release 记录
# 2. 删除 tag
git tag -d v1.0.0
git push origin :refs/tags/v1.0.0
```

### 5.7 本地手动发布（CI 降级方案）

```bash
export GH_TOKEN='你的TOKEN'   # 需要 repo 权限
git tag v1.0.0 && git push origin v1.0.0
npm run release               # 只能打当前机器对应平台/架构
```

## 六、问题解决方法论：从彩读的踩坑中学习

### 6.1 推翻/重写是常态

彩读明确推翻过 13 个方案，关键不在不犯错，而在**私有方案扩散前完成切换**：

| 推翻内容 | 动机 |
|----------|------|
| 电子书中间格式 .txt → Markdown | 自造标记无法表达层级/图片/链接 |
| Markdown 解析：手写正则 → marked | 私有解析器边角问题无穷 |
| 加载管线重构 | 大文件体验 |
| 网络：Node/undici → Chromium session.fetch | TLS 指纹被识别拦截 |
| 构建：本地 → CI | 跨平台打包 |

### 6.2 新功能带来新问题

| 新功能 | 引发的连锁修复 | 时间跨度 |
|--------|---------------|----------|
| 背景图（v3.8） | 粘性标题阴影切开背景图、圆角选区抠图露底、堆叠粘性标题修复 | 两周内 4 个 fix |
| 摸鱼模式（v3.8） | 定时滚动、最小窗高 setShape、任务栏 Z 序大战、拖动越拖越大 | 11 天 11 个版本 |

**可学习点**：新功能引入后预留 1-2 周的"救火期"，这是正常的，不是规划失败。

### 6.3 章节正则五次事故的教训

彩读章节正则经历 5 次事故（123 回误判 → 109 章漏配 → 标题残缺 → 缺第字 → 持久化未升级），核心教训：

| 教训 | 说明 |
|------|------|
| 字符类要双收形近字符 | 〇(U+3007) 与 ○(U+25CB) 编码不同但字形相同 |
| 捕获组约定是隐性契约 | 正则"能用"不等于"在别的引擎里能用" |
| 升级表要覆盖所有历史形态 | 持久化升级靠精确匹配，中间版本必须补进废弃表 |
| 验证要真机实测 | 不能只看正则"看起来对" |

### 6.4 功能开发的 6 步法

从彩读导出缓存功能开发全过程提炼：

```
① 定义请求/响应类型 (shared/types.ts)
② 定义 IPC 通道 (shared/ipc.ts)
③ 实现主进程逻辑 (main/新文件.ts)
④ 注册 IPC handler + preload 暴露
⑤ 复用现有排版函数
⑥ 两个 UI 入口 + 快捷键
```

**关键原则**：
- 改主进程/preload 必须彻底重启，否则渲染层调用旧接口必然失败
- 错误信息必须透传真实文案，不要给笼统提示
- 快捷键监听用捕获阶段，否则被 Monaco 等控件先吞掉

## 七、后续演进：万维读书计划

彩读的下一阶段是「万维读书（OmniReader）」，核心是信息表达方式的扩容：

```
彩读（现状）                    万维读书（目标）
颜色（1 个主通道）        →     8+ 个正交视觉通道
正则词法标注              →     分词 + 词性 + 叙事层 + 角色识别
颜色固定绑定语义          →     语义与通道解耦，可任意换位
```

**三个核心命题**：
1. **维度论**：语义与视觉通道是正交集合，通过映射矩阵连接
2. **文字重量实体化**：字重成为一级信息通道
3. **权利与位置分割**：信息表达权归标注引擎，展示位置归用户配置

**实施路线**：POC（1.5 周）→ α MVP（4 周）→ β（6 周）→ γ（8 周）

**可学习点**：即使是成熟项目，下一阶段也应先做 POC 验证关键假设，再决定投入。
