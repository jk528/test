# 进阶层 · 高质量开发工作流

> **适合人群**：有基础的开发者，已能做出可运行的软件，想提升迭代质量与速度
> **学习目标**：掌握彩读 5 个月 24 版本背后的 10 条控制哲学与全链路自动化
> **案例基底**：彩读从 v1.0.1 到 v3.8.11 的迭代全过程
> **预计学习时间**：3-4 小时

## 第一课：小步快跑——发布节奏的数学

### 1.1 彩读的节奏数据

| 阶段 | 周期 | 版本数 | 平均间隔 | 每版功能点 |
|------|------|--------|---------|-----------|
| 1.x | 2026-04（1 个月） | 5 个 | 5-11 天 | 2-4 个 |
| 2.x | 2026-05~06（2 个月） | 9 个 | 3-7 天 | 一个子系统 |
| 3.x 高产期 | 2026-07~09（3 个月） | 14 个 | 3.7 天 | — |

### 1.2 为什么小步快跑优于大步慢跑

```
大步慢跑（3 个月一版，每版 20 个功能）：
- 每个功能都是半成品
- 出 bug 难定位（20 个功能哪个出的？）
- 用户等 3 个月才看到变化，失去耐心
- 开发者心流被打断（3 个月没正反馈）

小步快跑（每 4 天一版，每版 3 个功能）：
- 每个功能都是完整品
- 出 bug 立刻定位（3 个功能哪个出的？）
- 用户每 4 天看到变化，保持关注
- 开发者持续获得正反馈，保持心流
```

### 1.3 发布即公告

彩读 24 个 release 全部带结构化中文说明，不是技术流水账，而是产品宣讲：

```
✗ 技术流水账："重构了加载管线，改了 12 个文件"
✓ 产品宣讲："大文件打开更快了，改格式化不再重新加载"
```

### 1.4 动手练习：规划你的迭代节奏

1. 把你想做的所有功能列出来
2. 按优先级排序
3. 每 3-7 天选 2-4 个功能点为一版
4. 为每版写 release 说明（用户视角）

## 第二课：补丁优先于替换

### 2.1 彩读的补丁哲学

面对 Monaco Editor 的中文排版短板，彩读有两条路：

```
路线 A（替换）：换掉 Monaco，用自研编辑器
  → 成本：几个月重写核心
  → 风险：新编辑器有新坑
  → 结果：项目可能死在重写期

路线 B（补丁）：保留 Monaco，用补丁层解决短板
  → 成本：几天写补丁
  → 风险：低（补丁可随时移除）
  → 结果：项目继续高速迭代
```

彩读选了 B，建立了 **Vite transform 改写 + 运行时补丁** 的双层体系。

### 2.2 补丁体系的具体实现

**postinstall 补丁**（安装时自动执行）：
```json
{
  "postinstall": "electron-rebuild && node scripts/patch-monaco-hover.mjs && node scripts/patch-xpath.mjs"
}
```

**Vite transform 插件**（构建时自动改写源码）：
- `monacoCjkWrapStringsPlugin`：中文换行
- `monacoLineSpacingPlugin`：段间距
- `pdfjsAssetsPlugin`：pdfjs 资源

### 2.3 补丁脚本的设计模式（幂等 + 安全）

每个补丁脚本都遵循同一套模式：

```
1. 检查目标文件是否存在 → 不存在则 warn + exit(0)，不阻断流程
2. 检查是否已打过补丁（marker 注释）→ 已打则 exit(0)
3. 精确匹配 needle（原始代码段）→ 匹配失败则 warn"结构已变" + exit(0)
4. 字符串替换写入 → 打印成功日志
```

**关键**：幂等（重复执行不报错）+ 安全降级（库升级后结构变了不崩溃）。

### 2.4 什么时候该替换，什么时候该补丁

| 场景 | 选择 | 原因 |
|------|------|------|
| 内核缺一个功能 | 补丁 | 成本低，可逆 |
| 内核方向与你冲突 | 补丁（关闭其优化） | 彩读三次"降级即升级" |
| 内核已停止维护 | 替换 | 补丁无意义 |
| 内核协议不兼容你的需求 | 替换 | 补丁解决不了 |
| 内核性能差 10 倍 | 替换 | 补丁补不了性能 |

### 2.5 动手练习：审视你的依赖

列出你项目里的 3 个核心依赖，对每个问：
1. 它有什么短板？→ 能补丁就补丁
2. 它有什么优化与你冲突？→ 关掉它的优化
3. 它有上游无解的问题？→ WARNING 明示，不掩盖

## 第三课：兼容而不复制

### 3.1 彩读的兼容策略

| 兼容对象 | 来源 | 彩读的做法 |
|----------|------|-----------|
| Legado 书源 JSON | 安卓阅读器数万书源 | TypeScript 复刻规则引擎 |
| CHM 格式 | libmspack (C 库) | 移植为 JavaScript 实现 |
| MOBI/EPUB | foliate-js | 参考实现，集成进自有管线 |
| 词典 | readest | 参考交互 |

### 3.2 兼容而不复制的核心

```
兼容 = 复用对方的格式/协议/生态
不复制 = 不引入对方的依赖/语言/运行时
```

彩读兼容 Legado 书源（Java/Rhino 生态），但不引入 Java/Rhino，而是用 TypeScript 重新实现规则引擎。

### 3.3 为什么不直接引入依赖

| 直接引入 | 重新实现 |
|---------|---------|
| 依赖债（对方升级你跟着升） | 自主可控 |
| 体积大（整个运行时） | 只实现需要的部分 |
| 架构冲突（JVM vs Node） | 架构统一 |
| 安全风险（对方漏洞） | 自己可控 |

### 3.4 动手练习：找你项目里的兼容机会

问自己：
1. 我的领域有什么现成生态可以兼容？（格式/协议/数据源）
2. 兼容它能让用户零成本迁移吗？
3. 我能用我的技术栈重新实现它的核心吗？

## 第四课：issue 驱动的公开开发闭环

### 4.1 彩读的 issue 节奏

5 个月近百个 issue/PR，大量 issue 直接成为版本主线：

| Issue | 主题 | 落地版本 |
|-------|------|---------|
| #50 | 摸鱼模式 | 3.8 |
| #58 | 极简视图 | 3.8 |
| #83 | 阅读尺（ADHD） | 3.8 |
| #67 (PR) | 火山引擎 TTS | 3.7 |
| #90 (PR) | Edge TTS 标点停顿 | 3.8.11 |

### 4.2 issue 驱动的工作流

```
用户提 issue → 作者评估优先级 → 排入版本计划
→ 开发 → release 说明回链 issue → 用户看到反馈被采纳
```

**关键**：release 说明逐条回链 issue 编号，让用户看到自己的反馈被重视。

### 4.3 如何处理 issue

| issue 类型 | 处理方式 |
|-----------|---------|
| 功能建议 | 评估优先级，排入版本计划 |
| bug 报告 | 立刻复现，修复后回链 |
| PR | review，合并后致谢 |
| 重复 issue | 标记 duplicate，指向原 issue |
| 无效 issue | 礼貌关闭，说明原因 |

### 4.4 动手练习：建立你的 issue 工作流

1. 给每个 issue 打标签（bug/feature/enhancement/question）
2. 用 GitHub Projects 看板管理（To do → In progress → Done）
3. 每次发布时在 release 说明回链本版解决的 issue

## 第五课：诚实的风险声明

### 5.1 彩读的诚实清单

| 场景 | 彩读的说法 |
|------|-----------|
| v3.0 书源 | "做不到 100% 复刻……目前算是测试版" |
| v2.5 AI 智能排版 | "请自行测试" |
| 乱码还原 | "有一定误还原风险，请自行检查" |
| README 高级换行 | "这个问题连 VSCode 都没能完美解决" |

### 5.2 为什么诚实比假装全能更好

```
假装全能：
- 用户信任度高 → 发现问题 → 信任度崩塌
- 用户期望高 → 稍有不满就差评

诚实声明：
- 用户期望合理 → 发现问题 → "作者说过，正常"
- 信任度可持续增长
```

### 5.3 如何诚实而不吓跑用户

| 错误 | 正确 |
|------|------|
| "这个功能很烂" | "这个功能目前是测试版，欢迎反馈" |
| "可能有很多 bug" | "如发现问题，请提交 issue" |
| "做不到" | "做不到 100%，但会持续迭代纠错" |

**原则**：声明局限性 + 给出解决路径 + 表达持续改进的态度。

## 第六课：全链路自动化

### 6.1 彩读的三层自动化

```
层 1：项目拆积木（postinstall 补丁 + Vite 插件）
  → 装完依赖即自动修补第三方库

层 2：调试效率（专用 dev 命令 + 探测脚本）
  → 跳过无关模块，直接调试目标

层 3：打包上传（CI/CD 五架构并行）
  → 推个 tag，全自动构建发布
```

### 6.2 调试效率设计

| 命令 | 用途 | 效率设计 |
|------|------|----------|
| `npm run dev` | 全功能热重载 | 三端统一 HMR |
| `npm run dev:find` | 只开找书窗口 | 跳过主窗加载 |
| `npm run typecheck` | 类型检查 | 不产出文件 |
| `npm run test` | 单元测试 | Node 原生 --test |

**可学习点**：为每个调试场景设计专用命令，不要一个 `npm run dev` 调所有东西。

### 6.3 CI/CD 的核心设计

```yaml
on:
  push:
    tags: ["v*"]          # 推 tag 自动触发
```

**发布流程（开发者只需 3 步）**：
```bash
git commit -a -m "修改了xxx"
npm version patch         # 自动改版本号 + 打 tag
git push && git push --tags
# CI 自动完成：5 架构并行构建 → 统一发布
```

### 6.4 CI 的质量门禁

彩读 CI 内置了多个质量门禁：

| 门禁 | 实现 | 作用 |
|------|------|------|
| Tag 版本校验 | CI Step 比对 tag 与 package.json | 不一致直接 fail |
| 包体大小校验 | AppImage > 200MB 则 fail | 防止裁剪退化 |
| 缓存优化 | cache electron + electron-builder | 加速 CI |

### 6.5 动手练习：为你的项目加自动化

1. 写一个 postinstall 脚本（哪怕只做一件小事）
2. 配一个 GitHub Actions（哪怕只跑 typecheck）
3. 加一个质量门禁（哪怕只检查包体大小）

## 第七课：问题解决方法论

### 7.1 推翻重写是常态

彩读明确推翻过 13 个方案，关键不在不犯错，而在**私有方案扩散前完成切换**：

| 推翻内容 | 时点 | 动机 |
|----------|------|------|
| .txt → Markdown 中间格式 | v2.5 | 自造标记无法表达层级 |
| 手写正则 → marked 解析 | v3.3 | 私有解析器边角问题无穷 |
| 本地构建 → CI 构建 | v2.5 | 跨平台打包 |
| Node/undici → Chromium fetch | v3.3 | TLS 指纹被拦截 |

**核心教训**：私有方案活得越久，迁移成本越高。越早切换成本越低。

### 7.2 新功能带来新问题（这是正常的）

| 新功能 | 引发的连锁修复 | 时间跨度 |
|--------|---------------|----------|
| 背景图 | 粘性标题阴影、圆角选区露底、堆叠修复 | 两周 4 个 fix |
| 摸鱼模式 | 定时滚动、最小窗高、Z 序大战、越拖越大 | 11 天 11 版 |

**可学习点**：新功能引入后预留 1-2 周的"救火期"，这是正常的，不是规划失败。

### 7.3 功能开发的 6 步法

从彩读导出缓存功能提炼的标准流程：

```
① 定义请求/响应类型 (shared/types.ts)
② 定义 IPC 通道 (shared/ipc.ts)
③ 实现主进程逻辑 (main/新文件.ts)
④ 注册 IPC handler + preload 暴露
⑤ 复用现有函数
⑥ UI 入口 + 快捷键
```

**关键原则**：
- 改主进程/preload 必须彻底重启
- 错误信息必须透传真实文案，不要笼统提示
- 快捷键监听用捕获阶段

### 7.4 漏洞修复的最小补丁法

从彩读三大漏洞修复方案提炼：

| 原则 | 说明 |
|------|------|
| 最小补丁 | 每个补丁只改一处，不做附带重构 |
| 优先级排序 | P0 数据安全 → P1 资源一致性 → P2 健壮性 |
| 锚点定位 | 先定位代码行号，再写 before/after |
| 验证用例 | 每个补丁配验证步骤 |
| 回滚方式 | 每个补丁说明如何回滚 |

### 7.5 动手练习：建立你的问题解决清单

下次遇到问题时按这个流程：
1. 复现问题（不要在不能复现的情况下修）
2. 定位根因（不要在症状上修）
3. 写最小补丁（不要附带重构）
4. 写验证用例（确认修好了）
5. 记录回滚方式（万一更糟）

## 进阶层总结：高质量工作流 10 条

```
□ 1. 发布即公告：release 说明是产品宣讲，不是技术流水账
□ 2. 小步快跑：每 3-7 天一版，每版 2-4 个功能点
□ 3. 补丁优先于替换：成熟内核的短板用补丁层解决
□ 4. 兼容而不复制：复用生态但不引入依赖债
□ 5. issue 驱动：把 issue 当需求池，release 回链
□ 6. 诚实风险声明：声明局限性 + 给出路径 + 持续改进
□ 7. 格式策略收敛：标准格式 > 私有格式，越早切换越好
□ 8. 降级即升级：关掉通用优化服务特定场景
□ 9. 全链路自动化：postinstall + Vite 插件 + CI/CD
□ 10. 平台坑清单化：跨平台问题文档化，不假装不存在
```
