# 入门层 · 从零开始制作软件

> **适合人群**：零基础新人，第一次想做一个完整软件
> **学习目标**：理解立项前的关键决策，能独立完成一个软件的从零到首发
> **案例基底**：彩读（ColorTxt）5 个月从 v1.0.1 到 v3.8.11 的全过程
> **预计学习时间**：2-3 小时（阅读 + 思考自己的项目）

---

## 第一课：软件不是从写代码开始的

### 1.1 彩读的第一步

彩读作者的第一步不是打开编辑器写代码，而是：

```
在 VS Code 里看小说 → 发现体验痛点 → 找到可复用的轮子 → 确定一句话定位
```

**真实过程**：
1. 作者平时在 VS Code 里看小说（真实使用场景）
2. 发现 VS Code 的代码语法高亮可以让对话、人物名、章节标题自动分色（体验痛点）
3. 找到插件 vscode-txt-syntax，确认语法高亮可以移植（现成轮子）
4. 定位："一款会给内容上色的本地 TXT 小说阅读器"（一句话定位）

### 1.2 新人最容易犯的错

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 先写代码再想做什么 | 做出来没人用 | 先找到自己真实使用的痛点 |
| 一上来就想造轮子 | 重复发明，进度缓慢 | 先找现成方案，确认"差最后一公里" |
| 定位模糊："一个好用的工具" | 无法聚焦，功能蔓延 | 一句话定位，含核心差异点 |
| 想一次做完所有功能 | 永远发布不了 | 首发只做一件事 |

### 1.3 动手练习：找到你的软件定位

回答这三个问题，如果你的软件定位清晰了再继续：

1. **我自己在什么场景下遇到了什么痛点？**（必须是真实场景，不是想象）
2. **现有方案差在哪里？**（如果现有方案够用，就不需要你做）
3. **一句话能说清我的软件是什么吗？**（说不清说明定位还没想好）

## 第二课：技术选型——选成熟内核而非自造

### 2.1 彩读的选型表

| 要选什么 | 彩读选了什么 | 为什么选它 | 为什么不选另一个 |
|----------|-------------|-----------|-----------------|
| 桌面应用壳 | Electron | 跨平台 + Node 生态 + Chromium | Tauri 更轻但生态当时不够 |
| UI 框架 | Vue 3 | 组合式 API、响应式、轻量 | React 在桌面端无额外优势 |
| 编辑器内核 | Monaco | 百万行级性能 + 行列模型 + 装饰器 | 富文本 div 做不了大文件 |
| 类型系统 | TypeScript | 多进程统一类型安全 | JS 在多进程项目维护成本高 |
| 构建工具 | electron-vite | 统一三端构建 + HMR | 手配 webpack 维护成本高 |

### 2.2 选型的核心原则

```
原则一：每个选型都选「最成熟 + 生态最厚」的方案
原则二：把创新留给业务层，不留给基础设施
原则三：选有大量前人踩坑记录的方案，不选没人用的新东西
```

### 2.3 新人选型避坑

| 坑 | 为什么是坑 | 怎么避 |
|----|----------|--------|
| 选最新最潮的框架 | 文档少、坑没人填、生态薄 | 选 Star 多、issue 多、CHANGELOG 长的 |
| 自己写 UI 框架 | 重复发明，永远在做基础设施 | 用现成框架，把时间花在业务上 |
| 选没人用的轮子 | 出问题找不到答案 | 在 GitHub 搜同类项目，看别人用什么 |
| 不考虑跨平台 | 后期移植成本极高 | 一开始就选跨平台方案 |

### 2.4 动手练习：为你的软件做选型

列出你的软件需要的 5 个核心能力，为每个能力找 2-3 个候选方案，按「成熟度 × 生态厚度」打分，选最高分。

## 第三课：架构分层——积木式拆分

### 3.1 彩读的架构图

```
┌─────────────────────────────────────────────────┐
│                  Electron 应用                   │
│  ┌──────────┐  ┌──────────┐  ┌────────────────┐ │
│  │ Main     │  │ Preload  │  │ Renderer (Vue) │ │
│  │ 主进程    │  │ 预加载   │  │ 渲染进程        │ │
│  │ IPC处理   │←→│ context  │←→│ Monaco编辑器    │ │
│  │ 文件I/O  │  │ Bridge   │  │ Vue组件树       │ │
│  │ AI/RAG   │  │          │  │ Composables    │ │
│  └──────────┘  └──────────┘  └────────────────┘ │
│  ┌──────────────────────────────────────────┐   │
│  │            Shared (共享层)                │   │
│  │  类型定义、常量、IPC通道、预设配置         │   │
│  └──────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘
```

### 3.2 为什么要分层

| 不分层的问题 | 分层的好处 |
|-------------|-----------|
| 代码混在一起，改一处牵全身 | 各层独立演进，互不影响 |
| 无法复用 | Shared 层可被多端复用 |
| 安全风险大（渲染进程能直接调 Node） | contextIsolation 隔离风险 |
| 难以测试 | 各层可独立 mock 测试 |

### 3.3 积木式设计要点（新人最该学的一点）

彩读采用 **多窗口 + 不同 HTML 入口** 的积木式架构：

| 窗口 | 入口 | 何时创建 | 何时销毁 |
|------|------|---------|---------|
| 主阅读窗 | index.html | 启动/新窗口/双击文件 | 用户关闭 |
| 找书窗 | find-book.html | F7 | 用户关闭 |
| 摸鱼窗 | stealth-reader.html | F9 | 用户关闭 |
| 取色器窗 | eyedropper.html | 配色面板→滴管 | 取色完成 |

**积木式核心思想**：
- 每个窗口是一个独立「积木块」
- 可以单独创建、组合使用、互不干扰
- 共用工厂函数，通过参数区分加载哪个 HTML
- 窗口关闭时若无剩余用户窗，强拆隐藏窗

### 3.4 存储也要分层

```
层级1: localStorage       → UI 偏好、会话快照（轻量、同步）
层级2: userData JSON 文件  → 配置、密钥（结构化、可加密）
层级3: SQLite 数据库       → 大数据、需查询（向量、书源）
层级4: 模型缓存目录         → 大文件、不常变（模型权重）
```

**原则**：数据按「大小 × 查询需求 × 变更频率」分层，不要全塞一个存储。

### 3.5 动手练习：画你的软件架构图

1. 画出你的软件有哪些「积木块」（窗口/模块/服务）
2. 画出它们之间如何通信（IPC/事件/共享存储）
3. 画出数据存在哪一层、为什么

## 第四课：首发只做一件事

### 4.1 彩读的首发

彩读 v1.0.1（2026-04-04）的 release 正文：

> 支持空格键跳转到下一屏

就这一句话。不是"支持空格键翻屏 + 章节识别 + 配色 + 电子书格式"，而是**只做一件事**。

### 4.2 为什么首发要极简

| 首发堆功能 | 首发极简 |
|-----------|---------|
| 每个功能都是半成品 | 一个功能是完整品 |
| 发布日期一再推迟 | 按时发布 |
| 用户不知道核心卖点是什么 | 用户一句话就懂 |
| 出 bug 不知道是哪个功能的 | 出 bug 立刻定位 |
| 心流被打断，容易放弃 | 获得正反馈，继续迭代 |

### 4.3 范围控制的 6 个维度

| 维度 | 彩读的做法 |
|------|-----------|
| 功能范围 | 首发一个核心功能，不堆功能 |
| 质量范围 | 便携版/AppImage/自定义安装路径一并发布 |
| 包体范围 | 剔除语言包、启用 asar |
| 架构范围 | 1.0 即采用 Monaco，不自己造渲染引擎 |
| 体验范围 | 侧栏改版为类 VS Code 风格，建立用户认知锚点 |
| 节奏范围 | 每个版本聚焦 2-4 个功能点 |

### 4.4 动手练习：砍掉首发功能的 80%

列出你想在首发做的所有功能，然后：
1. 找出那个"没有它软件就不成立"的核心功能 → 保留
2. 其余全部砍掉 → 放进 v1.1、v1.2 的待办
3. 问自己：砍成这样还值得发布吗？如果答案是"是"，范围就对了

## 第五课：开源协议与发布制度

### 5.1 选协议

| 协议 | 特点 | 适合 |
|------|------|------|
| MIT | 最宽松，允许一切 | 想最大化传播 |
| MPL-2.0（彩读选的） | 允许商用但需公开修改文件 | 想被商用但保护修改 |
| GPL | 强传染性，衍生作品必须同协议 | 想保护自由软件生态 |

### 5.2 建立发布制度

彩读从第一天就建立了发布制度：

```
每个版本前：Update CHANGELOG.md 提交
release 正文：结构化（新功能/改进/修复）
issue 回链：release 说明逐条回链 issue 编号
CHANGELOG.md 与 release 正文同源同步
```

**新人常犯的错**：
- 不写 CHANGELOG，只写 commit message → 用户不知道每版改了啥
- release 正文写技术流水账 → 应该写用户能感知的变化
- 不回链 issue → 用户不知道自己的反馈被采纳

### 5.3 动手练习：写你的首发 release 说明

用这个模板：
```
## v0.1.0（日期）

### 新功能
- [一句话说清用户能做什么]

### 改进
- [相比上一版用户能感知的改善]

### 修复
- [修了哪些问题，回链 issue #N]
```

## 入门层总结：从零到首发的 7 步清单

```
□ 第 1 步：找到自己真实使用的痛点
□ 第 2 步：确认现有方案差最后一公里
□ 第 3 步：写出一句话定位
□ 第 4 步：为 5 个核心能力做技术选型
□ 第 5 步：画积木式架构图（模块 + 通信 + 存储）
□ 第 6 步：砍掉首发功能的 80%，只留核心
□ 第 7 步：选协议 + 建立发布制度 + 发布
```

完成这 7 步，你就走完了彩读从零到 v1.0.1 的路。

## 下一步

完成入门层后，进入 **进阶层 · 高质量开发工作流**，学习如何从 v1.0 迭代到 v3.8。

> **关键提醒**：入门层最重要的不是技术，而是**立项前的决策**。80% 的软件失败不是因为代码写得差，而是因为定位不清、范围失控、选型错误。把这三件事想透，你已经赢了大多数新人。
