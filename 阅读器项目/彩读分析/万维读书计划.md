# 万维读书（OmniReader）计划

> **文档性质**：产品与技术总规划（V1.0）
> **基底项目**：ColorTxt 彩读 v3.8.11（Electron 35 + Vue 3.5 + Monaco 0.55）
> **整理日期**：2026-09-21
> **一句话定位**：让文字从"内容载体"升级为"多维信息实体"——每个词同时承载颜色、字重、倾斜、字宽、装饰线、背景、发光、字间距等正交维度，把语言结构（词性、叙事、角色）变成可感知、可配置、可换位的视觉语言。
> **关联文档**：[ColorTxt离线缓存问题与改善方案.md](./ColorTxt离线缓存问题与改善方案.md)、[ColorTxt导出缓存功能开发全过程.md](./ColorTxt导出缓存功能开发全过程.md)、[ColorTxt字体下载与设置全过程.md](./ColorTxt字体下载与设置全过程.md)

## 第一部分 · 总纲

### 1.1 范式跃迁：从彩读到万维读书

| 阶段 | 彩读（现状） | 万维读书（目标） |
|---|---|---|
| 信息载体 | 颜色（1 个主通道） | 8+ 个正交视觉通道 |
| 标注依据 | 正则词法（引号/括号/词表） | 分词 + 词性 + 叙事层 + 角色识别 |
| 通道关系 | 颜色固定绑定语义 | 语义与通道**解耦**，可任意换位 |
| 用户角色 | 规则使用者 | 皮肤消费者 / 标注修正者 / 维度配置者 |
| 智能位置 | 无 | 冷缓存 + 热解析混合管线 |
| 产物 | 上色文本 | 多维精标注文本 + 皮肤包生态 |

### 1.2 三个核心命题（本计划的理论支点）

1. **维度论**：语义信息（名词、对话、主角……）与视觉通道（颜色、字重……）是两个正交集合，二者通过一张**映射矩阵**连接，而非硬编码绑定；
2. **文字重量实体化**：字重不再是排版修饰，而是与颜色平等的**一级信息通道**——可以"用重量说话"；
3. **权利与位置的分割**：信息表达权（语义）归标注引擎，展示位置（一号位是颜色还是字重）归用户配置。位置可以移动、可以叠加、可以交换。

### 1.3 设计原则

| 原则 | 含义 |
|---|---|
| 可观测优先 | 吸取"假完成"教训：算法失误、缓存命中率、标注置信度必须可见可查 |
| 低侵入分叉 | 新功能集中在 `src/renderer/src/omni/`，不破坏主阅读器，可随上游升级 |
| 粗颗粒先行 | 先用 4 大词类跑通，再追求 7 词类细颗粒，准确率优先于颗粒度 |
| 窗口化渲染 | 只对可视区做重渲染，保证大文件流畅 |
| 一切皆可配置 | 语义维度、视觉通道、映射关系、皮肤方案全部开放接口 |

## 第二部分 · 双维度映射法（核心机制）

### 2.1 三层模型

```
┌─────────────────────────────────────────────────────────┐
│  语义层（被表达的信息）                                     │
│  词性 · 叙事层 · 角色 · 实体类型 · 自定义标注 ……            │
└──────────────────────┬──────────────────────────────────┘
                       │  映射矩阵 M（用户可配置、可换位）
┌──────────────────────▼──────────────────────────────────┐
│  通道层（表达手段，8+ 维）                                  │
│  颜色 · 字重 · 倾斜 · 字宽 · 装饰线 · 背景 · 发光 · 字间距  │
└──────────────────────┬──────────────────────────────────┘
                       │  皮肤包（预设方案）
┌──────────────────────▼──────────────────────────────────┐
│  位置层（通道在界面上的布局：一号位/次号位/关闭）            │
└─────────────────────────────────────────────────────────┘
```

### 2.2 映射矩阵示例（小说皮肤）

> 行 = 语义维度，列 = 视觉通道。值 = 该通道在此语义上的具体参数，空 = 不启用。

| 语义 ＼ 通道 | 颜色 | 字重 | 倾斜 | 背景 | 发光 | 装饰线 |
|---|---|---|---|---|---|---|
| 正文/旁白 | 基础色 | 400 | — | — | — | — |
| 人物对话 | 对话色 | 400 | — | — | — | — |
| 主要角色名 | 角色色A | 700 | — | — | 弱发光 | — |
| 次要角色名 | 角色色B | 500 | — | — | — | — |
| 标点符号 | 标点色 | 300 | — | — | — | — |
| 数字/外文 | 外文色 | 400 | italic | — | — | — |
| 自定义标注 | 标注色 | — | — | 标注底色 | — | 下划线 |

### 2.3 "换位"：同一语义的不同表达

以"动词"为例，映射可以整体换位而语义无损：

| 方案 | 动词的呈现 | 适用场景 |
|---|---|---|
| 颜色一号位 | 动词=蓝色（现状思路） | 普通阅读 |
| 字重一号位 | 动词=700 粗体，全部文字同色 | 学术精读、黑白打印 |
| 字宽一号位 | 动词=加宽 110% | 演示/教学 |
| 组合位 | 动词=深色 + 600 字重 + 下划线 | 最强提示 |

**这就是"权利与位置分割"的落地**：语义标签不动，用户拖动矩阵中的通道排位即可换一种"语言"阅读。

### 2.4 冲突规则（多维叠加的优先级）

一个词可能同时命中多个语义（如：主角名 + 实体 + 自定义标注）。规定：

1. 每个通道独立取值，**高优先级语义覆盖低优先级**（自定义 > 角色 > 词性 > 默认）；
2. 不同通道互不冲突（颜色被A占、字重被B占是允许的，这正是"多位置展示多维度"）；
3. 同通道冲突时按优先级表裁决，并在悬浮提示中显示该词的**全部标签**。

## 第三部分 · 语义标注引擎

### 3.1 两套标注体系

| 体系 | 颗粒度 | 标签 | 目标读者 |
|---|---|---|---|
| 学术（细颗粒） | 6+1 词性 | 名、代、动、副、介、连（+助/标点） | 语言学习、文本分析 |
| 学术（降颗粒） | 4 大类 | 实体类、动作类、修辞类、工具类 | 入门、降低分词误伤 |
| 小说（叙事颗粒） | 7 叙事维度 | 旁白、对话、主角、次角、标点、数字外文、自定义标注 | 小说阅读（主力场景） |

### 3.2 词性 7→4 归并表

| 大类 | 包含词性 | 视觉语义 |
|---|---|---|
| 实体类 | 名词、代词 | 文本的"骨架" |
| 动作类 | 动词 | 文本的"引擎" |
| 修辞类 | 形容词、副词 | 文本的"色彩" |
| 工具类 | 介词、连词、助词、标点 | 文本的"铰链" |

**为什么降颗粒能治分词失误**：细颗粒下"名词被误判为代词"是可见错误；归入同一大类后，**类间错误被视觉吸收**——这是用架构换准确率。

### 3.3 小说叙事 7 色标注规则

| # | 语义 | 判定来源（管线） |
|---|---|---|
| 1 | 正文/旁白基础色 | 默认兜底 |
| 2 | 对话色 | 引号配对（现有 Monarch 已支持，复用） |
| 3 | 主要角色/关键角色 | 角色识别：词频 + 对白归属 + NER |
| 4 | 次要角色 | 角色识别低分级 |
| 5 | 标点符号色 | 现有标点 token |
| 6 | 数字/外文 | 现有数字/英文 token |
| 7 | 自定义划线/标注 | 用户手动选择 + 规则词表 |

### 3.4 标注管线（流水线）

```
原文
 ├─ 预处理：繁简统一(opencc) · 章节切分
 ├─ 第1层 词法：Monarch（引号/括号/数字/外文/标点）     ← 现有，保留
 ├─ 第2层 分词+词性：@node-rs/jieba tag()              ← 快，默认
 ├─ 第3层 叙事层：引号状态 + 对白动词（说/道/笑道）统计
 ├─ 第4层 角色层：词频统计 + 对白归属 + (可选)transformers NER
 └─ 融合：每个词元得到一个标签集合 → 送映射矩阵
```

### 3.5 分词技术选型（项目已具备，无需新引依赖）

| 组件 | 现状 | 用途 |
|---|---|---|
| `@node-rs/jieba` ^2.0.1 | **已安装**，现用于 RAG 分词（src/main/ai/rag/jieba.ts，懒加载+自带dict） | 分词与词性标注主力，Rust 预编译二进制、免 node-gyp |
| `@huggingface/transformers` ^3.8.1 | **已安装** | ONNX 本地模型：POS 细标注 / NER 角色识别，按需加载 |
| `sqlite-vec` + better-sqlite3 | 已安装 | 角色向量聚类、相似实体归并 |
| `mdict-js` + opencc | 已安装 | 词典释义联动、繁简统一 |

**nodejieba 词典配置方法**（本项目用 @node-rs/jieba，比 nodejieba 简单）：

```ts
// 1) 默认词典：require("@node-rs/jieba/dict") （现有 jieba.ts 已用）
// 2) 自定义词典：用户词典文件（每行: 词 词频 词性，如：贾宝玉 1000 nr）
const jieba = Jieba.withDict(defaultDict);
jieba.loadDict(userDictBuffer);   // 叠加用户词典
// 3) 建议内置"小说人名词表"作为可选叠加词典（可由 mdict/全书角色统计自动生成）
```

> **POC 验证项**：@node-rs/jieba 的 `tag()` 词性接口在当前版本的标签集与准确率，作为阶段 0 第一项实测。

### 3.6 "无法观测到的失误"与对策

**问题本质**：算法错误（某词词性标错）不会造成崩溃、错位、排版异常，页面"看起来一切正常"，用户甚至意识不到错误存在。强匹配规则 + 粗放视觉呈现会掩盖这类失误。

| 对策 | 做法 |
|---|---|
| 降颗粒吸收 | 7→4 归并，类间错误不可见（3.2） |
| 置信度可见 | 低置信词加虚下划线，悬浮显示"机器标注·可修正" |
| 抽样审计工具 | 每章随机抽 20 词生成校对清单，统计准确率 |
| 双引擎对照 | jieba 与 transformers 结果不一致时标记"存疑" |
| 人工修正闭环 | 点词即可改标签，修正结果回写用户词典，越用越准 |

## 第四部分 · 多维度叠加渲染引擎

### 4.1 八维度 + 可扩展

| # | 维度 | CSS 属性 | 信息表达力 |
|---|---|---|---|
| 1 | 颜色 | `color` | 分类（现状主通道） |
| 2 | 字重 | `font-weight` 200–900 | 重要性/词性（**新主通道**） |
| 3 | 倾斜 | `font-style` | 外文/心理/特殊语义 |
| 4 | 字宽 | `font-stretch` / 可变字体 wdth 轴 | 强调/节奏 |
| 5 | 装饰线 | `text-decoration` | 标注/删除/专名 |
| 6 | 背景色 | `background` | 高亮/自定义标注 |
| 7 | 发光阴影 | `text-shadow` | 主角/关键信息 |
| 8 | 字间距 | `letter-spacing` | 断句/节奏（**受限，见 4.3**） |
| + | 可扩展 | 字号微差、轮廓描边、大小写变体等 | 自定义维度接口预留 |

**完整句子示例（八维叠加）**：主要角色名 = 角色色 + 700 字重 + 弱发光；其对白 = 对话色；对白中的外文词 = 斜体 + 外文色；强调词 = 加宽 + 下划线；自定义标注 = 背景色 + 字间距拉开——一个句子里八维各司其职、互不干扰。

### 4.2 Monaco 可行性矩阵（诚实评估，已对照现有架构）

现有上色走 Monarch token + 自定义主题（txtrTextMonarch.ts / readerInlineDecorations.ts），**token 主题只能表达颜色与 bold/italic/underline**。要实现 8 维必须改用 **decorations + inline CSS**。

| 维度 | Monarch token | decorations(inline CSS) | 结论 |
|---|---|---|---|
| 颜色 | ✅ | ✅ | 原生可用 |
| 字重 | ⚠️ 仅 bold 一档 | ✅ 200–900 全档 | **必须走 decorations** |
| 倾斜 | ✅ | ✅ | 原生可用 |
| 字宽 | ❌ | ✅ Chromium 支持可变字体 wdth 轴 | 需可变字体 + decorations |
| 装饰线 | ⚠️ 仅下划线/删除线 | ✅ 线型/颜色/粗细可控 | decorations 更完整 |
| 背景色 | ❌ | ✅ | 必须走 decorations |
| 发光阴影 | ❌ | ✅ 仅作用于可视区，性能可控 | decorations |
| 字间距 | � | ⚠️ 见 4.3 硬约束 | 高风险，限制使用 |

### 4.3 字间距硬约束（必须知情的技术红线）

Monaco 用**内部字符宽度表**计算光标定位、点击命中、自动换行。给 token 加 `letter-spacing` 后，视觉宽度与测量宽度不一致，会导致：点击位置错位、选区偏移、换行点错乱。

**对策分级**：

1. 不在常规阅读模式使用字间距；
2. 仅用于**临时态**（朗读当前句、选中句的短暂强调），此时不影响交互定位的感知；
3. 需要"节奏"语义时优先用别的通道（字宽/背景）替代；
4. POC 阶段实测错位程度，若可接受（如仅整段均匀加宽）再有限开放。

### 4.4 渲染性能策略

| 策略 | 说明 |
|---|---|
| 窗口化 decorations | 监听可视区变化，只给"可视行 + 上下缓冲"挂 decorations；全量标注结果在内存/缓存中 |
| 样式类预编译 | 每种渲染组合编译为一个 CSS class（`.omni-a7b…`），decoration 只引用类名，避免逐词内联样式 |
| 批量增量更新 | 滚动时 deltaDecorations 一次性替换，避免逐词刷新 |
| Worker 分词 | 标注计算放 worker，不阻塞渲染线程 |
| 虚拟滚动天然兜底 | Monaco 只渲染可视行 DOM，text-shadow 等昂贵属性的实际作用范围很小 |

## 第五部分 · 混合缓存机制（冷加载 / 热解析）

### 5.1 冷热定义

| 模式 | 触发 | 流程 | 延迟目标 |
|---|---|---|---|
| 冷加载 | 已缓存章节 | 读标注结果文件 → 直接生成 decorations | < 100 ms |
| 热解析 | 未缓存 / 新书 / 规则变更 | 可视区实时分词标注 → 后台补齐整章 | 首屏 < 500 ms |

### 5.2 标注缓存设计（吸取现有 .nb 与 RAG segmentCache 经验）

```
{userData}/omni_cache/
└── {书名哈希}/
    └── {章节哈希}.anno        ← 章级标注结果（建议 JSON/binary）
```

文件头元数据（版本控制，复用 AI_SEGMENT_VERSION 的 bump 思路）：

```json
{
  "version": 1,                 // 规则/词典/模型变更时 bump，自动失效重算
  "textHash": "md5(章节正文)",
  "tagger": "jieba@2.0.1+dictV3",
  "tokens": [ {"w":"宝玉","t":["nr","role_main"]}, … ]
}
```

### 5.3 与现有缓存问题的关系

本计划直接内建[离线缓存改善方案 S1/S2](./ColorTxt离线缓存问题与改善方案.md)的关键要求：

- 完成时显示真实「已标注 x/y 章」，不做假完成；
- 原子写入（临时文件 → rename）；
- 标注缓存与正文缓存（.nb）分离，互不污染；
- 提供命中率、占用空间、孤儿目录的可观测面板。

## 第六部分 · 字体基座（七种字体逻辑）

### 6.1 字体梯队

| 字体 | 可变/多字重 | 角色 | 现状 |
|---|---|---|---|
| 思源黑体 SC | 7 档静态字重（200–900） | 默认字体，字重通道基座 | **已安装并设为默认** |
| 思源宋体可变字体 | 单文件含 wght 轴 | 学术模式、宋体审美 | 需新增（可变版本，按语言子集） |
| 得意黑（Smiley Sans） | 可变 wght 400–700 | 个性皮肤、标题式阅读 | 需新增 |
| 系统字体栈 | — | 兜底 | 现有 |

### 6.2 字体 × 方案的预设组合（七种字体逻辑）

每套皮肤 = 一个字体 + 一套映射矩阵：

1. 思源黑体·小说（默认，叙事七色）
2. 思源黑体·学术（六词性 + 字重）
3. 思源黑体·纯重量（全部同色，仅字重表词性）
4. 思源宋体·学术（可变字重，书刊感）
5. 思源宋体·小说（宋体叙事）
6. 得意黑·个性（强对比，粗重表达）
7. 用户自定义皮肤

### 6.3 字体工程注意

- 可变字体单文件较大（数十 MB），需**子集化**（仅保留常用汉字）或首次使用时按需下载；
- wdth（字宽）轴需要可变字体支持，思源黑体现有静态 OTF 不含该轴——字宽通道依赖可变版本，纳入字体路线；
- 沿用现有 @font-face + presetFontDefinitions 的注册机制，不新起体系。

## 第七部分 · 系统架构与模块规划

### 7.1 模块布局（低侵入分叉）

```
src/renderer/src/omni/                ← 新增独立模块
├── engine/        分词器封装 · 词性标注 · 叙事标注 · 角色识别
├── mapping/       映射矩阵 · 冲突裁决 · 方案预设
├── render/        样式类编译 · decoration 规划 · 视区窗口化
├── cache/         标注缓存读写 · 冷热调度 · 命中率统计
├── skins/         七种皮肤定义 · 皮肤包导入导出
└── ui/            Omni设置面板 · 标签悬浮 · 校对工具
src/main/omni/                       ← 主进程：jieba tag IPC · 模型加载 · 缓存目录
src/shared/omni/                     ← 共享类型与通道定义
```

### 7.2 数据流

```
章节文本
  → [engine] 词元流(词+标签集合)
  → [mapping] 渲染指令流(标签集合 → 8 维参数)
  → [render] 编译为 CSS 类 + range
  → [视区窗口] deltaDecorations
  → Monaco 可视区呈现
  ↕ [cache] 章级标注结果冷读/热写
```

### 7.3 自定义维度接口

| 接口 | 内容 |
|---|---|
| 皮肤包格式 | JSON：字体 + 调色板 + 映射矩阵 + 通道开关；支持导入导出（可扩展自现有 .ctz 书包体系） |
| 语义标签扩展 | 允许第三方/用户注册新标签（如"伏笔""金句"）并绑定通道 |
| 渲染通道扩展 | 通道注册表，后续可加字号、描边等新维度 |
| 标注修正 API | 改标签 → 回写用户词典 → 全章重渲染 |

### 明确的"反目标"（本计划不做）

- 不做联网书库改造（找书维持现状）；
- 不做完整语法树/句法分析（投入产出比低）；
- 不重写 Monaco、不替换核心编辑器；
- 不在常规模式开放会造成错位的字间距。

## 第十三部分 · 结论

1. 万维读书的本质是一次**信息表达方式的扩容**：从颜色单通道走向 8+ 通道，从硬编码绑定走向**语义—通道映射矩阵**；
2. 三大支点——**维度解耦、字重实体化、位置可移动**——回答了"为什么改"；双引擎标注、窗口化渲染、冷热缓存回答了"怎么改"；
3. 项目底座**超出预期地完整**：jieba、transformers、Monaco、opencc、sqlite-vec 均已就位，主要工作是集成与管线建设，而非从零造轮子；
4. 最大的技术红线是 **Monaco 字间距错位**，最大的质量红线是**算法失误不可观测**——二者均已预置对策；
5. 建议立即从**阶段 0 POC** 开始：用 1.5 周把五个关键假设全部证实或证伪，再决定 α 阶段投入。POC 通过，则 MVP（四维文本）在约 4 周内可交付。
