## 2. 三方案核心差异

### 2.1 捕获组约定与标题来源（最关键差异）

| 方案 | 正则核心形态 | 组1 | 组2 | 标题来源 |
|------|-------------|-----|-----|----------|
| A splittxt | `^第([数字]+)(章\|回\|节\|卷)(\s*)(.*)$` | 数字 | 单位 | 整行（Python `group(0)` / VBA `m(0).Value`） |
| B splittxt2 | `第([数字]+)(章\|回\|节\|卷)(?:[ \t　]+(.*))?` | 数字 | 单位 | 整行 `m(0).Value` |
| C 彩读内置 | `(第[数字]+[章回节卷])(?:[ \t　]+(.*))?` | **完整序号（含第与单位）** | 副标题 | **组1 + 组2** |

> 彩读 [matchToTitle](file:///c:/Users/Administrator/Documents/这是什么/JK-temp/阅读器项目/彩读分析/.temp/ColorTxt/src/renderer/src/chapter.ts#L360-L366) 用「组1+组2」拼标题；splittxt/splittxt2 取整行。**同一条正则在这两套逻辑下表现完全不同**——这是「一回/二回」与「缺第字」两次事故的根因。

### 2.2 数字字符类演进

```
R1 splittxt:       0-9一二三四五六七八九十百千万零两
R2 splittxt2-1:    +〇 壹贰叁肆伍陆柒捌玖拾佰仟
R2 splittxt2 现行: +○（U+25CB）
终极版（B/C 共用）: 0-9０-９一二三四五六七八九十百千万亿億零〇○两兩壹貳贰叁參肆伍陸陆柒捌玖拾佰仟廿卅卌皕萬
```

### 2.3 尾部约束演进

```
宽松旧版:  (\s*)(.*)$      ← 单位后接任何内容都算标题（正文「第四回中…」会被误判）
收紧新版:  (?:\s+(.*))?$   ← 单位后接内容必须有空白（123 回事故的修复）
```

## 3. 三方案优缺点对比

### 3.1 A. splittxt 原版（单一正则）

| 优点 | 说明 |
|------|------|
| 简单 | 一条正则，逻辑最少，易读易维护 |
| 零依赖 | bas/py/js 三语言同式，随处可跑 |

| 缺点 | 说明 |
|------|------|
| 单一格式 | 只能匹配「第N章/回/节/卷」，英文 Chapter、序章、无第格式全漏 |
| 字符类残缺 | 缺 `〇`、缺大写、缺全角 → `第一〇〇章`、`第壹卷` 匹配不了 |
| 宽松尾部 | `(\s*)(.*)$` 把正文「第四回中…」误判为章节 → **红楼梦 123 回事故** |
| 无行首容错 | 行首缩进「　第一回」匹配不了 |

### 3.2 B. splittxt2 多正则版（现行）

| 优点 | 说明 |
|------|------|
| 多选并列 | `1,5` 同时覆盖「带第」与「无第」两类文本 |
| 终极字符类 | 全角/繁体/大写/俗写/〇/○ 全收（实测 8 类变体全命中） |
| 行首容错 | `[ \t　]*` 接受缩进 |
| 尾部收紧 | `(?:\s+(.*))?$` 拒绝正文句式，防误判 |
| 标题取整行 | 不依赖捕获组，标题永不丢字 |

| 缺点 | 说明 |
|------|------|
| VBA 专属 | 仅 VBA 版（原版有 py/js，本版没有） |
| 缺第缺数不可救 | `章`、`第回` 这类无数文本任何正则都失败（信息不足） |
| 跨工具需改写法 | 进彩读必须把 `第` 收进组1（见 §5 事故 3/4） |

### 3.3 C. 彩读内置规则（现行）

| 优点 | 说明 |
|------|------|
| 组1=完整序号 | 「组1+组2」拼标题天然完整，跨工具鲁棒 |
| 有界副标题 | `(?:\s+(.{1,40}))?` 限制标题长度，避免正文长句误入 |
| 自动升级 | SUPERSEDED 表静默升级旧规则，保留用户自定义 |

| 缺点 | 说明 |
|------|------|
| 数字/单位耦合 | 组1 混含 `第`/数字/单位，算区间需二次提取 |
| 依赖持久化升级 | 若用户保存了「未登记的中间版本」，升级不触发（见 §5 事故 5） |
| 无单位组格式需单列 | 序章/Chapter/纯数字需独立规则 |

## 5. 问题与解决全过程（详细）

### 事故 1：红楼梦 123 回误判（splittxt 宽松尾部）

**现象**：红楼梦全书 120 回被识别成 123 章。

**根因**：原正则尾部 `(\s*)(.*)$` 允许零空白直接接内容，正文三行被误判为章节：
- `第四回中既将薛家母子…`
- `第三十八回林潇湘…`
- `第一一九回中…`

**解决**：全部规则尾部收紧为「副标题前必须有至少一个空白」`(?:\s+(…))?`。纯序号行（`第1章`）仍可命中。

**验证**：收紧后 120 回正确，正文句式被拒。

---

### 事故 2：109 章漏配（○ 与 〇 编码差异）——第一次

**现象**：红楼梦桌面 txt 用正则扫描只匹配 109 章，100–110 回消失。

**根因**：字符类只有 `〇`（U+3007 汉字零），而 txt 的 100–110 回标题用的是 **`○`（U+25CB 白圈）**：

```
第一○○回　破好事香菱结深恨　悲远嫁宝玉感离情   ← 两个 ○ 都是 U+25CB
第一○一回　大观园月夜感幽魂　散花寺神签惊异兆
```

两字符字形几乎一样、编码不同（`〇` 在 CJK 符号区，`○` 在几何图形区），正则按码位匹配，漏掉 11 回。

**解决**：数字字符类同时收入 `〇` 与 `○`。实测从 109 → 120。

---

### 事故 3：「一回」「二回」残缺标题（捕获组约定冲突）

**现象**：把 splittxt2 正则直接粘进彩读，章节标题变成「一回」「二回」——`第` 字与真实标题都丢了。

**根因**：彩读 `matchToTitle` 用「组1+组2」拼标题；splittxt2 的组1=数字、组2=单位：

```
splittxt2:  ^…第([数字]+)(章|回|节|卷)…
            组1=「一」 组2=「回」 → 彩读拼出「一回」
```

**解决**：彩读必须用「组1=完整序号（含第与单位）」版本，或直接启用彩读内置 st2 适配规则。

---

### 事故 4：标题缺「第」字（`第` 在组1括号内外）

**现象**：用「彩读约定版」自定义正则，标题显示 `一○○回 破好事…`——仍缺 `第` 字。

**根因**：我此前给的修正版把 `第` 写在了捕获组1**括号外**：

```
错误:  ^[ \t　]*第([数字]+[章回节卷])(?:…)    ← 组1 = 「一○○回」，无「第」
正确:  ^[ \t　]*(第[数字]+[章回节卷])(?:…)    ← 组1 = 「第一○○回」，含「第」
```

**解决**：`第` 必须进组1。实测两种写法的组1：`一○○回` vs `第一○○回`。

---

### 事故 5：持久化规则未升级，109 章再漏——第二次（本轮修复）

**现象**：代码已更新为终极字符类，但彩读实际匹配仍只有 109 章。

**根因**（三层）：
1. 彩读把用户规则**持久化**在本地，启动时经 `upgradeOutdatedBuiltinRules` 升级；
2. 升级靠精确匹配 [SUPERSEDED_BUILTIN_PATTERNS](file:///c:/Users/Administrator/Documents/这是什么/JK-temp/阅读器项目/彩读分析/.temp/ColorTxt/src/renderer/src/chapter.ts#L305-L338) 里的旧 pattern；
3. 用户持久化的规则是「**收紧尾部 + 旧字符类**」的**中间版本**——废弃表里只登记了更早的「宽松尾部」版，**没覆盖这种**，所以升级未触发，旧字符类继续生效。

**证据**：用户贴出的运行中正则为 `…[零一二三四五六七八九十百千万两〇壹贰叁肆伍陆柒捌玖拾廿卅卌佰皕仟萬0-9０-９]{1,12}…(?:\s+(.{1,40}))?…`——字符类是旧版、尾部是收紧版，正是未登记的中间形态。

**解决**：在 SUPERSEDED 表中为全部 10 条内置规则**补充「收紧尾部 + 旧字符类」的中间版本 pattern**，使升级逻辑覆盖该形态。重启后自动升级为终极字符类。

**验证**：`npm run typecheck` 通过，应用重启，4 个 Electron 进程正常。

## 6. 教训与经验沉淀

| 教训 | 说明 |
|------|------|
| 字符类要双收形近字符 | `〇`(U+3007) 与 `○`(U+25CB) 编码不同但字形相同，必须同时收入 |
| 捕获组约定是隐性契约 | 正则「能用」不等于「在别的引擎里能用」——标题来源（整行 vs 组1+组2）必须先确认 |
| `第` 在组1内外决定完整性 | 彩读拼标题场景，`第` 必须在组1括号内 |
| 行首容错必须配尾部收紧 | 只加 `[ \t　]*` 会引入正文误判（121>120）；两者缺一不可 |
| 升级表要覆盖所有历史形态 | 持久化升级靠精确匹配，新出现的「中间版本」必须补进废弃表，否则旧逻辑悄悄残留 |
| 验证要真机实测 | 每次改完用真实 txt 全量扫描计数，不能只看正则「看起来对」 |
