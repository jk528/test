## POC-1：jieba 词性标注准确率验证

### 目标
验证 `@node-rs/jieba` 的 `tag()` 接口对中文小说文本的词性标注准确率，重点验证 4 大类粗归并后的准确率是否 ≥ 95%。

### 前置准备

| 项 | 说明 |
|---|---|
| 依赖确认 | 确认 `@node-rs/jieba` ^2.0.1 已安装，位置：`src/main/ai/rag/jieba.ts` |
| 测试文本 | 《红楼梦》第 1–3 回（约 2 万字），选取其中 200 词做人工校对样本 |
| 标注工具 | 准备一个简单的标注脚本，输出「词 / 原词性 / 大类 / 是否正确」四列表格 |

### 执行步骤

#### 步骤 1.1：tag() 接口可用性验证（0.5 天）

1. 在 `src/main/` 下新建临时文件 `omni-poc/poc1_jieba_tag.ts`
2. 调用 `Jieba.tag("宝玉笑道：「这个妹妹我曾见过的。」")`，观察输出
3. 记录标签集（n、v、adj、adv、nr、ns、r、p、c、u、w……），与 jieba 官方文档对照
4. 确认能否在 renderer 进程调用（走 IPC），还是必须在主进程

**验收子项**：
- [ ] `tag()` 能正常返回词 + 词性对
- [ ] 标签覆盖常见词性（名/动/形/副/代/介/连/助/标点）
- [ ] 在主进程可稳定调用，无崩溃

#### 步骤 1.2：粗归并逻辑实现（0.5 天）

根据总纲 3.2 的归并表，实现词性 → 4 大类的映射：

| 大类 | 包含词性标签 |
|---|---|
| 实体类 | n、nr、ns、nt、nz、nl、r、s… |
| 动作类 | v、vd、vn、vshi、vyou… |
| 修辞类 | a、ad、an、d… |
| 工具类 | p、c、u、uj、ul、ud、ug、w、x… |

1. 编写 `tagToCategory(tag: string): Category` 函数
2. 对边界 case（成语、简称、量词、方位词）做归类决策并记录
3. 写单元测试覆盖 30 个典型词

**验收子项**：
- [ ] 归并函数对 30 个典型词全部正确归类
- [ ] 边界 case 有明确的归类决策记录

#### 步骤 1.3：样章准确率统计（1 天）

1. 选取《红楼梦》第 2 回中连续 500 字作为基准样本
2. 运行 jieba tag()，输出所有词元
3. 人工标注 200 个词（按均匀分布抽取：名词 50、动词 40、形容词 20、副词 15、代词 15、介词 15、连词 10、助词 10、标点 25）
4. 计算两个准确率：
   - **细颗粒准确率**：原始词性标签的正确率
   - **粗归并准确率**：4 大类归类的正确率

**验收子项**：
- [ ] 200 词人工标注完成，有标注表格
- [ ] 细颗粒准确率有数据（预期 80%–90%）
- [ ] 粗归并准确率 ≥ 95%（核心通过标准）

### 失败应对
- 若粗归并准确率 < 90%：检查归并表是否合理，是否需调整边界归类；考虑加入"小说人名词典"叠加
- 若接口不可用或崩溃：评估切换到 `nodejieba` 或纯 JS 分词方案的成本

### 产出物
- `poc1_jieba_tag.ts` 验证脚本
- `poc1_accuracy_report.md` 准确率报告（含 200 词标注表）
- 词性 → 大类映射表（最终版）

## POC-2：decorations 八维渲染可行性

### 目标
验证 Monaco Editor 的 decorations（inline CSS）能否承载 8 个视觉维度，且视觉效果正确、无明显排版异常。

### 前置准备

| 项 | 说明 |
|---|---|
| 参考代码 | `src/renderer/src/monaco/readerInlineDecorations.ts`（现有 decoration 用法） |
| 测试环境 | 在现有阅读器中开一个 POC 模式，或独立 demo 页面 |
| 字体确认 | 思源黑体 SC 7 档字重已可用（`presetFontDefinitions.ts`） |

### 执行步骤

#### 步骤 2.1：decoration 模板搭建（0.5 天）

1. 在 `src/renderer/src/omni-poc/` 下新建 `poc2_decorations.ts`
2. 创建一个测试函数：给定一段文本和一组 range+style，生成 decorations 并应用到 Monaco
3. 验证基本的 `deltaDecorations` 调用是否正常

**验收子项**：
- [ ] 能通过代码向 Monaco 添加自定义 decoration
- [ ] decoration 的 range 定位准确
- [ ] 移除 decoration 正常

#### 步骤 2.2：逐维度验证（1 天）

对 7 个维度（除字间距，留到 POC-3）逐一验证：

| # | 维度 | CSS 属性 | 验证方法 | 通过标准 |
|---|---|---|---|---|
| 1 | 颜色 | `color` | 给"宝玉"标红色 | 颜色正确显示 |
| 2 | 字重 | `font-weight` | 给名词设 700，动词设 500，工具词设 300 | 字重差异清晰可见，200–900 各档均生效 |
| 3 | 倾斜 | `font-style: italic` | 给外文/心理活动设斜体 | 斜体正常，不影响行高 |
| 4 | 字宽 | `font-stretch` | 测试思源黑体是否支持；若不支持，用 CSS `transform: scaleX()` 替代方案 | 字宽变化可见，不导致严重错位 |
| 5 | 装饰线 | `text-decoration` | 下划线 + 波浪线 + 删除线，各换颜色 | 线型/颜色/粗细均可控 |
| 6 | 背景色 | `background-color` | 给自定义标注词加底色 | 背景色正确，不挤压行高 |
| 7 | 发光阴影 | `text-shadow` | 给主角名加 2px 模糊发光 | 发光可见，性能无断崖式下降 |

**关键验证点**：
- 多维度叠加在同一个词上是否正常（如：颜色 + 字重 + 下划线 + 背景同时加在一个词上）
- 行高是否稳定（背景色/装饰线不应撑大行高）
- 光标是否能正确定位到 decoration 修饰的文字上

#### 步骤 2.3：样式类预编译验证（0.5 天）

1. 实现一个 `compileClass(styleObj)` 函数，将样式对象编译为唯一 CSS class
2. 验证：相同样式组合复用同一个 class，decoration 只引用 class 名
3. 统计：1000 个词、20 种样式组合下，实际生成的 class 数量

**验收子项**：
- [ ] 样式类编译函数工作正常
- [ ] 相同样式复用同一 class（无重复）
- [ ] class 命名稳定（同样式 → 同类名）

### 失败应对
- 若某维度 Monaco 不支持：记录原因，评估是否从 MVP 中移除或寻找替代方案
- 若多维度叠加导致行高错乱：调整 inline CSS 为 `::before/::after` 或其他技巧

### 产出物
- `poc2_decorations.ts` 渲染 demo
- `poc2_screenshots/` 各维度截图
- `poc2_decoration_feasibility.md` 可行性报告（每维度 ✅/⚠️/❌ + 说明）

## POC-3：字间距错位实测

### 目标
量化 `letter-spacing` 在 Monaco 中导致的光标定位、点击命中、自动换行错位程度，决定字间距通道是否开放及开放范围。

### 前置准备
- POC-2 的 decoration 基础已跑通
- 准备一段 500 字的标准测试文本（含中英文混排、标点）

### 执行步骤

#### 步骤 3.1：基础错位测试（0.5 天）

1. 给整段文本统一加 `letter-spacing: 2px`
2. 测试以下交互：
   - **光标点击**：点击第 N 个字的中间，光标是否落在正确位置？偏差多少像素？
   - **选区拖拽**：从第 10 字拖到第 30 字，实际选中范围是否正确？
   - **自动换行**：调整窗口宽度，换行点与无 letter-spacing 时是否一致？
   - **光标移动**：按方向键左右移动，光标步进是否均匀？

3. 分级测试不同字间距：
   - `letter-spacing: 1px`（轻微）
   - `letter-spacing: 2px`（中等）
   - `letter-spacing: 4px`（明显）

#### 步骤 3.2：局部字间距测试（0.5 天）

1. 只给**单个词**加字间距（如给"宝玉"加 `letter-spacing: 4px`），观察：
   - 该行整体是否错位？
   - 光标在该词前后的定位是否偏移？
   - 该行的换行是否受影响？

2. 给**一整行**加字间距（如朗读高亮行），观察：
   - 临时态使用是否可接受？
   - 移除字间距后是否恢复正常？

### 决策矩阵

| 错位程度 | 决策 |
|---|---|
| 无感知（偏差 < 2px） | 全量开放，字间距列为正式通道 |
| 轻微可接受（偏差 2–5px） | 有限开放：仅用于临时态/整行均匀加宽 |
| 严重错位（偏差 > 5px） | 列为红线，常规模式禁用，仅特殊场景谨慎使用 |

### 产出物
- `poc3_letter_spacing_test.md` 测试报告（含偏差量化数据）
- 字间距通道决策结论（开放 / 有限开放 / 禁用）

## POC-4：窗口化 decorations 性能

### 目标
验证窗口化 decoration 策略在大文件（120 章长篇小说）下的滚动性能，确认帧率 ≥ 55 fps。

### 前置准备
- POC-2 的 decoration 渲染已跑通
- 准备测试数据：生成 120 章、每章 5000 字的模拟标注数据（每 10 字一个 decoration）

### 执行步骤

#### 步骤 4.1：全量 decorations 基准测试（0.5 天）

1. 先做最坏情况：将**全部** decorations 一次性挂到 Monaco
2. 用 Chromium DevTools Performance 面板录制滚动 10 秒
3. 记录指标：
   - 平均帧率（fps）
   - 最低帧率
   - 单次滚动帧耗时
   - 内存占用（JS Heap + DOM 节点数）

**预期**：全量模式下性能较差，作为对比基准。

#### 步骤 4.2：窗口化实现与测试（0.5 天）

1. 实现窗口化逻辑：
   - 监听 Monaco `onDidChangeVisibleRanges`
   - 只给「可视区行 + 上下各 50 行缓冲」挂 decorations
   - 滚动时用 `deltaDecorations` 批量更新

2. 同样录制滚动 10 秒，记录相同指标

3. 不同标注密度测试：
   - 低密度：每 20 字一个 decoration（约 5% 覆盖率）
   - 中密度：每 10 字一个 decoration（约 10% 覆盖率）
   - 高密度：每 5 字一个 decoration（约 20% 覆盖率，接近全词标注）

#### 步骤 4.3：样式类预编译性能对比（0.5 天）

1. 对比两种模式：
   - 模式 A：每个 decoration 用 inline CSS（逐词 style）
   - 模式 B：样式类预编译（decoration 引用 class 名）

2. 记录：
   - 初次渲染耗时
   - 滚动刷新耗时
   - 内存差异

### 验收标准

| 指标 | 目标 |
|---|---|
| 中密度滚动帧率 | ≥ 55 fps |
| 高密度滚动帧率 | ≥ 45 fps |
| 可视区 decoration 刷新 | ≤ 16 ms |
| Omni 模块内存增量 | < 150 MB |

### 失败应对
- 若帧率不达标：优化缓冲行数、增加样式类复用、检查是否有不必要的重渲染
- 若内存过高：评估是否将标注数据放 IndexedDB / SQLite，只在内存保留视区附近数据

### 产出物
- `poc4_performance_test.md` 性能报告（含帧率曲线）
- 窗口化 decoration 实现代码（可复用至 α 阶段）
- 性能优化建议清单

## POC-5：transformers POS/NER 对比

### 目标
评估 `@huggingface/transformers` 本地 ONNX 模型做词性标注（POS）和命名实体识别（NER）的准确率、速度、模型体积，与 jieba 做对比，决定是否在 β/γ 阶段引入。

### 前置准备
- 确认 `@huggingface/transformers` ^3.8.1 已安装
- POC-1 的 200 词标注数据可用作对照基准

### 执行步骤

#### 步骤 5.1：模型选型与加载测试（0.5 天）

1. 调研适合中文的轻量 ONNX 模型：
   - POS：`ckiplab/bert-base-chinese-pos` 或更轻量的 distil 版本
   - NER：`ckiplab/bert-base-chinese-ner` 或 `uer/roberta-base-finetuned-cluener2020-chinese`
2. 尝试加载模型，记录：
   - 模型文件大小
   - 首次加载耗时
   - 内存占用增量

#### 步骤 5.2：准确率对比（0.5 天）

1. 用 POC-1 的同一段 500 字文本，分别跑：
   - jieba tag()
   - transformers POS 模型
2. 以人工标注的 200 词为基准，分别计算准确率
3. 对比两者不一致的词，分析错误类型分布

**额外验证 NER**：
- 用 transformers NER 模型识别人名（PER）
- 对比"角色识别"的词频法，看哪个更准确

## 验收与决策

### POC 全部完成后的 Go/No-Go 决策

| 决策项 | Go 条件 | No-Go 后果 |
|---|---|---|
| POC-1 粗归并准确率 | ≥ 93% | 词性标注方案需重做，评估引入 transformers 或换分词器 |
| POC-2 核心维度（颜色/字重/倾斜/背景/装饰线） | 全部 ✅ | 渲染方案需调整，评估是否换编辑器内核 |
| POC-3 字间距 | 至少有限开放可用 | 字间距从 8 维移除，剩 7 维（可接受） |
| POC-4 中密度帧率 | ≥ 50 fps | 需额外投入性能优化，推迟 α 阶段 |
| POC-5 transformers | 准确率显著优于 jieba 则纳入路线图 | β 阶段不引入，纯 jieba 方案 |

### 决策会议议程

1. 逐项过 POC 结果（演示 + 数据）
2. 讨论风险项的应对方案是否充分
3. 决定是否进入阶段 1（万维 α）
4. 若 Go：确认 α 阶段的范围裁剪（哪些维度先上、哪些后上）
5. 若 No-Go：明确卡在哪一项、下一步行动是什么
