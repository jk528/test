# 提示词控制软件每日开发计划

> 基于：维读提示词控制需求规格（spec.md）、红楼梦范例教训、彩读依赖经验
> 核心理念：用提示词控制阅读方式，大模型辅助配置与自打磨，框架留扩展性
> 日期：2026-10-18

---

## 一、核心概念

### 1.1 提示词控制

用户输入自然语言提示词（如"用情感着色分析这一回的人物，展示关系图"），系统解析为结构化阅读配置：

```
提示词 → [本地规则预解析 / 大模型解析] → 阅读配置(阅读模式 × 分析维度 × 展示方式 × 参数)
```

### 1.2 维度体系

| 维度分类 | 说明 | 示例取值 |
|----------|------|----------|
| 阅读维度 | 阅读的方式 | 精读 / 泛读 / 略读 / 研读 |
| 分析维度 | 分析的方面 | 情感 / 人物 / 事件 / 伏笔 / 关系 / 词频 |
| 展示维度 | 展示的形式 | 着色 / 角色卡 / 时间线 / 关系图 / 词云 / 思维导图 |
| 交互维度 | 交互的方式 | 选区即分析 / 浮动工具条 / glyph margin标记 |

### 1.3 框架与动态内容分离

```
骨架层（稳定，维护者管理）
  ├─ 扩展点定义
  ├─ 接口契约
  └─ 调度核心
内容层（可变，大模型自打磨）
  ├─ 提示词模板
  ├─ 分析参数
  └─ 展示规则
```

### 1.4 大模型自打磨

在框架骨架约束下，大模型可以：
- 自动优化提示词模板（提高解析准确率）
- 调整分析参数（适应不同文本类型）
- 生成展示规则（新的着色方案、布局规则）
- **但不能修改扩展点定义和接口契约**（骨架不可变）

## 三、每日开发计划

### Phase 0：框架骨架搭建（Day 1–3）

#### Day 1：扩展点系统设计

**目标**：定义扩展点契约接口，搭建骨架层

**任务**：
1. 定义 `ExtensionPoint` 接口（标识、契约版本、注册接口）
2. 定义 `DimensionContract` 接口（元数据、校验规则、执行入口）
3. 定义四类维度基类（阅读/分析/展示/交互）
4. 搭建骨架层目录结构（skeleton/ vs content/）

**交付物**：
- `skeleton/extension_point.ts` — 扩展点基类
- `skeleton/dimension_contract.ts` — 维度契约接口
- `skeleton/dimension_types.ts` — 四类维度枚举

**验收**：扩展点可定义、契约可声明、骨架层与内容层物理分离

#### Day 2：维度注册中心

**目标**：实现维度注册、发现、校验机制

**任务**：
1. 实现 `DimensionRegistry`（注册/查询/禁用/注销）
2. 实现契约校验器（元数据完备性、取值合法性、签名验证）
3. 实现维度发现接口（供提示词解析器枚举可用维度）
4. 编写注册中心单元测试

**交付物**：
- `skeleton/registry.ts` — 维度注册中心
- `skeleton/contract_validator.ts` — 契约校验器

**验收**：维度可注册、可查询、可禁用；未通过校验的维度被拒绝

#### Day 3：调度核心

**目标**：实现维度调度器，协调多维度执行

**任务**：
1. 实现 `Scheduler`（接收阅读配置 → 调度各维度执行 → 汇总结果）
2. 实现维度隔离机制（单维度异常不影响其他维度）
3. 实现维度间通信协议（通过调度器，禁止直接调用）
4. 编写调度核心集成测试

**交付物**：
- `skeleton/scheduler.ts` — 调度核心
- `skeleton/isolation.ts` — 异常隔离

**验收**：多维度可并行调度、单维度异常被隔离、维度间通过调度器通信

### Phase 1：提示词解析引擎（Day 4–7）

#### Day 4：本地规则解析器

**目标**：实现基于规则匹配的本地提示词解析

**任务**：
1. 定义提示词规则格式（关键词 → 维度取值映射）
2. 实现规则匹配引擎（关键词提取 → 维度匹配 → 配置生成）
3. 实现缺失字段默认填充（基于历史偏好/全局默认）
4. 实现歧义检测（多义提示词返回候选选项）

**交付物**：
- `parser/local_parser.ts` — 本地规则解析器
- `parser/rules/` — 规则定义文件

**验收**：输入"情感着色分析人物"→ 输出分析维度=情感+人物、展示维度=着色

#### Day 5：大模型解析器

**目标**：实现大模型辅助的提示词解析

**任务**：
1. 定义大模型解析请求格式（提示词 + 维度注册表摘要 → 结构化配置）
2. 实现大模型调用客户端（支持多服务商：火山方舟/DeepSeek/Ollama）
3. 实现提示词净化（防注入）
4. 实现解析结果校验（通道组合合法性）

**交付物**：
- `parser/llm_parser.ts` — 大模型解析器
- `parser/sanitizer.ts` — 提示词净化

**验收**：大模型返回配置通过校验；含注入的提示词被净化

#### Day 6：降级与回溯机制

**目标**：实现大模型不可用时的降级与配置历史

**任务**：
1. 实现降级策略（大模型失败 → 本地规则解析 + 用户提示）
2. 实现解析历史记录（输入/命中路径/生成配置/是否采纳）
3. 实现配置撤销与重做
4. 编写降级场景测试

**交付物**：
- `parser/fallback.ts` — 降级策略
- `parser/history.ts` — 解析历史

**验收**：大模型不可用时自动降级；配置可撤销重做

#### Day 7：解析引擎集成

**目标**：整合本地+大模型+降级为完整解析管线

**任务**：
1. 实现解析管线编排（本地预解析 → 命中则返回 / 未命中则大模型 → 失败则降级）
2. 实现解析性能监控（耗时/命中率/降级率）
3. 编写端到端解析测试
4. 编写解析引擎使用文档

**交付物**：
- `parser/engine.ts` — 解析引擎入口
- `parser/README.md` — 使用文档

**验收**：完整解析管线可用；性能达标（本地≤200ms，大模型≤3s）

## 四、关键设计决策

### 4.1 为什么用提示词而非手动配置

| 方式 | 问题 | 提示词方案 |
|------|------|-----------|
| 手动配置 | 8+ 通道组合，N 个维度 × M 个取值 = 组合爆炸 | 一句话描述意图 |
| 手动配置 | 新用户不知道有哪些维度 | 提示词自然语言，降低认知负担 |
| 手动配置 | 每次切换要翻多层菜单 | 提示词即时切换 |

### 4.2 为什么框架与内容分离

```
骨架（稳定）           内容（可变）
├─ 扩展点定义          ├─ 提示词模板
├─ 接口契约            ├─ 分析参数
├─ 调度核心            └─ 展示规则
└─ 维度注册中心
     ↑                    ↑
  维护者管理           大模型自打磨
  人工评审             灰度发布
  版本化               可回滚
```

**原因**：
- 骨架变更影响所有维度，需人工评审
- 内容变更只影响单个维度，可自动化
- 大模型擅长生成内容（模板/参数/规则），不擅长设计架构

### 4.3 为什么留多后端扩展性

| 后端 | 优势 | 劣势 |
|------|------|------|
| Tauri | 体积小（≤60MB）、Rust 壳安全 | 原生集成成本高 |
| Electron | 生态成熟、彩读已验证 | 体积大（137MB） |

**策略**：框架核心不绑定后端，通过适配接口支持切换。默认 Tauri，退路 Electron。

### 4.4 为什么大模型只打磨内容不改骨架

- **安全**：骨架变更可能破坏所有已注册维度
- **可控**：内容变更可灰度可回滚，骨架变更不可逆
- **职责**：大模型擅长模式生成，不擅长架构设计
- **信任**：骨架由维护者人工评审，内容可自动验证

## 五、风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 大模型解析准确率不足 | 中 | 高 | 本地规则兜底 + 自打磨持续优化 |
| 维度组合冲突 | 中 | 中 | 通道组合校验 + 冲突提示替代方案 |
| 性能不达标 | 低 | 高 | 架构级预防（视口化/预处理/惰性加载） |
| 自打磨产出退化 | 中 | 中 | 质量退化检测 + 自动阻断 + 回滚 |
| 扩展点版本不兼容 | 低 | 高 | 语义化版本 + 兼容性校验 |

## 六、总结

本计划用 28 天（6 个阶段）从零搭建维读提示词控制软件：

1. **Phase 0（骨架）**：扩展点 + 注册中心 + 调度核心
2. **Phase 1（解析）**：本地规则 + 大模型 + 降级
3. **Phase 2（维度）**：四类维度各 2–3 个实现
4. **Phase 3（自打磨）**：大模型在契约内优化内容
5. **Phase 4（后端）**：Tauri + Monaco + 视口化装饰
6. **Phase 5（性能）**：预处理 + 惰性加载 + 监控
7. **Phase 6（扩展性）**：新维度/多后端/自打磨验证

核心原则：**骨架稳定留扩展性，内容可变由大模型自打磨，提示词一句话控制阅读方式**。
