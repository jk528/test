# M2 卡顿问题分析与解决方案

> 依据：红楼梦范例项目实测数据、优化作战清单、架构偏差分析报告
> 日期：2026-10-18

---

## 一、问题现象

红楼梦范例项目在 M2（接上析）阶段出现明显卡顿，具体表现为：
- 翻章时界面冻结数秒
- 情感着色渲染时帧率骤降
- 大文本（2.57MB / 3366 段）首屏白屏时间长
- 人物高亮（30027 条）导致 Monaco 装饰系统过载

---

## 二、五大根因分析

### 根因 1：sidecar 启动加载开销

| 维度 | 详情 |
|------|------|
| 现象 | sidecar 启动时需加载 jieba 词典 + EmotionAnalyzer 初始化 |
| 根因 | 依赖初始化集中在启动时刻，无延迟加载机制 |
| 影响 | 首次打开书籍时等待感强 |
| 状态 | ⚠️ 未完全解决 |

**解决方案**：
- 延迟加载：jieba 在首次分词请求时才加载，而非 sidecar 启动时
- 预热机制：sidecar 启动后后台异步预热，不阻塞主流程
- 分级加载：核心引擎先加载，非核心引擎按需加载

### 根因 2：翻章实时分析

| 维度 | 详情 |
|------|------|
| 现象 | 每翻一章实时计算情感分析 |
| 根因 | 无预处理机制，分析在阅读时同步执行 |
| 影响 | 翻章时界面冻结 |
| 状态 | ✅ **M4.5 已解决** |

**M4.5 解决方案**（已落地）：
- 全书 3366 段段落级情感 + 120 章级汇总一次性入库
- 首跑 13.6s（仅首次），后续秒回 0.011s
- 缺章增量补，库-实时等价性零差异
- 阅读时直接吃库，不再实时算

**经验提炼**：**分析前置是解决实时卡顿的根本方案**。把计算从"阅读时"移到"开书时"，用一次性预处理换取阅读时的零延迟。

### 根因 3：装饰全量渲染（最严重）

| 维度 | 详情 |
|------|------|
| 现象 | 人物 30027 条 + 情感 3366 行一次性渲染 |
| 根因 | Monaco decorations 无视口化，全量注册 |
| 影响 | 帧率骤降，滚动卡顿，内存占用高 |
| 状态 | ⏳ 待解决（OPT-1） |

**解决方案（OPT-1）**：
```
核心思路：仅渲染可见视口 ± 缓冲区域的装饰

实现要点：
1. 监听 Monaco onScroll 事件
2. 计算当前可见行范围 [firstVisibleLine, lastVisibleLine]
3. 扩展缓冲区 ±50 行
4. 从全量数据中筛选落在缓冲区内的装饰
5. 调用 deltaDecorations 增量更新（只增删差异部分）
6. overview ruler（右侧滚动条缩略图）保留全量 collection
```

**预期收益**：人物 30027→~200（-99%），帧率↑ 数量级

**工作量**：1–2 天

### 根因 4：每段一个 decoration

| 维度 | 详情 |
|------|------|
| 现象 | 全书 3366 段≈3366~6732 个 decoration |
| 根因 | 段距、首行缩进用 decoration 逐段实现 |
| 影响 | decoration 数量与段数线性增长，大文本过载 |
| 状态 | ⏳ 待解决（OPT-2） |

**解决方案（OPT-2）**：
```
核心思路：用 CSS/ViewZone 替代逐段 decoration

实现要点：
1. 段间距 → 改写 Monaco LinesLayout（参考彩读 v3.4 方案）
   - 每个物理行结束后增加常数像素空隙
   - 同一物理行因软换行产生的多行之间不加距
   - 额外状态 O(1)，与段数无关
2. 首行缩进 → CSS text-indent
   - 通过 Monaco 的 CSS 类直接应用
   - 无需逐段创建 decoration
3. 情感着色 → 保留 decoration（必须逐行着色）
   - 但配合 OPT-1 视口化
```

**预期收益**：减少 6000+ 装饰，降渲染压力

**工作量**：1 天

**彩读参考**：彩读 v3.4 正是用 Vite transform 改写 Monaco LinesLayout 实现段间距，是已验证的方案。

### 根因 5：初始帧全量渲染

| 维度 | 详情 |
|------|------|
| 现象 | 初始帧渲染范围 `[0, Infinity]` |
| 根因 | 无惰性渲染，Monaco 默认全量 |
| 影响 | 超大文本（10 万+行）首帧卡顿/白屏 |
| 状态 | ⏳ 待解决（H2） |

**解决方案（H2）**：
```
核心思路：首帧按预估视口惰性渲染

实现要点：
1. 文档加载后不立即 setValue 全量
2. 首帧仅渲染预估视口范围（如前 100 行）
3. 后续行通过 ViewZone 或虚拟滚动按需加载
4. 章节树/搜索等全量索引在后台异步构建
```

**工作量**：需与 OPT-1 协同设计

## 四、性能红线（维读框架应继承）

基于红楼梦范例的教训，维读框架应设定以下性能红线：

| 指标 | 红线 | 依据 |
|------|------|------|
| 装饰渲染 | ≤16ms（60fps） | OPT-1 视口化保证 |
| 全书预处理首跑 | ≤15s（3000~3500 段） | M4.5 实测 13.6s |
| 预处理后秒回 | ≤50ms | M4.5 实测 0.011s |
| 提示词解析 | ≤3s（含大模型往返） | 用户体验红线 |
| 本地回退解析 | ≤200ms | 大模型不可用时兜底 |
| 维度注册查询 | ≤10ms | 扩展点响应红线 |

## 五、架构级预防措施

维读框架在设计时应从架构层面预防卡顿，而非事后优化：

### 5.1 分析前置原则
- 所有分析任务在"开书时"预处理，而非"阅读时"实时算
- 预处理结果入库，阅读时直接查库
- 缺失数据增量补算，不重算全量

### 5.2 渲染视口化原则
- 装饰系统默认视口化，禁止全量渲染
- overview ruler 保留全量 collection（缩略图不卡）
- 滚动时增量更新装饰（deltaDecorations）

### 5.3 装饰最小化原则
- 优先用 CSS/ViewZone 实现排版效果，而非 decoration
- decoration 仅用于必须逐行/逐字着色的场景（如情感着色）
- 段距、缩进、行距等用 LinesLayout 改写

### 5.4 惰性加载原则
- 首帧仅渲染可见区域
- 分析引擎按需加载，不集中启动
- 大文件流式读取，不全量载入内存

---

## 六、总结

M2 卡顿的五大根因中，**根因 2（翻章实时分析）已由 M4.5 预处理方案解决**，剩余四个根因需要在维读框架设计时从架构层面预防：

1. **装饰视口化**（OPT-1）是 ROI 最高的优化，帧率可提升数量级
2. **CSS/ViewZone 替代 decoration**（OPT-2）从源头减少装饰数量
3. **惰性首帧**（H2）解决大文本白屏
4. **sidecar 延迟加载**解决启动开销

核心经验：**性能问题应从架构层面预防，而非事后补救**。维读框架应将"分析前置、渲染视口化、装饰最小化、惰性加载"作为设计原则，而非优化阶段才考虑。
