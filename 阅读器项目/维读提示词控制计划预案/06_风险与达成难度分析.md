## 三、关键难点深度分析

### 3.1 难点一：大模型自打磨的契约守卫与骨架保护

| 维度 | 内容 |
|------|------|
| 难点描述 | Phase 3 需在 4 天内实现大模型在契约约束下自打磨维度内容，同时保证骨架不可变。spec 5.2.1 规则 4 + 禁止项 + 5.5.1 禁止项共 3 条约束，需拦截"修改扩展点定义/接口契约/调度核心/注册中心/后端适配接口"5 类越权 |
| 为什么难 | (1) 越权场景枚举不全——大模型产出是自由文本，越权方式不可穷举（如间接修改、语义等价改写）；(2) 契约校验需覆盖字段缺失/类型错误/取值越界/签名不符等多维，JSON Schema 仅能校验结构不能校验语义；(3) 红楼梦范例 B1 已证明大模型链路脆弱，自打磨依赖大模型可用性 |
| 可能的解决路径 | (1) 内容层与骨架层物理隔离（不同目录 + 文件系统权限），自打磨引擎仅对 content/ 有写权限；(2) 契约校验用 JSON Schema 做结构校验 + 维度契约 validate() 做语义校验双层；(3) 越权检测用白名单——自打磨产出仅允许指定字段，其余字段变更一律拒绝 |
| 失败的后果 | 骨架被修改 → 所有已注册维度可能破坏 → 框架稳定性丧失 → 回滚不可逆（骨架变更不可回滚，spec 5.5.1 规则 4） |
| 建议的降难策略 | Phase 3 先实现提示词模板自打磨（仅改关键词映射，最安全），分析参数/展示规则自打磨延后。契约守卫先用结构校验，语义级越权检测标注为 TODO |

### 3.2 难点二：装饰视口化与性能红线达成

| 维度 | 内容 |
|------|------|
| 难点描述 | Phase 4 Day 19 需 1 天实现装饰视口化，保证 30000+ 装饰不卡顿、帧率 ≥60fps。spec 4.1 规则 4 要求单次可见区域装饰渲染 ≤16ms |
| 为什么难 | (1) 红楼梦范例 OPT-1 至今未落地（02 文档 ⏳ 待解决），说明 1–2 天工作量估计偏乐观；(2) 视口化需协同 onScroll 监听 + 可见行计算 + 缓冲区 ±50 行 + deltaDecorations 增量更新 + overview ruler 全量 collection，5 个机制耦合；(3) 滚动时增量更新的 diff 算理易引入 bug（装饰闪烁/遗漏） |
| 可能的解决路径 | (1) 直接参考 02 文档 OPT-1 方案的 6 步实现要点；(2) overview ruler 用独立 collection 不参与视口化（缩略图不卡）；(3) 缓冲区用常数 ±50 行，不做动态预测；(4) 增量更新用 Monaco deltaDecorations 原生 API，不自建 diff |

### 5.3 建议的调整方向

#### 建议一：范围裁剪（优先级最高）

v1 聚焦最小可用闭环，以下功能延至 v2：

| 裁剪项 | 原计划阶段 | 延后理由 |

| 浮动工具条/glyph margin | Phase 2 Day 12 | 红楼梦范例场景 3/4 仅 20%，交互维度复杂度高 |
| 分析参数/展示规则自打磨 | Phase 3 Day 13 | 先做提示词模板自打磨（最安全），其余延后 |
| 第三方维度包签名验证 | Phase 6 Day 25 | v1 无第三方维度，签名验证无对象 |

### 5.4 结论

**维读提示词控制软件 28 天开发计划可行性为"中低"，主要约束在工程风险（工期 + 单人）与依赖风险（大模型 API + 原生模块）。**

技术方案本身设计合理（骨架/内容分离、扩展点体系、性能红线预防均有依据），但 28 天单人完成全栈的工期与彩读 5 个月基准差距显著。建议采用"**范围裁剪 + 工期调整**"组合策略：

- **乐观路径**：范围裁剪 30% + 28 天严格按门禁推进 → 可交付 v1 最小可用闭环
- **稳健路径**：范围裁剪 30% + 工期扩展至 42 天 → 可交付 v1 + 部分扩展性验证
- **保守路径**：不裁剪 + 工期扩展至 56 天 → 可交付完整 v1

**推荐稳健路径**：裁剪 Electron 后端/关系图/浮动工具条/分析参数自打磨/签名验证，工期扩展至 42 天，性能监控与 dimension_development 文档前置。此路径下总体风险等级可降至 🟡 中，达成难度降至 ⭐⭐⭐（中等）。
