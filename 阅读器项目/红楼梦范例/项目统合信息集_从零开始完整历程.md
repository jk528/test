## 第一部分：项目起源与最初架构

### 1.1 项目目标

做一款**「阅读 × 分析」一体化**的古典小说桌面软件，以《红楼梦》为样板。

核心理念：
- 不是纯阅读器（如 ColorTxt）
- 不是纯分析器（如各种 NLP 报告）
- 而是**分析结果画回正文，阅读时就地感知**

### 1.2 技术选型（ADR-000）

| 层 | 选型 | 理由 |
|----|------|------|
| 桌面壳 | Tauri 2 | 包体小（~10MB），Rust 安全，Web 前端 |
| 前端 | Vue 3 + TypeScript + Vite | 生态成熟，开发效率高 |
| 文本渲染 | Monaco Editor | 装饰系统强大，支持 glyph margin / overview ruler / sticky scroll |
| 后端 | Python sidecar | NLP 生态无可替代，情感/分词/向量库都在 Python |
| 进程通信 | stdio JSON-RPC（NDJSON） | 零配置、跨平台、流式、可取消 |
| 存储 | SQLite + sqlite-vec | 结构化 + 向量一体化，无需外部服务 |
| 向量模型 | BGE-small-zh-v1.5 | 中文效果好，512 维，体积小 |

**为什么不用 Electron？** 包体 100MB+，超出 60MB 目标。
**为什么不用 WASM 跑 Python？** NLP 库（jieba / sklearn / sqlite-vec）WASM 兼容差，性能差。
**为什么 Monaco 不是 CodeMirror？** Monaco 的装饰系统、StickyScroll、OverviewRuler 都是工业级成熟方案，ColorTxt 已验证可行性。

### 1.3 原计划里程碑（V1.0 设计方案）

```
M0 搭环境    → M1 读起来    → M2 接上析    → M3 会回答
    ↓             ↓              ↓              ↓
M5 打得包    ← M4 全景分析  ← M4.5 全书预处理
                                （后追加：先全量分析入库，再进 M4 可视化）
```

| 里程碑 | 核心交付 |
|--------|---------|
| M0 | Python/Node 环境 + venv + Tauri 工程骨架 |
| M1 | Monaco 阅读器 + 章节树 + 书签/高亮/笔记 + 编码识别 + 排版主题 |
| M2 | 统一锚点 + 情感着色 + 人物高亮 + A1/A2 接入 |
| M3 | 选区问 AI + 混合检索 + 答案锚点 |
| M4 | 事件/伏笔/角色卡/可视化 + 导出 |
| M4.5 | 全书情感/事件/人物/伏笔/关系 全量预处理入库（后追加） |
| M5 | 单安装包 ≤ 60 MB |

### 1.5 统一锚点原则（架构基石）

> 所有持久化数据锚定**物理行**——磁盘原文的行号，永不改变。

- 书签、高亮、笔记 → 存物理行号
- 情感分析结果 → 存物理行偏移
- 人物出场 → 存物理行 + 字符偏移
- 事件锚点 → 存物理行
- 伏笔起收 → 存物理行

显示层怎么折腾（简繁转换、替换规则、硬换行重排）都不影响数据层——这是整个系统的地基。

### 2.3 阅读尺（视觉行级）

**原计划**：简单的单行聚焦。
**实际实现**：升级为**视觉行级**，支持软换行后的精准定位。

核心算法：
- `getTopForPosition(line, col)` 获取字符 top 坐标
- **二分查找**同一 top 值的最左列 → 找到视觉行起始位置
- `stepVisualLine` 上下移动一个视觉行
- `collectFocusBand` 收集 N 行聚焦带（当前 3 行，中间行最亮，上下渐暗）
- 跳过空行（自动落到下一个有内容的视觉行）

```
  聚焦带（3 行）：
  ┌──────────────────────┐
  │  上一行（暗色）       │ ← rulerAnchor - 1 视觉行
  │  当前行（最亮）       │ ← rulerAnchor
  │  下一行（暗色）       │ ← rulerAnchor + 1 视觉行
  └──────────────────────┘
```

键盘导航：
- `Ctrl/Cmd + ↑/↓`：上一/下一视觉行
- `Ctrl/Cmd + PageUp/PageDown`：上一/下一段落（跳 5 行）
- `Ctrl/Cmd + Home/End`：文首/文末

### 2.4 粘性章节条（StickyScroll）

**方案选型**：
- ❌ 自己实现绝对定位的浮条（复杂，滚动同步易抖）
- ✅ Monaco 内置 `StickyScroll` + `DocumentSymbolProvider`（原生，丝滑）

实现方式：
- 注册 `registerDocumentSymbolProvider('plaintext', ...)`
- 把章节列表转为 `DocumentSymbol[]`（Namespace 类型）
- Monaco 自动管理粘性条：滚动时当前章节标题粘在顶部，多层章节能堆叠

**注意事项**：
- `registerDocumentSymbolProvider` 是**全局**注册（按 language id）
- 单 reader 架构没问题，多 reader 需自定义 language id
- 章节变化时要先 dispose 旧 provider 再注册新的，否则会叠加
- 用 `stickyScroll.enabled = false → rAF → true` 强制刷新

### 2.5 段间距 + 行首缩进

**技术选型**：
- ❌ 修改文本内容（破坏行号映射）
- ✅ Monaco decoration（行级 className + CSS 控制）

实现方式：
- 段落首行加 `hl-para-spacing` 类 → CSS `padding-top` 实现段间距
- 段落首行第一个字符加 `indent-first-char` 类 → CSS `padding-left` 实现缩进
- 段落首行检测：空行之后的非空行 / 章节标题之后的第一行

### 2.6 全文搜索（查找栏）

**方案**：Monaco 内置 `model.findMatches()`
- 底层 Boyer-Moore 算法，性能优秀
- 支持大小写切换
- 结果计数 + 当前第 N 个
- 上一个/下一个跳转
- 右侧 overview ruler 显示全书分布

键盘快捷键：`Ctrl/Cmd + F` 打开查找栏，`Enter` 下一个，`Shift+Enter` 上一个。

### 2.7 阅读进度

底部进度条 + 百分比文字，基于 `visibleRanges.endLineNumber / totalLines` 计算。
平滑滚动时进度条实时更新。

## 第四部分：6 项性能优化

### OPT-1：视口化装饰渲染

**问题**：30000+ 人物出场 + 3366 情感行 + 全量 decoration → DOM 节点爆炸 → 滚动卡顿。

**方案**：只有视口 ± 缓冲（80 行）范围内的装饰才渲染。

```
全量渲染（旧）：30,000+ DOM 节点
视口渲染（新）：~200 DOM 节点（视口 ~40 行 × 每行列几个装饰）
```

**双集合架构**（P0-1 修复后）：
- `decoColl`：行内装饰，视口化（减少 DOM）
- `overviewColl`：右侧概览栏标记，全量（用户需要看到全书分布）

**视口缓冲**：上下各 80 行，避免快速滚动时出现短暂空白。

### OPT-2：概览栏全量标记

人物高亮和查找结果的右侧 overview ruler 必须全量渲染——这是用户感知"全书分布"的核心。
视口化只作用于行内 inline 装饰，不作用于 overviewRuler。

### OPT-3：视觉行级阅读尺

见 §2.3。核心价值：长行软换行后，阅读尺不再跳整段，而是按视觉行精准移动。

### OPT-4：章节二分查找

**原实现**：`chapterAtLine` 线性搜索 O(n)
**优化后**：二分查找 O(log n)

```typescript
export function chapterAtLine(chapters: Chapter[], line: number): number {
  let lo = 0, hi = chapters.length - 1, ans = 0;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (chapters[mid]!.line <= line) { ans = mid; lo = mid + 1; }
    else { hi = mid - 1; }
  }
  return ans;
}
```

120 章的红楼梦提升不明显，但对千章以上的超长篇小说意义重大。

### OPT-5：Monaco 内置 findMatches

**原方案**：自己写正则搜索。
**新方案**：`model.findMatches()` —— Monaco 内置，底层 Boyer-Moore 算法，性能远超手写正则。

### OPT-6：StickyScroll 章节粘性条

见 §2.4。用 Monaco 原生能力替代手写浮条，性能和体验都更好。

### 额外优化：行数组缓存

`renderDecorations` 中段间距检测每次都 `text.split("\n")` → 改为惰性缓存（key = 长度 + 首尾 20 字符），滚动时重复调用从 O(n) 降为 O(1)。

## 第五部分：架构自检与问题修复

### 5.1 自检三层

| 层面 | 检查内容 | 问题数 |
|------|---------|--------|
| 架构层 | 双坐标系一致性 / 装饰分层 / 数据流方向 | 0（双坐标系接入后再次验证一致） |
| 功能层 | 6 项优化交互矩阵 | 2 P0 + 1 P1 |
| 实现层 | 边界情况 / 代码逻辑 / 性能隐患 | 1 P2 |

### 5.2 P0-1：overviewRuler 被视口化

**问题**：视口化改造把人物高亮和查找结果的 `overviewRuler` 也做了视口过滤 → 右侧概览栏只显示视口内的标记，滚动时标记"消失又出现"。

**根因**：装饰集合单一，inline 和 overviewRuler 共享同一视口过滤逻辑。

**修复**：拆分为 `decoColl`（行内，视口化）+ `overviewColl`（概览栏，全量）两个独立集合。

### 5.3 P0-2：StickyScroll Provider 全局注册

**问题**：`registerDocumentSymbolProvider('plaintext', ...)` 全局注册，章节变化时重复注册导致 provider 叠加。

**修复**：
- 注册前先 `stickyProviderDisposable?.dispose()`
- `onBeforeUnmount` 中确保销毁
- 章节变化 watcher 中先销毁再注册
- 用 `enabled: false → rAF → true` 强制 Monaco 重新计算

### 5.4 P1：查找跳转匹配项短暂不显示

**问题**：跳转到视口外的查找匹配项时，平滑滚动过程中匹配项高亮短暂消失。

**根因**：
1. `revealMatch` 中临时扩展视口到目标行 ± 20 行
2. 但 `onDidScrollChange` 在平滑滚动中持续触发，每次重置视口为 `可见 ± 80`
3. 目标行远离当前视口时，滚动中途视口不包含目标行，装饰被过滤掉

**修复**：`forcedVpLine` 机制
- 跳转时设置 `forcedVpLine = targetLine`
- 滚动事件中：若存在 forcedVpLine，视口范围扩展为 `max(可见范围, 目标行 ± 80)`
- 目标行进入可见范围后，自动清除 forcedVpLine

### 5.5 P2：text.split 重复调用

见"额外优化：行数组缓存"。

## 第七部分：双坐标系落地

### 7.1 为什么需要双坐标系

单坐标系（Monaco 直接渲染原文）简单直接，但有局限性：
- 不能做简繁切换
- 不能做自定义替换规则
- 不能做硬换行重排
- 不能做段首空格规范化

双坐标系 = 物理行（原文锚点） + 展示行（屏幕显示） + 双向映射表。
所有标注锚定物理行，显示层怎么折腾都不错位。

### 7.2 核心模块：displayPipeline.ts

```
DisplayPipeline
├── physicalLines: string[]          // 物理行数组（原文）
├── displayLines: DisplayLine[]      // 展示行数组（含映射信息）
│   ├── physicalLine: number         // 来源物理行号
│   ├── physStartCol: number         // 在物理行中的起始偏移
│   ├── physEndCol: number           // 在物理行中的结束偏移
│   └── text: string                 // 展示文本
├── displayText: string              // 完整展示文本（送 Monaco）
└── physToFirstDisplay: number[]     // 物理行 → 第一条展示行映射
```

**坐标转换公式**：
```
展示列 = 物理列 - displayLine.physStartCol
物理列 = 展示列 + displayLine.physStartCol
```

### 7.3 转换函数一览

| 方向 | 函数 | 用途 |
|------|------|------|
| 物理→展示 | `physLineToDisplay()` | 行号转换（装饰渲染） |
| 物理→展示 | `physPosToDisplay()` | 字符位置转换（人物/情感高亮） |
| 物理→展示 | `physRangeToDisplay()` | 区间转换（1:1 映射下返回单段；硬换行重排等 N:1 场景下可能跨多展示行） |
| 展示→物理 | `displayLineToPhys()` | 行号转换（书签保存/视口通知） |
| 展示→物理 | `displayPosToPhys()` | 字符位置转换（选区分析） |

### 7.4 Reader.vue 接入点

**降级策略**：
所有坐标转换处都有 `pipeline ? convert() : direct` 的三元判断——`pipeline` 为 null 时直接退化到单坐标系（物理行=展示行），保证管线未初始化或异常时阅读功能不受影响。

**装饰渲染（物理 → 展示）**：
- 章节标题
- 书签
- 情感行底色 + 字级高亮
- 人物高亮 inline + overviewRuler
- 段间距 + 行首缩进
- StickyScroll DocumentSymbol（章节符号）

> ⚠️ 查找匹配（findMatches）不属此类：`model.findMatches()` 在展示文本上搜索，结果天然是展示行坐标系，无需转换。直接用 Monaco 行号渲染即可。

**用户交互（展示 → 物理）**：
- glyph margin 点击 → 书签保存（行级）
- 滚动视口范围 → 通知外层分析（行级）
- 初始视口补发 → view-range 事件（行级）

> ⚠️ 文本选中（text-selected）当前只传文本内容，不传位置信息，因此未用到字符级的 `displayPosToPhys` 转换。
> 未来若需要"选中一段 → 保存高亮/笔记"的位置锚定，才需要用 `displayPosToPhys` 把展示位置转回物理位置存库。

**对外 API（物理行入参）**：
- `revealLine(physLine0)` —— 滚动到指定物理行
- 所有 props 中的行号都是物理行

### 7.5 第一个转换：段首空格规范化

**问题**：红楼梦原文段落开头有全角空格缩进，加上 CSS 段首缩进后出现"双重缩进"。

**方案**：在展示层去掉行首全角/半角空格，用 CSS 缩进统一控制。

**验证**：39 项单元测试全部通过
- 行映射往返一致性
- 字符偏移转换正确性
- 实体高亮场景验证
- 区间转换正确性

管线架构已就绪，加新转换**只改 `rebuildPipeline` 一个函数**：

## 第九部分：关键决策记录（ADR）

### ADR-000：技术选型总表
- **状态**：✅ 采纳
- **内容**：Tauri 2 / Vue 3 / Monaco / Python sidecar / SQLite+sqlite-vec / BGE-small-zh-v1.5
- **理由**：包体小 + NLP 生态强 + 装饰系统成熟

### ADR-001：Monaco Editor 作为阅读器内核
- **状态**：✅ 采纳
- **理由**：装饰系统成熟、StickyScroll 原生、OverviewRuler 原生、ColorTxt 验证可行
- **替代**：CodeMirror 6 —— 更轻量但生态不如 Monaco

### ADR-002：Tauri + Python sidecar
- **状态**：✅ 采纳
- **理由**：包体小 + Python NLP 生态
- **替代**：纯前端 WASM —— NLP 库兼容差；Electron —— 包体太大

### ADR-003：物理行作为统一锚点
- **状态**：✅ 采纳
- **理由**：标注永不错位，显示层可自由迭代
- **替代**：锚定展示行 —— 文本转换后标注全部错位

### ADR-004：双坐标系（displayPipeline）
- **状态**：✅ 已落地（段首空格规范化）
- **理由**：为简繁/替换/重排等文本转换预留架构空间
- **时机**：段首空格规范化的需求促使提前落地

### ADR-005：全景数据回灌模式
- **状态**：⚠️ 临时方案
- **理由**：先有数据验证交互，再考虑实时计算
- **未来**：A1 分词集成进 sidecar 后改为实时计算

### ADR-006：StickyScroll 用 DocumentSymbolProvider
- **状态**：✅ 采纳
- **理由**：Monaco 原生，丝滑，支持多层堆叠
- **代价**：全局注册，多 reader 有冲突风险（当前单 reader 无碍）
