**在新机器上复现 Python 环境（venv 不随同步，需各机自建）：**


## 四、安装过程中踩过的坑（复装须知）

1. **PowerShell 5.1 无 BOM 中文乱码**
   含中文注释的 `.ps1` 若以「UTF-8 无 BOM」保存，PS5.1 按 GBK 解码导致语法错误。
   解决：脚本统一保存为 **UTF-8 带 BOM**（或注释只用英文）。

2. **Python 幽灵 ARP 注册**
   注册表残留 Python 3.12/3.13 记录，指向已删除的 `B:\pytest\`，winget 误报「已安装」并走升级流程后退出
   （`Found installed package, converting to upgrade flow`，码 `0x8a15002b`），但磁盘上无 python.exe。
   解决：`winget install --id Python.Python.3.12 --force` 强制实装。

3. **Rustup 作用域不兼容**
   winget 1.4 对 `Rustlang.Rustup` 加 `--scope user` 报
   `Installer scope does not match: Unknown != User`（码 `0x8a150010`）。
   解决：去掉 `--scope`；rustup-init 本就默认用户级、免管理员。

4. **winget 版本错觉**
   软件包元数据为 1.19，但 `winget --info` 报 CLI v1.4.11071，**不支持** `--disable-interactivity` 等新参数（传了未报错但需留意）。

5. **机器级安装触发 UAC**
   Node MSI、MSVC BuildTools 为机器级安装，会弹「用户账户控制」，须手动点「是」；
   Python 3.12 用户级安装、Rustup 不弹窗。脚本在非提权会话中运行，靠用户在 UAC 处授权。

6. **PowerShell 执行策略**
   当前环境 `Set-ExecutionPolicy` 报 Security error；用 `-ExecutionPolicy Bypass` 调用脚本可绕开，
   不影响安装。后续 venv 激活见第七节。

7. **Rust 工具链组件残缺（Administrator 机实遇，2026-09-17）**
   现象：`rustup show` 正常，但 `cargo --version` 报
   `the 'cargo.exe' binary ... is not applicable to the toolchain`，
   或 `Missing manifest in toolchain`；工具链 `bin\` 里有 cargo.pdb 却没有 cargo.exe
   （rustc 1.95.0 半成品状态）。
   普通 `rustup component add cargo` 无效（误报 up to date）。
   解决：**整体卸载后强制重装**
   ```powershell
   rustup toolchain uninstall stable-x86_64-pc-windows-msvc
   rustup toolchain install stable-x86_64-pc-windows-msvc --profile default --force
   # 装得 rustc/cargo 1.98.1，6 个组件齐全
   ```

8. **venv 创建时 ensurepip 失败（Administrator 机实遇）**
   现象：`python -m venv` 报
   `Command ... 'ensurepip' ... returned non-zero exit status 1`，
   生成的 venv 里没有 pip（本机 Python 的 ensurepip 引导不可用）。
   解决：**先建无 pip 的 venv，再用 get-pip.py 引导**
   ```powershell
   python -m venv --without-pip "$env:USERPROFILE\.venvs\honglou"
   Invoke-WebRequest https://bootstrap.pypa.io/get-pip.py -OutFile $env:TEMP\get-pip.py -UseBasicParsing
   & "$env:USERPROFILE\.venvs\honglou\Scripts\python.exe" $env:TEMP\get-pip.py
   # 再正常 pip install -r requirements.txt
   ```

9. **VS Installer `setup.exe modify` 不接受 `--wait`**
   直接命令行给已有 BuildTools 补工作负载时，`setup.exe modify ... --wait` 报
   `Option 'wait' is unknown`（该版本 Installer 4.5.35）。
   解决：去掉 `--wait`，用 `--quiet --norestart --nocache` 即可（命令本身会阻塞到结束）；
   本机经此方式把 **VS2026 BuildTools（18）** 补上 `VCTools` + Windows SDK 10.0.26100。

10. **云盘同步目录会锁文件、也会毁数据库（本轮实遇）**
  工程位于华为云盘同步目录。表现：编辑源码时 `EBUSY: resource busy or locked` 反复出现
  （云盘客户端正在扫描/上传该文件）；运行时数据（SQLite + 模型）放在目录内还会被
  多机覆盖、被客户端加锁、白占同步流量。
  **解决：一切"本机环境与本机运行时数据"都放同步目录外** ——
  venv → `%USERPROFILE%\.venvs\honglou`，主库与模型 → `%USERPROFILE%\.honglou`。
  判断标准很简单：**含本机绝对路径的、带二进制伴随文件的、能重新生成的，都不要同步。**

## 五、下载逻辑：什么在什么时候下载，为什么

核心原则：**按里程碑最小化安装；大件按需下载、不进基础环境、更不进安装包。**

### 5.1 下载时间线

```
现在（M0，已完成）
  └─ 基础工具链：Python / Node / Rust / MSVC / WebView2          一次性，约 3–7 GB（主要是 MSVC）
  └─ venv 档A/档B：jieba / openai / pydantic 等                    约 50 MB

M1 搭骨架时（自动发生，无需手动装）
  └─ pnpm 经 corepack 启用                                         几 MB
  └─ @tauri-apps/cli 作为项目 devDependency 安装（不全局装）        随 npm install
  └─ 前端依赖：vue / vite / monaco-editor / typescript 等           约 150–250 MB（node_modules）

首次 pnpm tauri dev / build（自动发生）
  └─ Rust 下载并编译 Tauri 全家桶 crate
     · cargo 注册表/缓存 + 项目 target/                            约 5–6 GB，耗时较长（仅首次；实测本项目 target/ 5.06 GB / 4,216 文件）

M3 进入「会回答」时才装（原估 0.12–0.15 GB，实测偏小，约 0.30 GB）
  └─ onnxruntime（CPU 版，勿装 -gpu）                              约 15–20 MB
  └─ fastembed（含 tokenizers，与 onnxruntime 复用/二选一）         约 40–60 MB
  └─ sqlite-vec                                                    约 1–3 MB
  └─ venv 新增依赖合计（含 numpy/pillow/tokenizers 等 18 个包）     实测约 120 MB
  └─ BGE-small-zh-v1.5 嵌入模型（ONNX，实测 90.4 MB）               首次用 RAG 时下载
     └─ HF 缓存在 Windows 不建符号链接，blobs 与 snapshots 各存一份 → 磁盘占用约 181.6 MiB
  └─ 给本书建向量索引（实测 228 分块 = 3367 行 ÷ RAG_CHUNK_LINES=20）  主库共约 2.81 MB（M3 阶段；M4 回灌后 4.93 MB；M4.5 情感全量后 7.09 MB）
```

### 5.2 为什么 RAG 那套（onnxruntime / 模型）现在不装

1. **M1/M2 用不到**：阅读器、标注、情感着色、人物高亮都走 jieba + 结构化 SQLite 查询，不涉及向量；模型只服务 M3 的语义召回。
2. **产品设计如此**：方案 §5.3 / 风险表明确「模型不进安装包，首次使用 RAG 时按需下载」，并保留「不用 RAG 也能全功能离线分析」的降级路径。
3. **选型 M3 才拍板**：onnxruntime（手写推理）与 fastembed（高层封装、自动管模型下载）二选一，早装可能白装。
4. **它是 Windows pip 易翻车的原生包**：带原生 dll，镜像同步/超时风险高；到时固定版本走官方源专门处理。
5. **Tauri CLI / pnpm 不全局装**：CLI 锁进项目 devDependencies 防版本漂移；pnpm 由 corepack 启用。

### 5.3 M3 一键安装命令（届时执行，现在不要跑）

```powershell
# 在项目根、新终端中
& "$env:USERPROFILE\.venvs\honglou\Scripts\python.exe" -m pip install onnxruntime sqlite-vec fastembed `
  --index-url https://pypi.org/simple
# 模型在首次调用 fastembed 时自动下载（实测 90.4 MB，HF 缓存磁盘占用约 181.6 MiB）；
# 也可提前手动下载放入 fastembed 缓存目录，实现完全离线。
```

**协议与数据契约（已固化）：**

### M3 缺陷修复（2026-09-17 第二轮，bug fix）

本轮以「实测定性」为原则：每个缺陷都先在真实库/真实协议上复现，再改代码。

#### 缺陷 1（P0）· 同一本书被重复入库，检索结果自我重复

| 项 | 内容 |
|---|---|
| 现象 | 提问「贾宝玉梦游太虚幻境」，召回 6 条里前 3 条是**同一段原文的三个副本**（`d=0.743` 重复出现），LLM 上下文被严重稀释 |
| 根因 | `retrieval.book_id_of(source_path, text)` **把源路径掺进了哈希**。同一本书被不同路径读到即生成不同 `book_id`：`C:\…\红楼梦.txt`、`\\?\C:\…\红楼梦.txt`（Rust `canonicalize` 产物）、另一份拷贝 |
| 实测 | `books` 3 条 / `chapters` 360 条（应 120）/ `chunks` 684 条（应 228）；库膨胀到 6.32 MB |
| 修复 | `book_id_of(text)` 改为**纯内容哈希**（先做换行归一化，CRLF/LF 视为同书）。书 = 内容，不是位置 |
| 验证 | `book_id` 稳定为 `d6eefd4f47ba122d`；检索 6/6 满额、去重 6；四个查询全部命中正确章节 |

#### 缺陷 2（P0）· 向量表孤儿行累积，召回数随重建递减

| 项 | 内容 |
|---|---|
| 现象 | 首次建索引后检索正常，但**每次重建都会掉召回** |
| 根因 | `storage.add_chunks()` 只 `DELETE FROM chunks`，**不清 `chunk_vec`**。`chunks` 是 AUTOINCREMENT，重插后拿到全新 id，旧向量行不会消失，变成指向已删除分块的孤儿。KNN 照常命中孤儿，随后的 `JOIN chunks` 再丢弃它们 |
| 实测 | `chunk_vec` 1140 行 / `chunks` 684 行 → 孤儿 456 行；KNN 取 6 行有 2 行是孤儿，实际只返回 4 条；**加 `book_id` 过滤后只剩 2 条** |
| 修复 | ① `add_chunks` 插入前先 `_purge_vectors_of(book_id)`；② 新增 `purge_orphan_vectors()` 与 `maintenance` 方法清理历史遗留；③ `store_embeddings` 的 `INSERT OR REPLACE` 改裸 `INSERT` —— **vec0 虚拟表不支持 OR REPLACE**（实测报 `UNIQUE constraint failed on v primary key`），旧写法靠 id 永不复用才没炸，是个哑弹 |
| 验证 | 孤儿 0；检索 6/6 满额去重 |

#### 缺陷 3（P0）· 索引每次打开书都重建

| 项 | 内容 |
|---|---|
| 根因 | `App.vue` 的 `loadBook` 无条件调 `buildIndex`，不判断库里是否已有 |
| 代价 | 每次开书白跑 228 次嵌入（实测一次全量建索引 108.2s，其中模型下载 67s） |
| 修复 | ① `books` 表加 `index_sig` 列（存「内容 + `RAG_CHUNK_LINES` + 章节结构」签名）+ 老库 `ALTER TABLE` 迁移；② 新增 `index_status` 方法；③ `build_index` 加幂等判断与 `force` 参数；④ 前端先问状态再决定是否重建 |
| 验证 | 二次调用 `skipped=True`，耗时 108.2s → **0.03s** |

#### 缺陷 4（P1）· `storage` 用 `print` 污染 NDJSON stdout（哑弹）

- `_try_load_vec` 的降级日志走 `print(...)`，而 **stdout 是 NDJSON 协议通道**。
- 一旦 sqlite-vec 加载失败（如打包后缺扩展），这行纯文本会插进响应流，Rust 侧 `serde_json::from_str` 解析失败 → **整个 sidecar 通信崩掉**，且表现为「打开书就报错」难以定位。
- 已改 `file=sys.stderr`；用「伪造 sqlite-vec 使 load 抛异常」的方式实测：降级日志正确出现在 stderr，stdout 仍为纯 NDJSON。

#### 缺陷 5（P1）· 情感分析结果不持久化（原待办 3）

- 新增 `storage.upsert_emotions()` + sidecar `upsert_emotions` 方法：**按行增量写、幂等**。
  不能用整章替换 —— 前端是视口驱动分批算的，整章替换会让后到的批次冲掉先前批次。
- `emotions` 表加 `spans_json` 列，**字级情感词位置一并落库**，否则重启后段落底色能回放、字级高亮会丢。
- 前端：开书/切章先 `getChapterEmotions` 回放，只补算缺口；每批分析完 `upsertEmotions` 回写。

#### 缺陷 6（P1）· 书签未迁到 SQLite（原待办 4）

- 前端 `loadBook` 后拉 `listAnnotations(book_id,'bookmark')`；库为空时把 localStorage 存量**一次性迁移**上去；切书签/删书签双写（localStorage 作离线兜底与首屏即时显示）。

#### 缺陷 7（P1）· 运行时数据落在云盘同步目录内

- 原 `app/.data/` 同时放 SQLite 主库与嵌入模型缓存，**位于华为云盘同步目录内**：
  库含本机绝对路径、有 `-wal/-shm` 伴随文件，模型近 181 MB。
  后果：云盘客户端加锁导致读写 `EBUSY`（本轮编辑文件时确实反复撞到）、多机互相覆盖导致库损坏、上百 MB 白占同步流量。
- 修复：新增 `config.DATA_DIR`，默认 `%USERPROFILE%\.honglou`（**同步目录外**，与 venv 同一处理原则），可用 `HONGLOU_DATA_DIR` 覆盖；已把 `app/.data`（281.56 MB）整体迁出并删除同步目录内的旧副本。
- `app/.gitignore` 补 `.data` / `*.sqlite*` / `models/` 兜底。

#### 缺陷 8（P2）· 401 直接抛原始 SDK 报文

- 界面原本显示一长串英文 JSON，用户看不出该改哪里。`llm.py` 新增 `_explain()`，按 401/403/404/429/超时/连接失败分类给出中文可操作提示（含当前 model 与 key 前后缀）。
