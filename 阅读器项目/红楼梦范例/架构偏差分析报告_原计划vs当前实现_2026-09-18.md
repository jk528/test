## 二、架构层偏差（3 项）

### 2.1 🔴 双坐标系：原计划"物理行/展示行" → 当前"物理行单坐标系"

**原计划（V1.0 §1.3 / §3.2）**：
- 完整照搬 ColorTxt 的**物理行 ↔ 展示行双坐标系**
- 物理行 = 磁盘原文，不加工，所有持久化数据锚定于此
- 展示行 = 经过替换规则 / 简繁转换 / 全半角转换后的显示文本，带双向映射表
- 搜索在展示行匹配，再用映射表转回物理行存标注

**当前实现**：
- **单坐标系**：Monaco 直接渲染原文，物理行 ≈ Monaco 行（1:1，仅 0 基 / 1 基差异）
- 阅读尺的"视觉行"是**软换行粒度**（解决长行折行后的阅读定位），不是原计划的"展示行"（解决文本转换）
- 无展示行转换层、无双向映射表、无文本转换功能

**偏差原因**：
- 文本转换（简繁/替换/清理）在当前优先级中较低，先做了核心阅读 + 分析联动
- 阅读尺的视觉行需求比文本转换更紧迫，先实现了软换行粒度的视觉行计算

**影响评估**：
- 短期无影响（当前不需要简繁转换等功能）
- 未来若要加"简繁切换 / 替换规则 / 文本清理"，需补建展示行管线——届时所有标注锚定物理行的设计仍然有效，只需加一层映射

**建议**：保持当前单坐标系，等真的需要文本转换时再加展示行层，避免过度设计。

---

### 2.2 🟡 模块划分：原计划 12 模块 → 当前扁平结构

**原计划（V1.0 §3.1 / §3.5）**：
```
读域 R：R1 章节 / R2 渲染排版 / R3 标注笔记 / R4 阅读辅助
析域 A：A1 分词 / A2 情感 / A3 事件 / A4 人物 / A5 LLM
通域 X：X1 混合检索 / X2 呈现导出 / X3 存储设置
共 12 个模块，职责严格分层
```

**当前实现**：
```
前端：App.vue（总控）+ 5 组件（Reader/ChapterTree/AiPanel/PanoramaPanel/...）
      + 6 个 lib（chapters/monaco/annotations/sidecar/tauri/...）
sidecar：6 个 py（storage/retrieval/llm/analysis_import/honglou_sidecar/config）
```

**偏差说明**：
- 没有严格按 R/A/X 三域 12 模块拆分，而是按功能文件组织
- 部分模块合并了（如 R1 章节解析同时存在前端 chapters.ts 和后端 storage.py 两处）
- 缺少的模块：A1 分词服务、X2 可视化导出、X3 密钥保险库

**影响评估**：
- 代码量尚小（前端 67 文件 / sidecar 6 文件），扁平结构反而更易维护
- 等模块数增长到 20+ 时再考虑严格分层不迟

## 三、读域偏差（R1–R4）

### 3.1 🟡 R1 章节识别与切分：双模式未统一

**原计划（V1.0 §2.3-①）**：
- 一套「章节规则引擎」，两个出口：
  - `outline()`：运行时识别（供阅读器用）
  - `materialize()`：批处理切分（供分析管线用）
- 共用同一份规则表（`chapterRules.json`），保证"读到的章节"与"切出的章节"永远一致

**当前实现**：
- 前端 `lib/chapters.ts`：正则解析，运行时识别 → 章节树
- 后端 `storage.py`：`add_book` / `add_chapters` 从全文提取章节信息入库
- 两处正则**不完全相同**：
  - 前端：`/^第([0-9一二三四五六七八九十百千万零〇两壹贰叁肆伍陆柒捌玖拾佰仟]+)(章|回|节|卷)\s*(.*)$/`
  - 后端：（需确认，但从数据看 120 章匹配一致）
- 无共用规则表，无 `materialize()` 批处理切分接口

**偏差原因**：
- 章节识别是个简单问题，两端各自实现了一版，目前恰好一致
- 但没有"单一事实源"的规则表，长期有漂移风险

**建议**：把章节正则抽成共享常量（或在 sidecar 提供 `chapter_outline` 方法，前端直接调用），消除双实现漂移风险。

## 五、通域偏差（X1–X3）

### 5.1 🟡 X1 混合检索：只有向量路，结构化路未合并

**原计划（V1.0 §2.3-③）**：
```
用户提问
  ├─ 结构化通路：查 SQLite 索引表（人物→出场 / 事件→章节 / 情绪→趋势 / 伏笔→线索）
  │     → 命中即得到【确定性答案 + 精确出处】
  └─ 语义通路：sqlite-vec 向量召回 topK 片段
        → 得到【相关原文片段】
  ↓ 合并去重、按锚点排序
  ↓ 交给 LLM 作答，答案每一句都附 (章, 物理行) 锚点
```

**当前实现**：
- ✅ 语义通路：向量 RAG 完整实现（分块 / 嵌入 / 索引 / 检索）
- ✅ 结构化查询 API：sidecar 有 `list_events` / `list_entities` / `get_entity` / `list_mentions` / `list_foreshadows` / `list_relations`
- ❌ **合并逻辑**：未实现——两路检索是独立的，没有在 `ask_ai` 里合并去重排序
- ❌ 答案带锚点：未验证（LLM 不可用）

**偏差原因**：LLM 不可用导致整条链路无法端到端验证，混合检索的合并逻辑延后了。

## 九、偏差原因分析

### 9.1 合理的优先级调整（可接受）

1. **先做数据层，后做可视化**：M4 先把 2235 事件 / 389 人物 / 30027 出场 / 1297 伏笔 / 2370 关系全部回灌入库，再考虑画图——这是对的，没有数据的图表是空壳。
2. **阅读尺升级到视觉行级**：原计划阅读尺是简单的"单行聚焦"，实际做成了视觉行级 + 3 行聚焦带 + 空行跳过 + 键盘导航——超预期，投入产出比高。
3. **M4.5 全书情感预处理**：原计划没有这个里程碑，后追加的。把情感分析从"实时算"变成"开书即备"，大幅提升了阅读体验，决策正确。

### 9.2 路径依赖（需注意）

1. **回灌路线绕过了 A1 分词**：M4 全景数据从 MD 报告回灌，而不是 sidecar 实时计算——导致 jieba 分词引擎至今没搬进 sidecar。未来如果要做"打开任意小说自动分析"，A1 是必须补的。
2. **前端列表替代了可视化**：PanoramaPanel 用列表展示了事件/人物/伏笔/关系，能看能用，但不是原计划的"可视化交互"。容易让人产生"M4 完成了"的错觉，实际上可视化这一层完全没动。

### 9.3 外部依赖阻塞

1. **LLM API Key 无效（N1）**：导致 M3 整条链路无法端到端验证，混合检索合并、流式输出、答案锚点等功能都延后了。这是外部问题，不是架构偏差。

## 十一、结论

### 核心架构：一致 ✅

最关键的架构决策全部按原计划落地：
- **Tauri + Python sidecar + stdio JSON-RPC** —— 完全一致
- **物理行作为统一锚点** —— 完全一致
- **SQLite 为骨的存储架构** —— 基本一致
- **Monaco 阅读器内核** —— 完全一致
- **读域抄 ColorTxt / 析域留 V2.0** 的大方向 —— 完全一致

### 功能完成度：约 55–60%

- 读域：~65%（核心阅读体验到位，标注/辅助功能部分缺失）
- 析域数据层：~85%（情感/事件/人物/伏笔/关系数据全部入库）
- 析域交互层：~30%（就地标记 / 角色卡 / 时间线 等"析回灌读"的交互做得少）
- 通域可视化：~0%（图表库都没装）
- 通域检索：~60%（向量路通，结构化路未合并）

### 最大偏差：可视化缺失 🔴

当前最大的架构缺口是 **X2 呈现与导出（可视化 + 导出）完全未启动**。数据都准备好了，但没有图、没有导出、没有"分析结果的视觉化呈现"。这是 M4 与原计划差距最大的地方。

### 整体评价

**骨架是对的，肉还没长全。** 核心架构决策（Tauri+sidecar、物理行锚点、Monaco、SQLite）全部正确落地，没有走偏。但功能实现上，"数据层"跑得快，"交互层"和"可视化层"落在后面——导致从"能用"到"好用"之间还有距离。

好消息是：数据都在库里了，后续补可视化和交互是"挂数据"的工作，难度比建地基小得多。
